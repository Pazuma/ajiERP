# 项目汇总任务统计关联优化方案

> 文档日期：2026-09-20  
> 当前阶段：方案沉淀，尚未修改业务代码。  
> 目标：解决项目详情中已有“进度节点/任务”，但 ERPNext“项目汇总”显示总任务数为 0 的口径不一致问题。

## 1. 问题结论

当前系统存在两套不同的“任务”概念：

| 名称 | 实际数据来源 | 当前项目汇总是否统计 |
|---|---|---|
| 标准任务 | ERPNext `Task`，通过 `Task.project` 关联 `Project.name` | 是 |
| 项目进度节点 | `Project Progress Item`，位于 Project 的进度节点子表 | 否 |

标准“Project Summary”报表按以下逻辑统计：

```python
frappe.db.count("Task", filters={"project": project.name})
```

因此，项目详情中维护的进度节点不会进入“总任务数、已完成任务、逾期任务”的统计。

已核对测试站点：项目记录存在，但 `tabTask` 没有对应标准任务记录；项目进度节点属于另一张子表。这是当前显示为 0 的直接原因，不是报表缓存或页面刷新问题。

## 2. 优化目标

让用户在项目下维护的“项目进度节点”能够以统一、明确的口径参与项目汇总，同时保留 ERPNext 标准 Task 的兼容能力。

推荐采用“项目汇总扩展统计”方案：

```text
标准 Task 统计 + 项目进度节点统计
```

但两者在页面中应明确区分，避免同一事项被重复计数。

## 3. 推荐方案：新增任务统计口径，不改老接口

### 3.1 统计字段

建议在项目汇总中新增以下字段，保留现有字段不变：

| 字段 | 含义 |
|---|---|
| `standard_total_tasks` | 标准 Task 数量 |
| `progress_item_total` | 项目进度节点数量 |
| `total_tasks` | 汇总展示总数，按产品最终口径计算 |
| `completed_tasks` | 已完成数量 |
| `overdue_tasks` | 逾期数量 |

初期建议采用“不重复计数”的口径：

```text
total_tasks = Project Progress Item 数量
```

标准 Task 继续单独展示，不直接与进度节点相加。原因是当前进度节点与标准 Task 没有一一对应关系，直接相加会造成重复统计风险。

若后续业务要求两者合计，再单独增加“统计来源/是否纳入汇总”的配置，不改变现有字段含义。

### 3.2 完成与逾期口径

项目进度节点状态目前使用项目进度状态，例如：

```text
待开始、进行中、待交接、已完成、已取消
```

建议映射为：

```text
已完成：status = "已完成"
逾期：expected_end_date < 当前日期 且 status not in ("已完成", "已取消")
```

标准 Task 仍沿用现有：

```text
Completed -> 已完成
Overdue   -> 逾期
```

## 4. 拟修改文件

### 4.1 报表后端

文件：

```text
apps/erpnext/erpnext/projects/report/project_summary/project_summary.py
```

拟调整内容：

1. 保留当前 `execute(filters)` 入口和返回结构。
2. 在查询每个 Project 时，新增读取 `Project Progress Item` 的统计方法。
3. 新增内部函数，例如：

```python
def get_progress_item_summary(project_name):
    ...
```

4. 为每一行补充进度节点统计字段。
5. 在 `get_chart_data` 和 `get_report_summary` 中使用新的明确字段。
6. 保留标准 Task 统计字段，避免影响已有调用方。

不建议修改 ERPNext `Project` DocType 的旧字段，也不建议直接回写 Project 上的冗余总数。

### 4.2 报表前端

3. 中文翻译继续走 Frappe `__()`，不硬编码页面文本。

4. 已完成、已取消、逾期节点的统计。
5. 空项目和无进度节点项目保持兼容。

## 5. 调用链路

当前链路：

```text
用户打开“项目汇总”
 -> project_summary.js 加载筛选条件
 -> Frappe 调用 Project Summary Script Report
 -> project_summary.py::execute(filters)
 -> 查询 Project
 -> 按 Task.project 统计 Task
 -> 生成表格、图表、顶部汇总
```

优化后链路：

```text
用户打开“项目汇总”
 -> 保持现有筛选条件
 -> execute(filters)
 -> 查询符合条件的 Project
 -> 查询标准 Task 统计
 -> 查询 Project Progress Item 统计
 -> 按明确口径生成 total/completed/overdue
 -> 返回原有报表结构 + 新增统计字段
```

项目详情已有的进度同步链路不需要改变：

```text
项目保存/进度节点操作
 -> client_akivision.utils.project_progress
 -> 更新 Project Progress Item 状态
 -> 项目汇总报表重新查询时实时读取
```

## 6. 受影响模块

| 模块 | 影响 |
|---|---|
| Projects / Project Summary | 主要修改点，增加进度节点统计 |
| Project 表单 | 不改现有字段和操作 |
| 项目进度节点 | 作为只读统计来源，不改变状态流转 |
| 标准 Task | 保留原有关联和统计能力 |
| 权限 | 查询沿用当前用户对 Project/Task 的权限过滤原则 |
| 日志 | 统计查询为只读，不新增业务操作日志 |
| 项目文件上传 | 无影响 |

## 7. 兼容性与小增量原则

1. 不修改现有报表入口 `execute(filters)`。
2. 不删除或重命名现有 `total_tasks`、`completed_tasks`、`overdue_tasks` 字段。
3. 不修改标准 Task 的 `project` 关联方式。
4. 不把进度节点自动创建为 Task，避免产生重复业务数据。
5. 不改变项目进度节点的交接式完成规则。
6. 无进度节点的历史项目继续显示原有标准 Task 统计结果。
7. 优先采用报表实时聚合，不新增需要维护一致性的冗余字段。

## 8. 预期效果

实施后：

- 项目详情中维护的进度节点可以在项目汇总看到对应数量。
- 标准 Task 与项目进度节点的统计来源清晰可追溯。
- 已完成、逾期统计不再因为只查询 `tabTask` 而全部显示为 0。
- 原有项目、标准 Task、筛选条件和报表路由保持兼容。
- 项目进度节点状态变化后，重新刷新报表即可看到最新统计。

## 9. 验收标准

1. 一个包含 3 个进度节点、无标准 Task 的项目，项目汇总显示进度节点数为 3。
2. 一个包含 2 个标准 Task、无进度节点的项目，原有标准 Task 统计保持正确。
3. 一个同时包含标准 Task 和进度节点的项目，不发生重复计数。
4. 完成一个进度节点后，已完成数增加 1。
5. 逾期节点按照预计结束日期和节点状态正确统计。
6. 项目汇总筛选公司、启用状态、项目状态仍然有效。
7. 不影响项目详情、进度节点操作、文件上传和已有操作日志。

## 10. 实施前需要最终确认的业务口径

在修改代码前，需要确认“总任务数”最终采用哪一种展示：

```text
A. 只显示项目进度节点数（推荐，避免重复）
B. 只显示标准 Task 数
C. 标准 Task + 进度节点合计
D. 同时展示两类数量，不提供合计
```

本方案默认采用 A，并保留标准 Task 独立统计字段，后续如业务确认采用 C，只需调整报表汇总计算，不需要改动项目进度节点和标准 Task 的数据结构。
