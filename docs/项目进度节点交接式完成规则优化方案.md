# 项目进度节点交接式完成规则优化方案

> 文档日期：2026-09-16  
> 当前阶段：方案沉淀，尚未修改代码。  
> 目标：将项目进度节点完成规则从“当前节点表单完成即节点完成”，调整为“下一个节点开始时，上一个节点才算完成”，让节点耗时更符合真实业务流转周期。

## 1. 背景

当前项目进度节点已经具备以下能力：

```text
项目进度节点维护
节点绑定业务表单
业务表单保存/提交后回写节点关联单据
节点状态、实际开始时间、实际完成时间、耗时展示
项目总览展示当前进度节点和当前节点耗时
```

但当前规则偏向“表单完成即节点完成”：

```text
节点 A 的关联表单完成/提交
 -> 节点 A 立即完成
 -> 节点 B 自动进入进行中
```

这个口径在实际项目管理中会有偏差。很多节点的真实结束并不是“表单做完”，而是“下一环节真正开始”。例如：

```text
采购订单已经完成
但采购送货单还没有开始
```

这段等待时间仍然应该算在“采购订单到采购送货交接”的周期里，而不是直接把采购订单节点结掉。

因此需要调整为交接式完成规则：

```text
节点 A 做完准备动作
 -> 节点 A 进入待交接/已就绪
 -> 等节点 B 开始
 -> 节点 A 才正式完成
 -> 节点 A 的完成时间 = 节点 B 的开始时间
```

## 2. 本次优化目标

### 2.1 核心目标

将节点完成规则调整为：

```text
下一个节点开始时，上一个节点才算结束。
```

### 2.2 保留现有能力

本次不推翻现有项目进度能力，继续保留：

```text
节点绑定业务单据
关联单据回写到项目节点
项目总览展示当前节点
节点耗时展示
项目列表展示当前进度
```

### 2.3 小增量改造原则

本次优先采用新增分支、兼容旧字段的方式：

```text
不大改老接口
不重建 DocType
不影响已有项目节点数据
不改变业务表单原有保存/提交流程
仅调整项目进度联动口径
```

## 3. 新业务规则

## 3.1 节点状态建议

建议在现有状态基础上增加一个中间状态：

```text
待处理
进行中
待交接
已完成
延期
已取消
```

其中：

```text
进行中：
  当前节点已经开始执行。

待交接：
  当前节点的关联表单已经完成或人工确认完成，
  但下一个节点尚未开始，
  当前节点还不能正式结项。

已完成：
  下一个节点已经开始，
  当前节点正式结束。
```

如果暂时不想新增状态，也可以将“待交接”作为前端展示语义，后端仍保存为“进行中”，但不推荐。因为用户会看到表单完成后节点还显示“进行中”，容易误解。

推荐方案：

```text
后端状态正式新增：待交接
前端明确展示：待交接，等待下一节点开始
```

## 3.2 节点开始规则

节点第一次进入执行时，记录：

```text
actual_started_on = 当前时间
status = 进行中
```

注意：

```text
如果 actual_started_on 已经有值，不重复覆盖。
```

原因：

```text
节点可能反复重算，开始时间应该代表第一次真正开始的时间。
```

## 3.3 节点准备完成规则

当前节点关联表单完成后，不再直接把节点改成“已完成”。

改为：

```text
关联表单保存/提交/人工确认完成
 -> 当前节点 status = 待交接
 -> 保留 actual_started_on
 -> 不写 actual_completed_on
 -> 不计算最终 duration_days
 -> duration_display 显示“待交接，已进行X天”
```

示例：

```text
采购订单节点开始：2026-09-16 10:00
采购订单表单提交：2026-09-16 15:00

此时：
采购订单节点状态 = 待交接
实际开始时间 = 2026-09-16 10:00
实际完成时间 = 空
耗时 = 待交接，已进行1天
```

## 3.4 下一个节点开始规则

当节点 B 开始时，系统需要同时处理节点 A：

```text
节点 B 开始
 -> 节点 B status = 进行中
 -> 节点 B actual_started_on = 当前时间

 -> 找到节点 B 的上一个未完成节点 A
 -> 节点 A status = 已完成
 -> 节点 A actual_completed_on = 节点 B actual_started_on
 -> 节点 A duration_days = 节点 B actual_started_on 日期 - 节点 A actual_started_on 日期 + 1
 -> 节点 A duration_display = "{duration_days}天"
```

示例：

```text
采购订单节点开始：2026-09-16 10:00
采购订单表单提交：2026-09-16 15:00
采购送货单节点开始：2026-09-18 09:00

最终：
采购订单实际完成时间 = 2026-09-18 09:00
采购订单耗时 = 3天
采购送货单状态 = 进行中
```

## 3.5 最后一个节点完成规则

最后一个节点没有“下一个节点”触发结束，需要单独处理。

建议采用人工确认方式：

```text
最后一个节点关联表单完成
 -> 最后一个节点进入待交接
 -> 项目负责人点击“完成项目”或“完成最后节点”
 -> 最后一个节点写入 actual_completed_on
 -> 项目流程进度达到 100%
```

原因：

```text
最后节点完成通常意味着整个项目阶段结束，
不建议由普通业务表单提交自动关闭项目。
```

首期如果需要更简单，也可以做配置：

```text
最后节点表单完成后自动完成最后节点：默认关闭
```

本方案首期建议先不做配置开关，采用人工确认，更稳。

## 5. 调用链路设计

### 5.1 业务表单完成当前节点

```text
业务表单保存/提交
 -> project_progress_reference 同步关联信息
 -> 后端 mark_progress_step_ready(project, milestone_code, reference_doctype, reference_name)
 -> 当前节点变为“待交接”
 -> 更新 Project 当前节点显示
 -> 刷新项目进度
```

说明：

```text
这里不再调用“完成节点”逻辑。
这里只代表当前节点的业务表单已经完成，等待下一节点启动。
```

### 5.2 启动下一个节点

```text
项目进度页面点击“开始节点”
 或 从项目关联区创建/绑定下一节点表单
 或 业务表单保存时识别为下一节点正式开始
 -> start_progress_step(project, milestone_code)
 -> 当前节点写入 actual_started_on
 -> 上一个未完成节点写入 actual_completed_on
 -> 重新计算节点耗时
 -> 重新计算项目当前节点
 -> 刷新项目详情/总览
```

### 5.3 项目总览展示

```text
打开 Project List / Project Form
 -> 读取 Project.custom_current_progress_step
 -> 读取 Project.custom_current_progress_duration
 -> 若当前节点状态为待交接，展示“节点名（待交接）”
 -> 若当前节点状态为进行中，展示“节点名（已进行X天）”
```

## 8. 兼容历史数据

历史数据可能存在：

```text
节点已经是已完成
actual_completed_on 已经有值
duration_display 已经计算
```

处理原则：

```text
1. 已完成节点不主动回滚为待交接。
2. 已有 actual_completed_on 的节点保留原值。
3. 只对后续新触发的节点流转使用新规则。
4. 手动点击“重新计算进度”时，也不覆盖历史已完成时间，除非用户明确选择重算。
```

这样可以避免历史项目数据突然变化。

## 9. 权重与进度百分比口径

新规则下，“待交接”不计入已完成权重。

示例：

```text
采购订单权重 40%
采购送货单权重 60%

采购订单状态 = 待交接
流程实际进度 = 0%

采购送货单开始后：
采购订单状态 = 已完成
流程实际进度 = 40%
```

原因：

```text
既然业务口径定义为“下一个节点开始时，上一个节点才算结束”，
那么待交接还不应该贡献完成进度。
```

## 10. 异常场景处理

### 10.1 用户跳过中间节点，直接开始后面节点

建议首期允许，但需要提示：

```text
中间存在未完成节点，是否仍开始该节点？
```

如果用户确认：

```text
前一个待交接节点完成
中间待处理节点保持待处理
目标节点进入进行中
```

为了小增量，首期可以先限制只能开始“当前节点或下一个节点”，避免状态跳跃。

推荐首期规则：

```text
只能开始第一个待处理节点。
```

### 10.2 当前节点表单取消提交

如果业务表单被取消：

```text
若当前节点为待交接：
  恢复为进行中
  清除 reference 的完成状态

若当前节点已经因为下一节点开始而已完成：
  首期不自动回滚下一节点
  记录提示，需要人工处理
```

原因：

```text
节点已经交接后再取消上游单据，属于业务异常，自动回滚风险较高。
```

### 10.3 多个表单绑定同一节点

如果一个节点绑定多个业务表单：

```text
所有必需表单完成后，节点才进入待交接。
```

首期如果系统仍是一节点一主单据，则保持现状：

```text
主关联单据完成后，节点进入待交接。
```

### 10.4 最后节点没有下一节点

最后节点进入待交接后：

```text
需要人工点击“完成最后节点/完成项目”。
```

首期不自动完成项目。

## 12. 实施顺序建议

建议按小增量分三步实现：

### 第一步：后端口径调整

```text
1. status 增加“待交接”。
2. 新增 mark_progress_step_ready。
3. 新增/调整 start_progress_step。
4. 调整耗时计算。
```

### 第二步：前端显示和入口

```text
1. 项目进度页面显示“待交接”。
2. 增加“开始节点”入口。
3. 项目列表显示待交接状态。
```

### 第三步：业务表单联动

```text
1. 业务表单完成后进入待交接。
2. 创建/绑定下一节点表单时启动下一节点。
3. Playwright 跑完整闭环。
```

## 13. 最终预期闭环

完整业务闭环如下：

```text
项目开始
 -> 第一个节点进入进行中
 -> 创建/绑定第一个节点业务表单
 -> 第一个节点表单完成
 -> 第一个节点进入待交接
 -> 创建/启动第二个节点
 -> 第一个节点自动完成，完成时间=第二个节点开始时间
 -> 第二个节点进入进行中
 -> 项目总览显示第二个节点
 -> 重复直到最后节点
 -> 最后节点待交接
 -> 人工确认完成项目
```

最终用户看到的效果：

```text
表单做完不会马上把节点关掉。
只有下一步真正开始，上一步才结束。
节点耗时包含中间等待和交接时间。
项目总览能准确看到项目卡在哪一步。
```
