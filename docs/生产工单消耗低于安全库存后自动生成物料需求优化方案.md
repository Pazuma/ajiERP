# 生产工单消耗低于安全库存后自动生成物料需求优化方案

## 1. 问题结论

生产工单提交、制造出库或物料转移提交后，ERPNext 不会同步创建物料需求单。当前自动补货由 ERPNext 的定时任务 `erpnext.stock.reorder_item.reorder_item` 负责，属于库存重订货流程，不属于生产工单流程。

因此，“螺丝消耗后库存低于安全库存，但没有立即出现物料需求”通常是以下原因之一：

1. 期待了即时触发，但系统只按定时任务执行。
2. 站点 scheduler 或 worker 未运行。
3. `Stock Settings.auto_indent` 未启用。
4. 螺丝没有配置有效的 `Item Reorder` 行。
5. 配置的是自定义“最低安全库存”字段，但标准补货逻辑读取的是 `Item Reorder.warehouse_reorder_level`。
6. 实际比较值是仓库 `projected_qty`，不只是当前实际库存。

## 2. 当前实现与关键约束

### 2.1 标准触发链路

```text
生产工单
  -> 制造/转移 Stock Entry 提交
  -> Bin.actual_qty / projected_qty 更新
  -> scheduler 执行 daily_maintenance
  -> erpnext.stock.reorder_item.reorder_item
  -> 读取 Item Reorder
  -> projected_qty <= warehouse_reorder_level
  -> 创建并提交 Material Request
```

标准任务位于 ERPNext `daily_maintenance` 事件中，并非 Stock Entry 或 Work Order 的 `on_submit` 事件。因此页面刷新、重新打开工单或重新提交工单都不会主动补建物料需求。

### 2.2 标准逻辑读取的字段

| 对象 | 字段 | 作用 |
| --- | --- | --- |
| Stock Settings | `auto_indent` | 是否允许自动创建物料需求 |
| Item | `is_stock_item`、`disabled` | 是否纳入补货计算 |
| Item Reorder | `warehouse` | 触发补货的仓库 |
| Item Reorder | `warehouse_reorder_level` | 重订货点/安全库存比较值 |
| Item Reorder | `warehouse_reorder_qty` | 默认补货数量 |
| Item Reorder | `material_request_type` | Purchase、Transfer、Manufacture 等 |
| Bin | `projected_qty` | 实际用于触发比较的预计库存 |

自定义的“最低安全库存”或“安全库存预警线”字段不会被 ERPNext 标准 `reorder_item` 自动读取，除非额外开发字段同步或替换补货逻辑。

## 3. 推荐优化方案

### 3.1 先修复标准配置

这是上线风险最低的方案，建议优先执行：

1. 在 Stock Settings 开启 `自动创建物料需求（auto_indent）`。
2. 在螺丝 Item 的 `Item Reorder` 表中增加实际消耗仓库的记录。
3. 将安全库存填写到 `warehouse_reorder_level`。
4. 将补货数量填写到 `warehouse_reorder_qty`。
5. 选择正确的 `material_request_type`，采购补货使用 `Purchase`。
6. 确认仓库启用、归属公司正确，螺丝为库存物料且未停用。
7. 启用站点 scheduler、Redis 和 worker。

配置完成后，自动物料需求最迟在下一次 `daily_maintenance` 执行时生成，而不是在工单提交瞬间生成。

### 3.2 增加“立即检查”入口

如果业务要求工单消耗后立即检查，建议增加一个明确的后台方法或按钮，而不是修改标准库存计算：

1. 在制造 Stock Entry 提交成功后，提交一个短队列任务。
2. 任务只调用统一的安全库存检查服务。
3. 服务按 Item、仓库汇总 `projected_qty`，读取安全库存和补货数量。
4. 使用幂等键避免重复创建，例如 `item_code + warehouse + 未关闭需求`。
5. 创建 Material Request 时记录来源工单/Stock Entry，便于追溯。
6. 失败时写入 Error Log，并在页面提示“已提交检查，结果稍后可见”。

不建议在前端 JavaScript 中直接创建物料需求，也不建议复制一份 ERPNext `reorder_item.py` 后长期维护；这会造成权限、并发和版本升级风险。

### 3.3 统一安全库存字段

如果业务必须使用自定义安全库存字段，应选定唯一数据源：

- 方案 A：保留标准 `Item Reorder.warehouse_reorder_level`，将自定义字段作为展示或报表字段。
- 方案 B：保留自定义字段，在保存 Item/Item Reorder 时同步到标准字段。
- 方案 C：实现自定义补货服务，明确优先级、仓库范围、预计库存算法和重复需求合并规则。

推荐方案 A 或 B，避免同一物料同时存在两套互相矛盾的安全库存数值。


## 6. 回归标准

- 工单制造出库后库存数量正确扣减。
- 定时任务正常执行且无 Redis/worker 错误。
- 达到重订货点时只生成一张有效物料需求，不重复生成。
- 未达到安全库存时不生成物料需求。
- 同物料不同仓库分别按各自安全库存计算。
- 已有未完成采购需求时不会无限重复补货。
- 物料需求可追溯到物料、仓库、工单或 Stock Entry。
- 权限不足用户不能通过前端或接口越权创建补货需求。

## 7. 实施建议

先按 3.1 修复标准配置并通过 4 节验收；若业务仍要求“工单提交后立即生成”，再实施 3.2 的后台异步检查和幂等控制。不要把“安全库存报表显示低于阈值”直接等同于“ERPNext 自动补货条件已满足”，两者必须使用同一数据源和同一仓库口径。

## 10. 自动物料需求标题

即时补货服务创建的采购类物料需求，标题统一为 `采购申请-物料名`。标题取自动补货明细中的物料名称；同一批次包含多个物料时，按去重后的物料名称以逗号连接，并控制在标题字段长度以内。物料名称缺失时回退到物料编码，避免生成空标题。

该规则只作用于 `production_reorder._create_material_request` 的自动记录。用户手工新建、Excel 导入或 ERPNext 其他来源创建的物料需求仍保留原有标题生成规则；历史物料需求也不会被批量改名。

## 11. 已入库后再次低于安全库存的补货修复

### 11.1 问题与根因

测试流程“自动采购申请入库 -> 再次生产消耗同一物料 -> 库存低于安全库存”本身正确。实测螺丝 `common item1` 在 `进行中 - T` 的实际库存为 2、安全库存为 12，且制造出库 `MAT-STE-2026-00046` 已提交并实际消耗 50 个螺丝，满足自动补货条件。

未生成新申请的原因是历史自动采购申请 `MAT-MR-2026-00020` 已经为 `Received`，但旧版 `_has_open_request` 只排除了 `Stopped`、`Cancelled`、`Completed`。它错误地把已完成收货的申请当作未关闭申请，进而跳过本次创建。

### 11.2 修复内容与数据流

`_has_open_request` 现在将 `Received` 一并视为已关闭状态。已收货采购申请不再阻止下一次补货；草稿、待采购、待收货及部分收货状态仍会阻止重复创建，避免同一缺口被重复采购。

```text
制造出库提交
  -> after_commit 短队列检查实际来源仓库
  -> Bin.projected_qty <= Item Reorder 安全库存
  -> 查询同物料、同仓库、同申请类型的未关闭申请
  -> 忽略 Stopped / Cancelled / Completed / Received
  -> 不存在有效未关闭申请时，创建并提交 采购申请-物料名
```

### 11.3 依赖清单

| 依赖 | 要求 |
| --- | --- |
| Stock Entry | 已提交，类型为 `Manufacture` 或 `Material Transfer for Manufacture`，且有来源仓库 |
| Item / Item Reorder | 物料启用且为库存物料；实际消耗仓库配置安全库存和补货数量，或 Item 配置 `safety_stock` |
| Bin | `projected_qty` 小于或等于阈值 |
| Material Request | 仅同物料、同仓库、同类型且未关闭的申请会阻止创建 |
| 队列与 Hook | `Stock Entry.on_submit` Hook、生效的 worker 与 Redis 队列 |

### 11.4 风险与复测场景

| 风险点 | 处理和复测要求 |
| --- | --- |
| 已收货记录被误判为未完成 | 已修复；完成入库后再次消耗并低于阈值，应生成一张新申请 |
| 待收货或部分收货时重复采购 | 仍应阻止新申请；确认业务上部分收货需继续等待原申请 |
| 不同仓库相互影响 | 同物料分别在两个仓库触发，均可各自产生申请 |
| 重复执行任务 | 对同一未关闭申请重复执行检查，不应产生第二张申请 |
| 队列执行失败 | 检查 Error Log；当前实现会在入队异常时回退为同步检查 |

## 12. 防止队列服务再次漏启动

本开发环境的 Frappe 服务运行在 `devcontainer-frappe-1`，不是宿主机的 bench。过去 `frappe` 容器使用 `sleep infinity` 作为主进程，容器虽然显示为运行中，但 web、worker 和 scheduler 并未启动，导致生产提交产生的 `check_reorder_for_stock_entry` 长时间停留在 Redis 队列。

`.devcontainer/docker-compose.yml` 已改为容器启动时执行 `cd /workspace/development/frappe-bench && exec bench start`，并设置 `restart: unless-stopped`。以后重新创建或重启开发环境时使用：

```bash
docker compose -f .devcontainer/docker-compose.yml up -d --force-recreate frappe
```

启动后必须确认 worker 在线，而不能只看容器状态：

```bash
docker exec devcontainer-frappe-1 bash -lc \
  'cd /workspace/development/frappe-bench && bench --site aji_test.localhost doctor'
```

验收标准：

- `Workers online` 至少为 `1`；
- `show-pending-jobs` 中不应持续堆积 `check_reorder_for_stock_entry`；
- `/tmp/bench-start.log` 无 worker、Redis 或 scheduler 启动错误。

代码或 hooks 变更后，执行迁移和清缓存：

```bash
docker exec devcontainer-frappe-1 bash -lc \
  'cd /workspace/development/frappe-bench && bench --site aji_test.localhost migrate --skip-search-index && bench --site aji_test.localhost clear-cache'
```

若发现 worker 为 0，先恢复服务再判断业务逻辑：

```bash
docker compose -f .devcontainer/docker-compose.yml up -d --force-recreate frappe
```
