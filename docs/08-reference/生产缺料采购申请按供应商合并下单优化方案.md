# 生产缺料采购申请按供应商合并下单优化方案

## 1. 背景与目标

生产工单在领料或库存移动时发现物料不足，系统当前可弹出缺料提示，并通过“发起采购申请”入口创建采购申请。采购人员随后对申请物料进行供应商比价、选择供应商，再组织采购。

实际采购习惯是：

1. 缺料物料逐项申请、逐项比价及确定供应商；
2. 采购人员最终按供应商合并采购需求；
3. 通常一个供应商生成一张采购订单；
4. 采购订单必须可追溯到每张申请、每个需求物料以及发起需求的生产工单；
5. 在保留现有采购申请、比价和采购订单能力的前提下，小增量实现，不改动旧接口行为。

本方案描述后续代码实施范围。本轮仅沉淀方案，不修改业务代码。

## 2. 当前系统能力与差距

### 2.1 已有能力

- Stock Entry 库存不足弹窗可解析缺料物料、仓库和缺口数量；
- 弹窗提供“发起采购申请”入口；
- Material Request 支持 Purchase 类型申请；
- Purchase Comparison 可从已提交采购申请创建/恢复，并复用现有价格规则、供应商报价、Item Price 和历史采购价进行比价；
- 比价单支持逐物料候选供应商、选择结果和预选供应商；
- 可根据选中的比价行生成采购订单草稿；
- 采购订单草稿可按供应商/company/比价单复用，并保留 Material Request 明细引用。

### 2.2 当前与目标的差距

1. 缺料弹窗现在将多个缺料物料一并放入一张 Material Request，而业务希望一物料一申请；
2. 采购比价目前围绕单张 Material Request 创建；
3. 不同申请对应不同比价单时，现有 PO 草稿复用范围通常被比价单隔开，无法稳定将不同申请的同供应商需求汇总到同一张采购订单；
4. 标准 Purchase Order Item 的单个 Material Request 明细引用不能表达多张申请的来源分摊；
5. 部分下单和剩余未下单数量需在多来源合并场景下明确防重与追踪规则。

## 3. 目标流程

```text
生产工单/Stock Entry 检查到缺料
    ↓
缺料弹窗按物料拆分采购申请（每物料一张）
    ↓
申请保留来源工单、工单物料行、仓库、缺料数量和需求日期
    ↓
采购申请提交
    ↓
每张申请分别进入现有 Purchase Comparison 比价
    ↓
采购人员逐申请确认供应商、价格和订购数量
    ↓
打开“按供应商汇总待下单”工作台/列表
    ↓
按公司 + 供应商分组，采购人员检查并勾选可下单数量
    ↓
每个供应商生成/复用一张草稿 Purchase Order
    ↓
PO 行保留多来源分摊；来源申请回写已转数量、剩余数量和 PO
    ↓
采购订单提交、收货，沿用现有采购流程
```

## 4. 业务规则建议

### 4.1 一物料一张申请

- 从缺料弹窗发起时，按缺料行分别创建采购申请；每张 Material Request 只包含一个物料行。
- 同一物料若在一次缺料结果中出现多行，是否合并为同仓库/同单位一张申请，应以物料 + 仓库 + 单位为拆分键；若来源工单行不同，申请仍需保存多个来源关系，不能覆盖来源。
- 申请数量使用后端缺料校验结果为准，前端解析只负责展示和传参，后端需重新验证数据或至少校验必要字段。
- 创建过程应支持部分失败：某个物料创建失败，不应让其他已成功创建的申请丢失；反馈每个物料对应的结果。
- 对相同 Stock Entry / Work Order / item / warehouse 已有未取消、未完成的缺料申请时，应提示已存在或按剩余缺口补差，避免重复创建。

### 4.2 来源追溯

每张采购申请保存：

- 来源生产工单；
- 来源 Stock Entry（如从库存移动弹窗发起）；
- 来源工单物料行或库存移动行；
- 来源销售订单及销售订单行（工单存在销售订单时）；
- 缺料仓库、需求日期、原始缺口数量。

若一张申请允许聚合多个来源，使用来源明细子表保存来源单据和数量，不将多个来源压缩为一个 Link 字段。

### 4.3 比价和中选规则

- 不复制报价计算，继续以 Purchase Comparison 为每张 Material Request 的比价工作流和价格记录。
- 比价完成后，由采购人员确认最终供应商、报价、下单数量和报价有效性；系统自动推荐结果不等于最终确认。
- 只有已提交申请、比价有效、供应商明确、单价有效、剩余未下单数量大于零的申请明细进入待下单池。
- 用户修改供应商或价格时，必须重新校验报价/公式价格；若价格依据已失效，要求刷新比价。
- 无报价申请继续走现有询价流程，不得以空价或默认价生成正式采购订单草稿。

### 4.4 按供应商汇总采购订单

- 汇总键建议为 company + supplier + currency + buying_price_list + schedule/收货条件（若条件不兼容应拆为不同订单）。
- 默认一个供应商一张采购订单；如现有草稿 PO 的公司、币种、价格表或采购条款不兼容，则另建订单并在汇总界面提示原因。
- 采购人员可以选择部分申请或部分数量转 PO；未转部分继续进入待下单列表。
- 同一物料可以在一个 PO 中合并为一行，但保留独立来源分摊明细；如 ERPNext 原生 MR 引用限制或其他标准逻辑要求，第一阶段可以先保留多个同物料 PO 行以保持原生追溯，合并行作为后续优化。
- 不自动提交采购订单，由采购人员审核草稿后按既有权限提交。

### 4.5 防重及状态

建议以“申请明细行”作为数量台账，记录：

- 申请数量；
- 已转采购订单数量；
- 当前可下单剩余数量；
- 关联采购订单和采购订单明细；
- 转单状态：待比价、待确认、待下单、部分下单、已下单、已取消/已关闭。

创建 PO 来源关系必须幂等，并在服务端锁定/重新读取剩余数量后校验。取消 PO 或删除 PO 草稿时，应释放对应数量；已提交 PO 的取消按 ERPNext 原生采购申请 ordered_qty 逻辑与本地来源台账同步，不能只改自定义状态。

## 5. 数据模型方案

优先新增字段和子表，不更改标准 Material Request / Purchase Order 必需字段。

### 5.1 Material Request / Material Request Item

建议新增自定义字段（按当前系统已经存在的字段复用，避免重复创建）：

| 字段 | 类型 | 用途 |
|---|---|---|
| `custom_purchase_source_type` | Select | 标记生产缺料等来源场景 |
| `custom_source_work_order` | Link: Work Order | 单一主要来源工单，便于列表过滤 |
| `custom_source_stock_entry` | Link: Stock Entry | 发起缺料的库存移动单据 |
| `custom_source_sales_order` | Link: Sales Order | 来源工单关联的销售订单 |
| `custom_purchase_batch_key` | Data | 防重复申请/补差识别键 |

建议申请明细或来源子表记录 item、warehouse、source row、requested qty 和已下单 qty。若一单严格一物料且只有一个来源，可以先把字段放在 MR Item；若同一物料可聚合多个工单来源，则新增 `Material Request Source Detail` 子表。

不重复新增当前已有的预选供应商、比价状态、最近比价单等字段；它们由 `misc_purchase.ensure_schema` 等现有逻辑维护。

### 5.2 新增采购订单来源分摊子表

建议新增 Child DocType：`Purchase Order Source Allocation`，挂载 Purchase Order 或 Purchase Order Item（建议挂 PO Item，追溯更精确）。字段：

| 字段 | 类型 | 用途 |
|---|---|---|
| `material_request` | Link: Material Request | 来源采购申请 |
| `material_request_item` | Link/Data | 来源申请明细行 |
| `purchase_comparison` | Link: Purchase Comparison | 比价来源 |
| `work_order` | Link: Work Order | 来源工单，可冗余快照便于筛选 |
| `work_order_item` | Data | 来源工单物料/子行标识 |
| `source_stock_entry` | Link: Stock Entry | 缺料单据来源 |
| `qty` | Float | 分摊到该来源申请的采购数量 |
| `received_qty` | Float | 可选：来源分摊的收货数量 |

子表是跨申请合并采购订单的追溯关键；标准 Purchase Order Item 的单一 `material_request` / `material_request_item` 继续尽量填入单一来源兼容旧功能，但完整多来源关系以新增分摊明细为准。

### 5.3 汇总操作记录

第一阶段可不新增独立头 DocType：通过新增供应商采购汇总页面/API 临时生成候选分组；提交创建 PO 后，来源分摊明细和标准单据链接作为持久记录。

若采购人员需要保存“待下单篮子”、多人协作或后续审批，第二阶段再新增 `Supplier Purchase Consolidation` 头单及其来源行。本阶段不预先引入复杂工作流。

## 7. 调用链路与模块影响

### 7.1 创建缺料申请链路

```text
Stock Entry 原生库存不足校验
  → stock_entry_shortage_dialog.js 增强弹窗
  → 新增 create_purchase_requests_for_shortages API
  → 服务端校验/去重/拆分
  → 多张单物料 Material Request 草稿
  → 采购人员检查并提交
```

旧库存不足校验、错误消息和弹窗仍然有效；新增 API 仅承担采购申请创建分支。

### 7.2 比价与选供应商链路

```text
单物料 Material Request 提交
  → 现有 material_request.js 的 Compare Suppliers
  → 现有 purchase_comparison.create_from_material_request
  → 现有 Purchase Comparison 价格引擎
  → 采购人员选择供应商/数量/价格
```

该链路不替换、不复制，也不改变原有比价 API。

### 7.3 按供应商汇总下单链路

```text
采购人员打开汇总工作台并选择供应商
  → 新 API 查询该供应商各申请的已确认、未下单剩余量
  → 选择申请和部分数量
  → 服务端锁定/重新读取来源数量及价格状态
  → 按兼容条件生成或复用该供应商草稿 PO
  → 每条 PO Item 写来源分摊行
  → 返回 PO 链接
  → PO 提交/取消后更新来源台账和剩余待下单数量
```

### 7.4 受影响模块

| 模块 | 变更 | 兼容方式 |
|---|---|---|
| 制造/库存弹窗 | 采购申请由多物料一张改为单物料多张 | 保留原缺料校验，仅新增创建分支 |
| Material Request | 记录工单来源及缺料上下文 | 新增可选字段/来源子表；普通申请不受影响 |
| Purchase Comparison | 继续每张申请单独比价 | 复用现有 DocType 和接口 |
| 询价/RFQ | 无价格来源时仍可询价 | 保留原询价逻辑 |
| Purchase Order | 按供应商跨申请集中生成草稿 | 新增汇总入口，不替换既有单申请转 PO 接口 |
| 采购收货 | 按标准 PO 收货 | 不改收货和库存估值接口 |
| Buying Workspace | 增加待下单汇总入口 | 新增 sidebar link/page |
| 权限/审计 | 限制创建、比价和批量下单角色 | 复用 Frappe 权限并保留 Version/Comment/来源关系 |
| 报表/列表 | 可按供应商、工单、申请查看待下单与已下单量 | 新增字段筛选/汇总，不改变旧报表列含义 |

## 8. 小增量与接口兼容原则

1. 保留 `create_from_material_request`、`run_comparison_for`、`create_po_drafts` 等现有函数签名及返回结构。
2. 新增缺料采购 API 与供应商汇总下单 API；旧客户端不调用新 API 时仍走原行为。
3. 现有标准 Material Request 到 Purchase Order 的映射和用户手工创建 PO 的流程不改。
4. 先从缺料弹窗新入口实施“拆分单物料申请”，不改变手工创建的多物料采购申请。
5. 先保留多来源 PO 行分拆，确保 ERPNext 标准 Material Request ordered_qty 和明细链接语义稳定；只有在验证完子分摊逻辑后，才启用同物料合并行。
6. 新字段均为可选，历史单据不回填不重算；新增页面只处理带生产缺料来源标记且状态有效的申请。
7. 采购订单维持草稿，由采购人员复核并提交；不增加未经确认的自动下单或审批。
8. 多单据创建采用逐物料保存点/明确事务策略，界面返回成功和失败明细，避免出现“只提示失败但已经创建部分申请”的歧义。

## 9. 风险与控制

### 风险一：重复申请

控制：基于来源单据、物料、仓库和活动状态计算剩余缺口；服务端加锁或数据库唯一键/幂等令牌保护。

### 风险二：跨申请合并后无法回溯

控制：在 PO Item 下保存多行来源分摊，禁止仅将来源申请号拼入备注字段。

### 风险三：部分下单导致超采购

控制：每次批量生成前锁定/重新计算可下单余量；来源台账以数量为准，不仅依赖页面传入值。

### 风险四：采购订单取消后申请仍显示已下单

控制：PO submit/cancel/trash 生命周期与分摊明细联动；已提交单据的取消仍由 ERPNext 标准逻辑更新 ordered_qty，再同步扩展状态。

### 风险五：价格过期或供应商变更

控制：下单前校验 Purchase Comparison 行、报价有效期和公式价格；与当前选中供应商不符时中止并要求重新比价。

### 风险六：一供应商不等于所有字段可合并

控制：汇总时同时校验 company、currency、price_list、payment_terms、warehouse/收货要求和预计交期；不兼容需求拆成多张 PO 并说明原因。

## 10. 分阶段实施建议

### 阶段一：缺料申请拆分与来源标记

- 保持弹窗交互；
- 新增服务端拆分创建接口；
- 每个物料产生独立采购申请；
- 记录来源工单、Stock Entry、仓库及销售订单；
- 增加幂等与结果反馈。

### 阶段二：供应商待下单汇总

- 采购工作台按供应商展示已比价、已确认的待下单数量；
- 支持跨多个 Material Request 选择物料和部分数量；
- 每供应商创建一张/必要时多张草稿 PO；
- 第一版 PO 行保持来源申请维度，不合并不同来源行。

### 阶段三：来源分摊、生命周期同步与可选同物料合并

- 上线 PO Item 来源分摊 Child DocType；
- 验证订单提交、部分收货、取消、删除草稿等数量生命周期；
- 再评估相同物料 PO Item 合并，同时确保每个来源申请的数量分摊准确。

推荐先完成阶段一和二的闭环，阶段三中的“同物料合并为单一 PO 行”可后置，避免首期改动范围过大。

## 11. 验收与预期效果

### 11.1 业务验收

- 一个 Stock Entry 有多个缺料物料时，可分别生成多张单物料采购申请；
- 每张申请可回到来源工单/库存移动单据，并看到正确缺料数量、仓库和需求日期；
- 重复点击或重新打开缺料流程不会重复申请同一未完成缺口；
- 每张申请可以继续使用既有 Purchase Comparison 单独比价、选择供应商；
- 多张申请选定同一供应商后，可在一个汇总操作中生成该供应商的草稿 PO；
- 其他供应商需求进入其他 PO，不混在不同供应商订单中；
- 部分数量下单后，剩余数量仍显示待下单，再次操作不会超过剩余量；
- PO 每行可追踪到一个或多个来源申请及工单；
- PO 提交、取消和草稿删除后，来源数量状态准确恢复/更新；
- 无报价、过期报价、币种或公司不兼容等情况会明确提示，不静默错误合并。

### 11.2 预期效果

实施后，生产缺料仍从现有弹窗发起，但申请将按物料拆分，采购人员能对每个物料独立比价、确定供应商；比价确认后，再通过按供应商汇总的采购工作台把不同申请合并成符合企业习惯的采购订单。系统既能减少“一料一申请”带来的多张 PO 操作负担，也能保留每张申请和每张工单的数量来源，支持部分下单、防重复采购和后续收货追踪。

全过程继续使用 ERPNext 标准采购申请、采购比价、采购订单和采购收货机制；采购订单仍为草稿待人工检查提交，不引入自动审批或自动正式下单。
