# 销售订单销售团队默认分摊与导入状态隐藏优化方案

## 1. 文档目的

本文用于沉淀销售订单两项优化的实施方案：

1. 新建销售订单时，默认将订单上方的“业务人员”带入原生“销售团队”子表；
2. 在销售订单表单界面隐藏“导入状态”字段。

本阶段只形成设计、文件清单、调用链路和验收标准，不修改业务代码、不修改数据库、不执行历史数据迁移。

## 2. 当前仓库边界与现状假设

当前仓库是 `frappe_docker` 部署仓库，未包含实际运行中的 ERPNext 自定义业务 App 源码。因此本文使用实施阶段的目标路径，实际落位前必须在 Bench 中确认自定义 App 名称、现有 hooks、事件处理器和字段配置。

截图及现有方案表明：

- 销售订单使用 ERPNext 原生 `sales_team` 子表；
- 订单已有“业务人员”字段，截图中显示为业务人员；
- `sales_team` 至少包含 `sales_person`、`allocated_percentage`、`commission_rate`、`contribution_amt` 等标准字段；
- “导入状态”是销售订单上的现有字段，主要用于导入过程或历史追溯；
- 当前需求允许多个业务员按比例分摊。

实施前需确认业务人员字段的真实字段名及类型：优先复用已存在的 Link 到 `Sales Person` 字段；若现有字段只是导入文本，不改变旧字段类型，另行新增 Link 字段。

## 3. 需求定义与业务规则

### 3.1 默认销售团队

新建销售订单或草稿订单选择/修改“业务人员”后：

1. 当原生销售团队为空时，自动新增一行；
2. `sales_person` 取订单“业务人员”；
3. `allocated_percentage` 默认 `100`；
4. 佣金率沿用 ERPNext 默认值或现有销售团队默认逻辑；
5. 不新建第二张销售团队表，不复制原生字段。

### 3.2 多人分摊

- 用户可以继续新增多个销售团队成员；
- 每行业务员、贡献比例、佣金率可按现有 ERPNext 权限和表单规则编辑；
- 多人分摊时由用户将 `allocated_percentage` 调整为各自比例；
- 最终提交继续使用 ERPNext 原生“销售团队贡献比例合计为 100%”校验；
- 本次不改写原生分摊算法、不新增替代比例字段。

建议的覆盖边界：

- 仅当 `sales_team` 为空时自动新增默认行；
- 已有一行或多行时不因普通刷新、客户变化或业务人员字段变化而无条件覆盖；
- 若业务员字段变化但销售团队已经有人工分摊，页面给出提示，由用户决定是否调整团队；
- 已提交订单继续遵循标准单据状态控制，不批量回写。

### 3.3 导入状态隐藏

- 仅隐藏销售订单表单中的“导入状态”显示；
- 不删除字段、不改变字段类型、不清理历史值；
- 不修改 Excel/API 导入参数和后台读取逻辑；
- 默认同时隐藏新建、草稿查看和已保存订单查看页面；
- 列表列、报表筛选和后台接口是否隐藏，需按现有使用情况单独确认。第一期建议只处理表单展示，保留后台可查询能力。

## 4. 推荐技术方案

采用“客户端即时体验 + 服务端保存兜底 + 原生销售团队兼容”的最小增量方案。

### 4.1 客户端

新增或扩展 Sales Order Client Script：

- 监听“业务人员”字段变化；
- 在 `sales_team` 为空时新增默认行并刷新子表；
- 业务人员为空时不创建空的销售团队行；
- 通过 `frm.set_df_property` 或等价的标准表单扩展点隐藏“导入状态”；
- 不覆盖现有客户、日期、年份/月和结算模式脚本。

客户端只负责即时显示，不能作为唯一数据保证。

### 4.2 服务端

在现有 Sales Order `before_validate` 或等价保存前扩展中增加独立函数：

1. 仅处理草稿/新建订单；
2. 判断订单业务人员是否有效；
3. 仅在 `sales_team` 没有明细时追加一行默认成员；
4. 不删除、不重排、不覆盖已有团队明细；
5. 交给 ERPNext 原生校验处理比例合计、业务员有效性和提交规则。

如果当前系统已有 `before_validate` 处理器，应在原函数后追加独立分支，或在事件列表中追加处理器，不能替换既有处理器。

### 4.3 字段显示配置

优先通过自定义 App 的字段元数据、Property Setter 或现有表单脚本隐藏“导入状态”。不建议修改 ERPNext 核心 JSON；不删除字段；不通过数据库直接改列。

## 5. 计划修改的代码与文件

以下是实施阶段的目标文件，当前不执行修改。实际路径以运行中的自定义 App 为准。

| 文件/位置 | 变更类型 | 主要职责 |
|---|---|---|
| `apps/<custom_app>/<custom_app>/doctype/sales_order/sales_order.py` 或现有 Sales Order 事件模块 | 增量修改 | 新增保存前默认销售团队行的独立函数；保留原有校验和接口 |
| `apps/<custom_app>/<custom_app>/public/js/sales_order_sales_team.js` | 建议新增 | 监听业务人员变化、空表自动填充、隐藏导入状态、提示人工分摊 |
| `apps/<custom_app>/<custom_app>/hooks.py` | 最小修改 | 追加 `doctype_js` 或文档事件，不覆盖既有脚本/事件 |
| `apps/<custom_app>/<custom_app>/config/excel_form_fields.json` 或字段同步模块 | 视现状修改 | 确认“导入状态”和业务人员字段的布局/显示属性；不改旧导入字段含义 |
| `apps/<custom_app>/<custom_app>/patches/vX_X/...` | 可选新增 | 只用于同步 Property Setter/字段元数据；默认不回写历史订单 |
| `apps/<custom_app>/<custom_app>/doctype/sales_order/test_sales_order_sales_team.py` | 新增 | 服务端默认、多人分摊保护和历史数据不变测试 |
| `apps/<custom_app>/<custom_app>/public/js/tests/sales_order_sales_team.test.js` | 视测试体系新增 | 客户端字段变化、隐藏状态和空团队填充测试 |

### 5.1 不修改的文件和接口

- 不修改 ERPNext 核心 Sales Order 控制器；
- 不修改原生 `sales_team` DocType 结构；
- 不修改现有 Excel 导入接口、CRM/API 下单接口的参数契约；
- 不修改送货单、销售发票、回款和业绩报表接口；
- 不批量改写已提交销售订单；
- 不删除或重命名“导入状态”数据库字段。

## 6. 调用链路

### 6.1 浏览器新建订单

```text
用户打开新建 Sales Order
  -> 表单加载脚本
  -> 隐藏“导入状态”字段
  -> 用户选择/修改业务人员
  -> 判断 sales_team 是否为空
  -> 为空：新增业务员行，比例 100%
  -> 不为空：保留现有多人分摊，不自动覆盖
```

### 6.2 保存、导入和接口入口

```text
浏览器保存 / Excel 导入 / CRM 或后台 API
  -> Sales Order 标准保存入口
  -> 现有 before_validate 逻辑
  -> 新增 ensure_default_sales_team 分支
  -> 仅空 sales_team 时追加默认行
  -> ERPNext 原生校验贡献比例、业务员和单据状态
  -> 保存/提交
```

### 6.3 后续业务链路

```text
Sales Order.sales_team
  -> Delivery Note / Sales Invoice 的标准映射
  -> 佣金、销售业绩和相关报表沿用原有读取逻辑
```

本次不新增下游同步接口；下游继续读取原生 `sales_team`，因此不会产生两套业务员归属。

## 7. 受影响模块

| 模块 | 影响范围 | 处理方式 |
|---|---|---|
| 销售订单表单 | 默认销售团队、字段展示 | 新增前端分支；隐藏导入状态 |
| 销售订单保存/提交 | 空团队默认行、比例校验 | 服务端增量兜底；沿用标准校验 |
| Excel/CRM/API 导入 | 可能缺少销售团队 | 不改入参，由保存前分支补齐 |
| 销售团队/佣金 | 多人比例分摊 | 使用原生子表和原生 100% 校验 |
| 送货单、发票、回款 | 读取订单销售团队 | 不改代码，保持既有映射 |
| 销售业绩报表 | 业务员归属 | 继续读取 `Sales Order.sales_team` |
| 权限 | 业务员编辑和提交权限 | 维持现有角色和单据状态规则 |
| 历史数据 | 已保存/已提交订单 | 不自动回写；先输出影响清单 |

## 8. 兼容性与小增量原则

1. 复用原生 `sales_team`，不新增重复销售团队表。
2. 新逻辑只在空表时生效，已有人工分摊数据优先保留。
3. 新增函数和新脚本采用独立命名，避免修改老函数内部复杂逻辑。
4. hooks 使用追加方式，保留既有 `doctype_js`、`doc_events` 和导入处理器。
5. “导入状态”只改变显示属性，数据库和接口契约保持不变。
6. 服务端是最终数据约束，客户端失败不应导致错误数据保存。
7. 不对历史订单做自动迁移；如需补齐，先预览数量、客户、业务员和变化内容，再单独审批。

## 9. 异常与边界处理

| 场景 | 预期处理 |
|---|---|
| 业务人员为空 | 不新增销售团队行；提交时是否强制要求业务员，沿用现有业务规则 |
| 业务人员已禁用/为组节点 | 服务端拒绝作为默认业务员，并返回可操作提示 |
| `sales_team` 已有一行 | 不覆盖比例、佣金率或业务员 |
| `sales_team` 已有多人 | 不修改任何行，由用户按原生规则维护比例 |
| 多人比例合计不为 100% | 使用 ERPNext 原生校验阻止提交 |
| 导入状态有历史值 | 字段隐藏但值保留，后台仍可查询 |
| 导入/API 未传业务人员 | 不改变接口报错契约；若订单团队为空则按现有可用默认来源处理，否则保留为空 |
| 已提交订单 | 不由本功能回写或重建销售团队 |
| 客户/业务人员变化导致团队可能不一致 | 仅提示，不自动清空人工分摊；后续可另行设计“重新按负责人生成”操作 |

## 10. 测试与验收标准

### 10.1 默认单人订单

1. 新建订单填写业务人员，销售团队自动出现一行该人员；
2. 贡献比例为 100%；
3. 保存、重新打开后数据保持；
4. 通过 Excel、CRM/API 或后台脚本创建且销售团队为空的订单，也能在服务端补齐。

### 10.2 多人分摊

1. 在默认行基础上新增第二名业务员；
2. 修改为 60%/40% 或其他合计 100% 的比例后可保存提交；
3. 已有多人分摊订单再次保存时，原人员和比例不被自动覆盖；
4. 比例合计不为 100% 时仍由原生校验阻止提交。

### 10.3 导入状态

1. 新建、草稿、已保存订单表单不显示“导入状态”；
2. 列表/报表/接口行为按确认范围保持不变；
3. 通过旧导入流程写入的值仍可保存、查询和审计；
4. 不产生字段缺失、接口参数错误或迁移失败。

### 10.4 下游兼容

1. 从订单生成送货单、销售发票的标准流程不受影响；
2. 佣金和销售业绩仍从原生 `sales_team` 读取；
3. 已提交历史订单的销售团队数据完全不变。

## 11. 实施顺序

1. 在测试站点确认真实字段名、现有 hooks 和 Sales Order 保存事件。
2. 先只部署“隐藏导入状态”的前端/元数据变更，确认表单和导入流程。
3. 增加服务端空团队默认分支和客户端即时填充。
4. 验证单人订单、多人分摊、Excel/API 三类入口。
5. 观察销售团队、佣金、送货、发票和业绩报表回归结果。
6. 输出历史草稿订单影响清单；未经确认不做批量补齐。

## 12. 预期效果

实施后，销售人员在新建订单时只需填写/确认订单业务人员，系统即可在原生销售团队中生成默认 100% 归属；需要联合销售时仍可使用同一张原生子表添加多人并按比例分摊。保存和提交继续受 ERPNext 标准比例校验保护，订单、送货、发票、佣金和业绩统计仍沿用同一数据源。

“导入状态”从销售订单表单界面移除视觉干扰，但字段、历史值、导入流程和后台查询能力保留。整体改造为新增分支和显示配置，老接口、老字段和历史订单不被破坏，便于后续升级和回滚。

## 13. 实施前需确认

1. 截图中的“业务人员”真实字段名是否为 Link 到 `Sales Person`；
2. 业务人员变化且已有多人销售团队时，是否只提示，还是需要提供“按业务人员重置销售团队”的明确按钮；
3. “导入状态”是否只隐藏表单，还是同时从列表列、报表筛选和权限可见字段中移除；
4. 业务人员为空的订单是否允许提交，还是仅允许保存草稿；
5. 现有自定义 App、hooks 和 Sales Order 事件模块的实际路径。
