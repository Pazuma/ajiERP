# 采购申请列表目的细分与标题简化优化方案

日期：2026-10-16  
状态：方案沉淀，尚未实施。本次只新增本文档，不修改业务代码、接口、数据或数据库结构。

## 1. 目标及范围

将采购申请列表标题中的“生产缺料”信息移到“目的”列展示。列表标题突出申请物料，“目的”列区分生产缺料、零星采购、常规采购。使用现有字段，小增量增加显示分支，不更改 Material Request 的底层类型、名称、编号或旧接口。

第一阶段仅调整标准 Material Request 列表的展示和配套用途筛选；表单、采购申请 PDF、导出、报表继续使用原始字段。不得把列表显示值写回原始目的或标题。

## 2. 已核实的系统现状

以下路径以 `development/frappe-bench/apps/client_akivision/client_akivision/` 为应用根目录。

| 位置 | 当前行为 |
| --- | --- |
| `public/js/material_request_list.js` | 扩展标准列表，保留原 onload，默认添加 `material_request_type = Purchase` 筛选；增加预选供应商读取和采购申请 PDF 操作；列表显示名称改为采购申请 |
| `utils/supplier_purchase_consolidation.py::ensure_schema` | 定义生产缺料标记、来源工单、来源库存移动、来源明细行、来源销售订单、缺料来源明细表 |
| 同文件 `create_purchase_requests_for_shortages` | 按缺料行创建申请，设置目的 Purchase、缺料标记 1、来源信息；标题生成“生产缺料采购申请-{物料名称}”，采购场景设置为常规采购 |
| `utils/layered_manufacturing.py::_allocate_shortage` | 分层/直接组件缺料安排中，外购分支创建 Material Request；同样写入目的 Purchase、缺料标记、来源工单和缺料明细，但未在该分支显式设置上述标题前缀 |
| `utils/misc_purchase.py::ensure_schema` | 定义采购场景，值为常规采购、零星采购；比价字段只对普通采购显示 |
| `utils/supplier_purchase_consolidation.py` 后续查询 | 供应商汇总待下单等逻辑使用 `custom_production_shortage_request = 1` 判断，不依赖标题 |

框架当前支持列表 `settings.formatters[fieldname](value, df, doc)`；标题字段也有独立 formatter 调用入口。因此可在应用列表脚本添加展示分支，无需修改 Frappe/ERPNext 核心代码。

注意：截图中标题没有“生产缺料”的 BOM 申请也可能属于生产缺料，不能仅从标题判断。以上是代码链路核查结果，尚未完成全量历史数据审计。

## 3. 数据来源和判断规则

### 3.1 分类权威数据

| 字段 | 用途 | 是否修改 |
| --- | --- | --- |
| `material_request_type` | 系统原始目的，例如 Purchase、Material Transfer | 不修改 |
| `custom_production_shortage_request` | 是否生产缺料采购申请，系统创建链路写入 | 不修改 |
| `custom_purchase_scene` | 常规采购/零星采购 | 不修改 |
| `title` | 原始申请标题 | 第一阶段不修改 |
| `custom_shortage_source_work_order` | 来源生产工单，追溯依据 | 不修改 |
| `custom_layered_work_order` | 分层补料来源工单，兼容追溯依据 | 不修改 |
| `custom_shortage_source_stock_entry`、`custom_shortage_source_item_row` | 来源领料单及行 | 不修改 |
| `custom_shortage_source_allocations` | 缺料来源明细，记录来源、物料、仓库、数量 | 不修改 |

先判断原始目的，只有 Purchase 才进入细分类分支：

```text
非 Purchase ─────────────────────────────→ 显示原始目的的译文
Purchase → 缺料标记为 1 ─────────────────→ 生产缺料
         → 非缺料且采购场景为零星采购 ───→ 零星采购
         → 非缺料且采购场景为常规或空 ───→ 常规采购
```

缺料标记优先于采购场景，因为正常缺料申请本身会同时记录“常规采购”。缺料标记与零星采购场景同时存在属于异常组合：显示生产缺料，同时列入历史核查清单，不在展示时自动纠正数据。

采购场景遇到未来新增的非空未知值时，保守显示“采购”，不擅自归为常规采购；后续扩展需同步显示和筛选规则。字段缺失、读取受限时不得通过标题猜测缺料用途，应退回原始目的。

### 3.2 展示分类与来源追溯的区别

缺料标记负责分类；来源工单、领料单和缺料明细负责说明“为什么采购、给哪张工单采购、采购多少”。不从来源表或标题反向推导并回写分类。

标题简化条件必须同时满足：原始目的为 Purchase、缺料标记为 1、原始标题以已知系统前缀“生产缺料采购申请-”开头。仅将该前缀显示为“采购申请-”，后缀原样保留。不得全局删除标题内任意位置的“生产缺料”，不得批量改写历史标题。

已有自定义标题（例如采购申请BOM_test）、非采购标题、无已知前缀的标题原样显示。搜索标题仍搜索原始数据；简化后的标准标题保留“采购申请”和物料后缀，建议用户按物料或单号搜索。原始完整标题可通过列表标题的悬停提示或进入表单查看；若框架默认提示不保留原值，仅在本列表补充提示，不修改全局控件。

## 5. 拟修改文件与代码设计

### 5.1 必改：`public/js/material_request_list.js`

1. 保留现有设置、原 onload、默认 Purchase 筛选、预选供应商和 PDF 操作。
2. 在现有 `add_fields` 上合并并去重，补充 `material_request_type`、`custom_production_shortage_request`、`custom_purchase_scene`、`title`。按元数据可用性处理自定义字段，避免旧站点字段未安装导致列表查询报错。不得每行再发接口查询或读取整个缺料子表。
3. 合并原 `formatters`，仅覆盖本次涉及的字段，并在非适用分支调用原 formatter 或沿用标准值。
4. 新增纯展示辅助函数，集中分类规则；展示标题和目的不得改写传入 doc。
5. 增加“申请用途”筛选控件；初始化和刷新不得重复生成控件或事件。

拟新增代码结构（示意，实施时按实际 Frappe 生命周期适配）：

```javascript
function get_request_display_purpose(doc) {
    if (doc.material_request_type !== 'Purchase') return null;
    if (Number(doc.custom_production_shortage_request) === 1) return '生产缺料';
    if (doc.custom_purchase_scene === '零星采购') return '零星采购';
    if (!doc.custom_purchase_scene || doc.custom_purchase_scene === '常规采购') return '常规采购';
    return null; // 调用原格式化逻辑显示“采购”
}

function get_request_display_title(value, doc) {
    const prefix = '生产缺料采购申请-';
    if (doc.material_request_type === 'Purchase'
        && Number(doc.custom_production_shortage_request) === 1
        && typeof value === 'string' && value.startsWith(prefix)) {
        return '采购申请-' + value.slice(prefix.length);
    }
    return value;
}
```

目的 formatter 输出安全转义后的标签；标题 formatter 根据框架标题链接的插入方式进行转义，避免重复转义或原始 HTML 注入，保留链接、复选框、选中行及打开表单行为。原始值为空时保留框架编号兜底。

## 6. 筛选、搜索、排序和导出配套

列表“目的”是派生展示，原系统目的筛选仍筛原始类型。顶部原“采购”筛选保留，不伪造一个不存在的 `material_request_type = 生产缺料` 条件。

新增“申请用途”控件，转换成现有字段条件，交给原列表服务端查询，不能仅过滤当前页：

| 用途选择 | 条件 |
| --- | --- |
| 全部用途 | 移除该控件自己添加的用途条件，保留其他筛选 |
| 生产缺料 | Purchase 且缺料标记 = 1 |
| 零星采购 | Purchase 且缺料标记 = 0 且采购场景 = 零星采购 |
| 常规采购 | Purchase 且缺料标记 = 0 且采购场景为“常规采购”或空 |

实施前核对 Check/Select 字段的历史 NULL、空字符串及默认值在现有查询操作符中的实际行为。“常规或空”优先使用现有查询支持的集合条件，必须实测包含空值；若不能表达，不得退化成“只匹配常规采购”却继续声称覆盖历史空值。可改为下拉单独提供“场景未设置”筛选分支，并在控件标注，仍不改老接口。

用途控件只管理自己添加的条件，不清空用户筛选；切换用途先移除上一组自有条件再添加新组，防止互斥条件累积。高级筛选与用途冲突时如实显示零结果，不静默删除用户条件。与保存筛选、路由恢复保持一致；不能恢复时回显“自定义条件”，不能误显示“全部用途”。

目的标签第一阶段只展示，不沿用原 Purchase 标签的点击筛选行为，避免点击“生产缺料”却筛到全部采购。用途筛选统一走控件。

标题搜索、排序、导出继续使用原始字段；目的排序仍是原目的值，不声称按派生用途排序。导出/PDF不自动套用列表 formatter；若后续要求同口径，另行新增用途导出列和打印分支，不替换原目的字段。

## 7. 调用链路及实际业务流

```text
生产工单开始 → 创建生产领料单 → 库存校验发现缺料 → 弹窗确认采购
    ├─ stock_entry_shortage_dialog.js
    │    → supplier_purchase_consolidation.create_purchase_requests_for_shortages
    └─ layered_shortage_dialog.js
         → layered_manufacturing.allocate_shortage / allocate_direct_component_shortage
         → _allocate_shortage 中 purchase 分支
                 ↓
Material Request：Purchase + 缺料标记1 + 来源工单/明细
                 ↓
标准列表查询（新增读取已有分类字段，无新接口）
                 ↓
material_request_list.js：目的显示“生产缺料”，标题仅显示时简化
                 ↓
打开原申请 → 核对物料、数量、预选供应商 → 按原流程提交
                 ↓
原比价/供应商汇总下单 → 采购订单 → 原质检和收货流程
```

普通采购：手工创建采购申请 → 选择常规/零星场景 → 保留原保存及提交逻辑 → 列表按场景显示。半成品选择自产分支时不应因本次变更生成采购申请或改变生产工单。

## 9. 历史数据核查

实施前只读统计以下组合，并给出单号、原始标题、目的、场景、缺料标记和来源信息：

1. 已有缺料标记且来源完整：直接适用新展示，无需回填。
2. 标题含缺料但标记为0/空：待核实，不按标题自动归类。
3. 有来源工单或缺料明细但无标记：待核实来源生成方式，不能仅因有关联工单就认定缺料采购。
4. 标记缺料但场景零星采购，或目的非Purchase：异常组合清单，单独核实。
5. 非缺料采购场景为空：按约定显示常规采购，但不回写场景。

第一阶段不提供自动补齐历史标记功能。如确需清洗，应形成明确单号清单、旧值备份、修正规则和回滚脚本，再单独执行，不夹带在列表加载中。

## 10. 验收与回滚

验收需覆盖：

- 两条缺料链路产生的申请都显示生产缺料，含无固定标题前缀的单据。
- 缺料标记优先于常规场景；零星、常规、非采购及未知场景降级正确。
- 仅精确系统前缀简化；自定义标题和历史原始值不变，标题链接仍可打开正确单据。
- 用途筛选作用于全量分页数据，切换不累加条件，清除不删除其他筛选；空场景和保存筛选恢复经过实测。
- 列表刷新、切换模块、返回列表不重复创建控件；目的标签不触发错误筛选。
- 有限权限账号无额外读取权限，分类所需字段缺失时安全降级；无每行额外请求。
- 原保存、提交、比价及汇总下单入口可用；列表改显示不改变表单、PDF、导出原值。

发布仅需更新列表资源并清除站点缓存，无数据库迁移要求。回滚本次列表增量并清除缓存即可恢复，不需还原任何业务数据。不得整体覆盖已有列表文件中的其他功能或用户未提交的修改。
