# 销售订单财务核算权限、人工维护与自动取数增量方案

编制日期：2026-10-23。状态：讨论方案，尚未实施。本次仅新增本文档，不修改业务代码、权限或数据库。

## 1. 业务目标与建议结论

销售订单的“生产成本与毛利”“税费与记账预览”属于财务核算信息，业务人员不能查看或填写。前期缺少生产、项目等历史数据，由财务在开票后手工维护并统计；后期具备项目、生产工单和库存等关联数据后，可以自动获取，财务仍保留核对、调整和确认权限。

建议新增独立的“销售订单财务核算”记录，保存人工输入、自动建议值和财务确认版本。销售订单是操作入口和汇总展示入口，不直接放开现有只读成本字段。旧自动归集继续服务原有业务，新核算分支独立保存，避免刷新成本覆盖人工数据。

首期只建设权限隔离、人工核算、确认版本和基础统计。项目自动成本分摊等放到后续增量，不在首期重构生产和财务主链路。

### 已明确与待确认边界

- 已明确：业务人员不能看到上述两个区域；财务可人工填写、修改；后续支持自动取数；本轮只出方案。
- 首期建议：“开票后”以关联的已提交 `Sales Invoice` 为条件。实际增值税发票开具登记不是同一事件，若业务指实际税票，应在实施前替换条件，不能混用。
- 首期建议：财务权限采用明确授权角色，业务角色本身不获得核算权限；同时拥有业务与财务授权的人员按财务授权处理。若要求双角色也禁止，需另定拒绝优先规则。
- 本方案隔离财务核算内容，不擅自隐藏业务报价所必需的原生含税售价、订单总额与原生税费配置。原生税额也要保密时，须单独评估报价、打印和接口影响。
- 财务手工核算是管理核算数据，不直接改写原生销售发票、订单税额、库存估值或正式凭证。

## 3. 权限设计

建议新增 `Sales Order Finance Reader` 与 `Sales Order Finance Editor` 两个专用角色；由管理员明确分配给财务人员。系统管理员作为管理例外保留访问能力。不能仅凭拥有订单读写权限就允许查看核算。

| 人员/授权 | 两个财务区域 | 人工保存 | 确认及修改已确认版本 | 财务统计/内部核算导出 |
|---|---|---|---|---|
| 仅业务角色 | 不显示、不返回敏感数据 | 拒绝 | 拒绝 | 拒绝 |
| 仅采购/仓库/生产角色 | 默认不授予订单财务权限 | 拒绝 | 拒绝 | 拒绝 |
| 财务查看授权 | 可查看权限范围内订单 | 拒绝 | 拒绝 | 可读取权限范围内数据 |
| 财务维护授权 | 可查看 | 开票后允许 | 允许，必须留痕 | 允许 |
| 系统管理员 | 管理访问 | 同样校验开票条件和数据完整性 | 留痕 | 允许 |

后端统一执行：角色授权 → 订单记录权限及公司范围 → 发票归属和状态 → 操作权限 → 数据校验。专用角色不能额外授予所有销售订单的访问权。

权限落点包括：字段 permlevel、DocType 权限、核算 API、现有预览/刷新 API、老成本报表、内部导出，以及标准列表、REST、打印、数据导出等出口。自定义 SQL/模板不能假设会自动应用字段权限。关联发票、凭证链接须校验对应记录读取权限。

使用销售订单独立的财务字段权限层级，实施前检查站点层级占用再确定数值；不要直接改全局 `COST_ROLES`。订单行上的成本字段同时纳入隔离；损耗率、归集开关等参与生产的输入仍由既有业务机制读取，避免权限迁移阻断工单创建。

## 4. 新增数据模型

建议在 `china_finance` 新增三个 DocType，实际文件目录以该应用模块规范为准。

### 4.1 主表：Sales Order Finance Accounting

- 关联：公司、销售订单、对应销售发票、核算日期、统计期间。
- 版本：版本号、状态、前一版本、当前有效版本标识、确认人/时间、修改原因。
- 口径：来源模式（人工/自动建议后调整）、单据币种、本位币、发票汇率快照、数据完整性状态。
- 汇总：本次核算未税销售额、生产成本、匹配销售成本、税额、其他费用、毛利、毛利率。
- 核算金额与正式发票金额的差异及说明；正式记账状态从来源单据读取，不能人工勾选为“已记账”。

以“订单＋发票”为核算单元，一张发票涉及多个订单时按订单拆记录，禁止重复取整张发票金额。每个核算单元仅一个当前有效确认版本，服务端事务与唯一性约束共同保证。

### 4.2 子表：Sales Order Finance Accounting Item

关联 `Sales Order Item.name` 和 `Sales Invoice Item.name`，记录产品、核算数量、发票行净额、项目/工单来源、成本分项、自动建议金额、人工调整金额、最终金额、来源完整性和调整原因。

不能只用产品编码作关联键，同产品在订单中可能出现多行，也可能对应不同工单。前期允许无项目/工单；后续关联来源时不修改已有确认版本。

### 4.3 子表：Sales Order Finance Accounting Tax

记录税费项目、税率、计税基数、税额、费用类型、建议科目、人工核算金额及差异原因。预计分录由这些记录推导，不开放随意修改借贷平衡结果。

新记录保存来源单据关键金额与行标识快照，启用修改追踪。确认后不可原地编辑或删除；调整生成新草稿版本，重新确认后原版本标记被替代。保存、确认、替代须校验版本并发，不使用静默覆盖。

## 5. 人工录入、计算和统计规则

1. 财务开票后选择订单对应的有效发票行，填写成本、费用和核算税费；可保存不完整草稿，完整且勾稽通过后才可确认。
2. 建议首期要求订单与发票均已提交且未取消。历史订单没有系统发票时显示“待关联发票”，不为绕过条件自动创建发票。历史补录例外若需要，另行定义授权和凭据。
3. 材料、辅料、人工、制造费用、废料回收支持手填；损耗必须标注是否已包含在材料成本中，避免重复累加。默认正常损耗为成本分析拆分，不再额外叠加。异常损耗是否计入销售成本或期间费用由财务选择口径。
4. 生产总成本与本次开票匹配销售成本分开维护。前者描述生产投入，后者与本次开票收入匹配；不能将整单生产成本在每次部分开票中重复扣除。
5. 管理核算毛利 = 本次核算未税收入 − 本次匹配销售成本；毛利率 = 毛利 / 未税收入 × 100%。税额和其他费用独立统计，扣除费用后的管理利润另列，不能混叫毛利。不替换现有已发货毛利公式。
6. 空值表示缺失，明确录入 0 才是零成本/免税；缺失成本不显示虚假毛利，不参与已确认利润合计。收入为零时毛利率为空并提示原因。
7. 人工金额原则上沿用发票行净额和已确认税额；需要调整管理核算金额时记录差异原因，页面同时展示正式金额与核算金额。不能用手工税额覆盖原始税费或正式账簿。
8. 按发票行及原订单行检查累计核算数量/金额，禁止同一范围重复确认。数量单位换算、多币种及舍入按来源精度处理；金额、税额分摊尾差明确落到指定行。
9. 财务统计默认只取当前有效、来源未失效的已确认版本；分别显示待填写、草稿、已确认和待复核数量。统计日期采用核算日期，另保留发票日期，不把订单日期报表冒充期间利润表。
10. 退货/红字发票采用独立反向核算记录并关联原核算范围，不能简单以负成本绕过校验。来源取消、修改或新增冲销导致口径变化时，保留历史快照，当前记录进入待复核且不再计入有效确认汇总。

示例：本次发票未税收入 10,000 元、税额 1,300 元，财务确认匹配销售成本 6,000 元，则管理毛利 4,000 元、毛利率 40%；发票含税额仍是 11,300 元。成本未填时毛利显示“待完善”，不能显示 10,000 元。

## 6. 自动取数与人工数据保护

自动取数仅返回“建议值＋来源＋完整性”，不自动确认、不修改人工确认版本。建议值为空不能当作零，也不能用最新产品通用成本替代历史订单实际成本。

- 已有来源：订单 → Work Order → 已提交 Manufacture Stock Entry；订单 → Delivery Note → Stock Ledger Entry。
- 后续来源：订单/产品行 → Project、工单及其他实际费用。项目与订单的分摊关系需单独明确，首期不实现模糊产品匹配或整项目费用重复归集。
- 生产工单只是关联入口，实际库存成本优先取已过账流水；分层工单需避免父子成本重复累计。
- 新增只读建议适配器，首期只实现已明确来源。必要时局部提取旧归集的纯查询函数，但不能调用带回写的 `refresh_sales_order_cost()` 来做预览。
- “获取自动建议” → 显示与当前人工金额差异 → 财务选择采用行 → 必要时填写调整原因 → 保存/确认新版本。禁止后台定时刷新替换手填值。
- 旧 `custom_*cost*` 累计字段仍由旧链路维护，新财务结果不回写这些字段。页面和报表明确标注“原归集口径”与“财务核算口径”。

## 8. 调用链路

### 8.1 页面与人工维护

```text
Sales Order.refresh
  → 非敏感权限能力判断
  ├─ 业务人员：隐藏财务字段/区域/按钮，不调用财务数据 API
  └─ 财务授权：读取订单权限范围内的核算摘要和原预览
       → 尚未开票：显示待开票；不提供写入
       → 已开票：选择订单对应发票行 → 财务填写 → save_accounting_draft
            → 后端复核角色/订单/发票归属/数量/币种/版本
            → 服务端计算金额 → 保存独立核算草稿
            → confirm_accounting → 校验完整性及勾稽 → 确认有效版本
            → 销售订单财务区域及新报表只读汇总
```

### 8.2 后期自动来源

```text
财务点击获取自动建议
  → get_cost_suggestions（只读）
  → 按订单行/工单/库存来源获取实际数据和完整性
  → 展示建议值、人工值和差异
  → 财务选择采用及调整 → 保存草稿/新版本 → 确认

现有 Stock Entry/Delivery Note 提交或取消
  → 原异步归集 → 旧订单累计字段（保持原链路）
  → 新财务确认数据不被覆盖
```

### 8.3 来源失效与统计

```text
Sales Invoice 取消/相关来源口径变化
  → 新增轻量事件标记对应核算记录待复核（提交后执行，支持重复事件）
  → 保留旧快照和审计记录，不删除历史核算
  → 新统计排除失效版本并显示待复核数

核算汇总报表/导出
  → 财务角色 + 订单/公司记录范围
  → 当前有效确认版本 + 核算期间
  → 数量、未税收入、匹配成本、税费、毛利汇总
```

读摘要和确认时再核验来源有效性，避免只依赖异步失效事件而短暂展示过期确认结果。

## 9. 受影响模块与兼容约束

| 模块 | 影响 |
|---|---|
| 销售订单表单 | 两个财务区域权限收紧；财务新增维护入口；业务报价、保存、提交维持既有行为 |
| 财务核算及统计 | 新增独立记录、版本、期间统计和核算导出；不等同于正式利润表 |
| 老成本报表及内部导出 | 权限收紧，旧数据含义保持；财务新结果通过独立分支提供 |
| 项目、工单、生产入库、送货、库存流水 | 首期作为既有自动归集来源；后续只读接入建议分支，不改变估值和过账 |
| 销售发票、中国会计凭证、销售结算 | 作为开票条件、关联状态和正式事实来源；不新增自动开票或自动记账 |
| Item/Bin 权限及采购、仓库页面 | 原权限策略不变，验证不存在全局角色收紧副作用 |
| 原接口和外部集成 | 不改现有方法名、参数、成功返回结构；敏感入口新增拒绝无权访问；外部下单无需新增财务参数 |

标准导入或 REST 写新核算 DocType 也必须走控制器校验，不能只保护白名单保存方法。若发现旧通用打印/导出绕过字段权限，只修复涉及销售订单敏感字段的明确出口，先列明再纳入实施。

## 10. 小增量实施顺序与回退

1. 权限增量：新增角色和局部字段隔离，堵住预览、报表及导出入口；核验 schema 幂等。此步不改变成本数据。
2. 人工核算增量：新增主子表、新 API 和财务录入入口；完成开票条件、版本及确认校验。
3. 汇总增量：新增财务统计和导出，仅统计有效确认版本，页面明确两套口径。
4. 自动建议增量：优先复用可靠库存/工单只读来源，再逐项扩展项目费用分摊。

各阶段分别验收后发布；不把全部后期来源一次接入。新分支可通过新增功能开关停用，但权限保护仍保留。回退时隐藏新录入入口并保留核算表及历史记录，不删除数据、不撤销正式单据、不把新核算金额批量覆盖回旧字段。

历史订单不自动标记为已确认，也不把现有零值当成人工零成本；旧归集数据仅可作为待核对建议。迁移先在副本核对角色、字段层级、事件注册和历史订单展示，再在目标站点执行。

## 11. 预期效果与验收

| 场景 | 预期效果 |
|---|---|
| 业务人员打开历史/新订单 | 页面不出现两个财务区域及成本按钮；网络响应、列表、打印与导出不泄漏受限核算数据 |
| 业务人员直接请求预览、刷新、核算或成本报表 | 服务端拒绝；不能靠改前端或接口参数绕过 |
| 财务打开尚未开票订单 | 可见待开票状态，不能保存核算；原订单业务操作不受阻 |
| 财务维护无项目/工单的已开票订单 | 可以手填成本、税费，保存草稿并确认，产生可统计结果 |
| 成本未填写与明确录入零成本 | 前者待完善、无毛利；后者在财务确认和原因规则通过后可按零统计 |
| 同订单分两次开票/同发票关联多订单 | 按对应行范围核算，不重复收入和成本，不重复取整张发票税额 |
| 手填后库存凭证触发旧成本刷新 | 旧归集照常更新，新人工及已确认版本不变 |
| 后期绑定工单/项目 | 可看到自动建议及来源，经财务采用后形成新版本，原确认记录可追溯 |
| 已确认后修改/多人同时确认 | 新建修订版本并记录原因；并发冲突明确提示，仅一个当前有效确认版本 |
| 发票取消、退货或红冲 | 原记录保留且待复核，统计不继续当作有效收入；反向核算可追溯 |
| 财务打开新统计 | 可按公司、客户、订单、发票和核算期间查询；分别列出收入、匹配成本、税费、毛利和待完善数量 |
| 核算金额与正式发票不一致 | 显示差异和原因，不改变原发票或凭证，不冒充正式记账结果 |
| 重复 migrate/单独 schema 初始化 | 财务字段权限不被重置；Item/Bin 和生产模块原权限不发生意外变化 |

验收至少覆盖纯业务、纯财务查看、财务维护、仅生产、双角色和跨公司用户；同时验证标准 REST、通用数据导出、客户版与内部版输出，以及原订单提交、备货、生产、出库、结算和记账回归。

## 12. 实施前需要确认的业务选择

1. 开票条件采用系统销售发票提交，还是实际增值税发票开具登记。
2. 谁获得财务查看/维护角色；双角色用户是否按明确财务授权处理。
3. 前期成本录入细到产品行还是另需订单总额快速分摊；首期建议产品行，避免后续无法匹配部分开票。
4. 异常损耗、其他费用的管理核算归类，以及红冲历史数据的处理口径。

这些选择在实施前确定；本文已给出默认建议，尚未修改任何业务行为。
