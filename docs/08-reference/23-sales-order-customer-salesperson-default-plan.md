# 销售订单按客户自动带出业务员方案

## 背景与目标

业务上，客户通常由唯一业务员负责。新建销售订单并选择客户后，系统应自动在订单的原生“销售团队”中带出该业务员，作为订单、交付、回款和业绩统计的统一归属。

本方案只描述实现边界和规则，确认后再实施代码与数据修复。

## 现有基础

系统已有以下字段和数据结构：

| 位置 | 字段/表 | 用途 |
|---|---|---|
| Customer | `custom_responsible_sales_person` | 客户负责业务员，Link 到原生 `Sales Person` |
| Customer | `custom_responsible_business_name` | Excel 导入保留的业务员原始文本，不是可靠关联 |
| Customer | `sales_team` | ERPNext 原生客户销售团队，可保留历史配置 |
| Sales Order | `sales_team` | ERPNext 原生订单销售团队，含业务员、贡献比例和佣金率 |

销售订单的业绩、列表及经营看板均应读取订单的原生 `sales_team`，不新增重复的“订单业务员”字段。

## 主数据规则

### 权威来源

客户的 `custom_responsible_sales_person` 作为一对一负责关系的权威来源。

该字段必须指向已启用的叶子节点 `Sales Person`。`custom_responsible_business_name` 仅保留导入原文，不参与下单自动带出，避免名称相同或人员未建档时写入无效业务员。

### 与客户销售团队的关系

为兼容已有数据，读取优先级如下：

1. 客户 `custom_responsible_sales_person`；
2. 若该字段为空，且客户原生 `sales_team` 恰好有一条有效业务员记录，则使用该记录；
3. 两者都没有时，视为“客户未配置负责业务员”；
4. 原生客户销售团队有多条记录时，不自动猜测，要求先维护客户负责业务员。

后续客户维护以 `custom_responsible_sales_person` 为准。实施时应提供一次数据核查，找出“自定义负责业务员”与客户销售团队首条业务员不一致的客户，由业务确认后统一。

## 销售订单自动带出规则

### 触发时机

1. 用户在新建或草稿销售订单中选择客户；
2. 用户将草稿订单的客户从 A 改为 B；
3. 通过 Excel、接口、CRM 或服务器脚本新建或更新草稿订单时，在保存前由服务端再次执行。

客户端用于即时展示，服务端用于保证所有入口的数据一致，不能只做前端脚本。

### 写入结果

当客户能解析出唯一业务员时，系统将 Sales Order 的 `sales_team` 重置为一行：

| 字段 | 值 |
|---|---|
| `sales_person` | 客户负责业务员 |
| `allocated_percentage` | `100` |
| `commission_rate` | 维持 ERPNext 默认值或客户销售团队对应值 |

写入的是订单快照。之后即使客户更换负责业务员，已保存订单的业务员不回写，确保历史业绩归属稳定。

### 客户变更与未配置场景

- 草稿订单改客户时，旧客户带出的销售团队必须被替换，不能保留旧业务员。
- 新客户未配置负责业务员时，系统清空此前自动带出的销售团队，并显示明确提示：`客户未维护负责业务员，请先在客户资料中维护后再下单。`
- 默认方案为阻止订单提交，避免无业务员归属的订单进入后续交付、回款和业绩统计；草稿可以暂存。
- 已提交销售订单不得通过普通编辑更改客户或销售团队，继续遵循 ERPNext 的单据状态控制。

## 人工调整边界

本次目标是一对一自动归属，不开放普通下单过程的多人分摊。

- 客户选择后，销售团队自动生成且默认只读展示；
- 如确有临时转单、联合销售或业绩分摊，应由销售主管在草稿阶段使用单独的“覆盖业务员”操作；该操作需要填写原因并记录操作日志；
- 覆盖后，只要客户不再变更，服务端不得在普通保存时覆盖人工调整；
- 一旦客户变更，原人工覆盖作废，系统按新客户重新计算并要求再次确认。

本期如不需要上述例外操作，可先禁止直接编辑销售团队，后续再按审批需求扩展。

## 实施设计

### 服务端

在 `client_akivision` 的 Sales Order `before_validate` 事件增加同步函数，并与现有年份/月自动计算逻辑并列执行。

函数职责：

1. 仅处理草稿订单；
2. 判断订单是否新建、客户是否变化或销售团队为空；
3. 读取客户负责业务员，必要时按兼容优先级读取客户原生销售团队；
4. 校验业务员存在、启用且不是组节点；
5. 按规则写入一条 `sales_team`；
6. 无有效映射时清理自动带出的旧行，并在提交校验时返回可操作错误。

需要保存一个隐藏标记或通过订单版本差异识别“自动带出”和“人工覆盖”，防止普通保存覆盖已批准的人工调整。建议新增两个只读审计字段：

- `custom_sales_person_source`：`Customer Default`、`Manual Override`、`None`；
- `custom_sales_person_override_reason`：人工覆盖原因。

这两个字段只用于审计，不替代 `sales_team`。

### 客户端

新增 Sales Order Client Script：监听 `customer` 字段变化，调用受权限保护的服务端接口获取默认业务员，并立即更新 `sales_team` 与页面提示。

客户端返回的数据只用于页面体验；最终保存结果仍以服务端 `before_validate` 为准。切换客户时先清除旧自动带出行，再应用新客户结果，避免短暂显示错误归属。

### 客户资料校验

在 Customer 保存时增加校验：填写 `custom_responsible_sales_person` 时必须为启用的叶子业务员。客户导入完成后应输出以下异常清单：

- 未维护 `custom_responsible_sales_person` 的启用客户；
- 负责人为禁用或组节点的客户；
- 客户负责人和客户原生销售团队不一致的客户；
- 仅存在 `custom_responsible_business_name` 文本、但没有关联业务员的客户。

## 数据迁移

不批量修改已提交销售订单，历史订单保留原有销售团队作为业绩快照。

实施前仅对客户主数据进行预检和补齐：

1. 从客户原生 `sales_team` 唯一记录补写 `custom_responsible_sales_person`；
2. 仅有原始名称文本时，生成待人工确认清单，不能按名称模糊匹配后自动写入；
3. 输出总数、成功补齐数、无映射数和冲突数；
4. 业务确认后执行写入，并保留导出结果。

现有草稿销售订单可在确认后执行一次预览修复：只列出将变化的订单、客户、原业务员和新业务员；经确认后才写入。

## 验收场景

1. 客户 A 配置业务员甲，新建订单选择 A 后销售团队仅有甲，分摊为 100%。
2. 草稿订单从客户 A 切换为客户 B，甲被移除并替换为 B 的负责人乙。
3. 客户未配置负责人时，订单不能提交，并能定位到需要维护的客户资料。
4. 从 Excel、CRM 接口或后台脚本创建订单时，未经过浏览器也能写入正确业务员。
5. 客户负责人日后改为丙，已提交订单仍保留甲；新建订单带出丙。
6. 已批准的人工覆盖订单在客户不变时保存，不被自动逻辑覆盖；变更客户后重新按新客户计算。
7. 订单、送货、回款及业务员业绩报表对同一订单显示一致的业务员归属。

## 风险与前置确认

- 客户一对一负责关系必须先完成维护，否则严格阻止提交会暴露历史主数据缺口。
- 业务员和员工/系统用户不是同一对象；本方案使用 `Sales Person`，不按姓名直接匹配 Employee 或 User。
- 是否需要“人工覆盖业务员”和多人分摊审批，是实施前唯一需要业务确认的策略项。默认按一对一且无人工覆盖实现，范围最小、统计口径最稳定。
