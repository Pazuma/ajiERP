# 正式客户对账单 PDF 生成方案

状态：仅方案，暂未修改业务代码或站点数据。

生产工单领料 PDF 属于系统通用导出方案的独立正式模板，详见 `30-system-wide-document-export-plan.md` 第 12 节；它与本客户对账单模板分别实现和维护，不共用业务取数逻辑。

## 1. 目标与边界

销售人员在销售订单或送货单列表选定需要核对的数据后，系统直接生成排版完整、可打印盖章并发送给客户的正式 PDF 对账单。系统自动填入客户、对账期间、订单、产品、数量、含税单价、含税金额、送货单号、付款和未付款金额，避免人工将 Excel 再制作成对账单。

本功能作为新增 PDF 分支，不替换已有“导出已选对账明细”Excel，不修改销售订单、送货单、销售发票、付款凭证或现有结算接口。首期只读生成 PDF，不自动创建销售结算单、发票、收款或会计凭证。

## 2. 预期效果

1. 销售人员在销售订单或送货单列表勾选记录，点击“生成客户对账单 PDF”。
2. 系统校验所选记录属于同一公司、同一客户和同一币种；不符合时明确提示拆分生成。
3. 系统按固定版式直接下载 A4 横向 PDF，销售人员无需再次编辑即可打印盖章或发送客户。
4. PDF 顶部显示“阿基视觉科技（东莞）有限公司”和右上角 `AKI VISION / Make it Easy` Logo。
5. PDF 自动显示对账期、客户名称、总金额、已付款和未付款，并逐行列出业务明细。
6. 明细超过一页时自动分页，后续页重复公司抬头、Logo、对账标题和明细表头。
7. 页尾显示确认文案、收款账户信息，以及付款方签字、盖章、日期区域。
8. 生成过程不修改任何业务单据，生成前后库存、应收、付款和单据 `modified` 均不变化。

## 3. 入口与交互

### 3.1 已选记录生成

在 `Sales Order` 和 `Delivery Note` 列表“操作”菜单新增 `生成客户对账单 PDF`。用户至少勾选一条记录后可执行；确认弹窗显示所选单据数、客户和对账期间。

### 3.2 筛选结果生成

保留“导出筛选结果”的交互思想，新增 `按筛选结果生成客户对账单 PDF`。服务端重新执行当前客户、日期、状态等白名单筛选，不受当前列表分页条数限制。为防止误生成跨客户文件，筛选结果必须只包含一个客户；否则提示先增加客户筛选。

### 3.3 生成前确认

确认弹窗展示：公司、客户、币种、对账开始/结束日期、明细数量和预计总额。用户确认后下载 PDF；不创建中间业务单据。

## 4. PDF 固定版式

- 纸张：A4 横向，页边距 8–10 mm。
- 抬头：深蓝色横幅，中间白字公司名称，右上角黄色 Logo。
- 标题：`对账单（对账期：YYYY.MM 或 YYYY-MM-DD 至 YYYY-MM-DD）`。
- 客户区：客户名称、联系人、联系电话；右侧显示总金额、已付款、未付款。
- 明细表：蓝底白字表头，细边框，金额右对齐，文本自动换行。
- 合计区：数量、含税金额、已付款、未付款合计，并明确币种。
- 页尾：确认说明、收款单位、开户行、账号、付款方签字/盖章/日期。
- 多页：每页重复抬头、标题和表头；账户及签章区只放最后一页。

明细字段固定为：

| 序号 | 日期 | 订单号 | 产品编码 | 产品名称 | 单位 | 数量 | 单价（含税） | 总金额（含税） | 已付款金额 | 未付款金额 | 送货单号 | 备注 |
|---|---|---|---|---|---|---:|---:|---:|---:|---:|---|---|

## 5. 数据口径

### 5.1 业务明细

- 从销售订单生成：以 `Sales Order Item` 为基础，送货单号从其后续 `Delivery Note Item` 关联结果汇总。
- 从送货单生成：以 `Delivery Note Item` 的实际交付数量为基础，订单号取 `against_sales_order`，避免把未交付数量列入出货对账。
- 数量、单价、金额使用对应业务行的原始精度；含税口径优先读取单据明细的含税值或按 ERPNext 原有税费明细分摊，不由浏览器计算。

首期建议以送货单为正式客户对账的主入口，因为它代表实际交付；销售订单入口用于合同/订单范围确认，并在 PDF 上明确数据来源。

### 5.2 已付款与未付款

`总金额` 为本次所选对账明细的含税金额合计。`已付款` 不直接使用销售订单的预付款比例，也不将整张发票已付金额重复分配到每一行，而是基于关联 `Sales Invoice` 和已提交 `Payment Entry Reference` 的实际分配金额，按本次对账范围进行比例分摊。

```text
本次未付款金额 = 本次对账总金额 - 本次范围内已付款金额
```

若当前数据不能可靠建立“送货行 -> 发票行 -> 付款分配”的链路，首期 PDF 应将已付款标记为“以财务确认为准”，不得生成看似精确但重复计算的金额。正式上线前必须通过财务样本验证预付款、部分付款、合并开票、部分退货和取消发票场景。

### 5.3 客户与账户信息

- 客户名称、联系人和电话读取当前客户主数据及主联系人。
- 公司名称读取当前 `Company`，版式显示名称固定为“阿基视觉科技（东莞）有限公司”或由公司配置覆盖。
- 开户行和账号不得硬编码在 HTML；从 `Bank Account`/公司配置或新增的对账单配置中读取。
- Logo 源文件已确认：`/home/cst/frappe_docker/df8baa79f9b81863358a5464f8673abf.png`，规格为 `1246 × 616`、RGBA PNG。实施时复制到应用内受版本管理的 `client_akivision/public/images/aki_vision_logo.png`，PDF 右上角按约 `2.02:1` 原始比例等比缩放，不拉伸或裁切。运行时不得直接依赖仓库根目录绝对路径；应用静态资源找不到时仅显示公司名称，不阻断 PDF。

## 6. 校验和安全

服务端逐单执行读取权限校验，并校验同公司、同客户、同币种。取消单据、退货冲销、无权限记录和无有效明细记录不进入正式明细；部分跳过时在生成确认阶段明确告知，正式 PDF 只显示最终纳入范围。

接口仅接受白名单 `source_doctype`、单据名称数组或受控筛选条件，不接受任意 SQL、字段名、模板路径或 HTML。单次限制单据数和明细行数；文件名、客户文本和备注在渲染前转义，避免模板注入。

## 7. 调用链路

```text
销售订单 / 送货单列表
  -> 勾选单据或设置筛选条件
  -> 前端调用预检接口
  -> 服务端校验权限、公司、客户、币种、状态和数量上限
  -> 聚合订单/送货/发票/付款数据并返回确认摘要
  -> 用户确认生成
  -> PDF 接口复用同一聚合服务重新校验和取数
  -> Jinja HTML 模板填充抬头、Logo、明细、合计、账户、签章区
  -> Frappe PDF 引擎生成 A4 横向 PDF
  -> 浏览器下载 `对账单-客户-对账期.pdf`
```

预检与正式生成复用同一查询函数，避免确认金额与最终 PDF 不一致。

## 9. 新增接口

```python
@frappe.whitelist()
def preview_customer_reconciliation(source_doctype, document_names=None, filters=None):
    """Return validated customer, period, count and amount summary."""

@frappe.whitelist()
def download_customer_reconciliation_pdf(source_doctype, document_names=None, filters=None):
    """Generate the official customer reconciliation PDF from validated data."""
```

已有 `download_reconciliation_export` 和 `download_document_export` 保持原样。新接口仅增加 PDF 能力，不改变旧 Excel 返回格式或调用者。

## 10. 受影响模块

| 模块 | 影响 |
|---|---|
| 销售订单、送货单列表 | 增加正式对账单 PDF 入口 |
| 客户、联系人 | 只读获取客户名称和联系方式 |
| 销售发票、付款凭证 | 只读计算实际付款，不新增或修改记录 |
| 公司、银行账户 | 只读获取对账抬头和收款账户 |
| 打印/PDF | 新增独立模板和样式 |
| 现有 Excel 导出 | 无行为变化，继续用于内部数据分析 |
| 库存、财务记账、结算审批 | 不触发业务写入 |

## 11. 验收场景

1. 勾选同一客户、公司、币种的多张已提交送货单，生成 PDF 的明细、总额和送货单号正确。
2. 混选不同客户、公司或币种时不生成文件，并提示需要拆分。
3. 明细超过一页时不截断、不重叠，后续页重复表头，签章区只出现在最后一页。
4. 中文客户、产品和备注无乱码；Logo 不拉伸且打印清晰。
5. 预付款、部分付款、合并发票、退货和取消发票场景的已付/未付金额经财务核对一致。
6. 无权限用户手工构造请求也无法读取其他客户或公司的单据。
7. 生成前后销售订单、送货单、发票、付款和库存数据均不变化。
8. 已有 Excel 导出入口和下载文件保持可用。

## 12. 实施顺序

1. 先确定透明 Logo、公司法定名称、开户行和账号的配置来源。
2. 实现只读数据聚合与预检接口，并用真实财务样本确认金额口径。
3. 实现 HTML/CSS 固定版式和 PDF 下载接口。
4. 在送货单列表接入按钮并验收，确认稳定后再接入销售订单。
5. 在 `aki_test.localhost` 用单页、多页、中文长文本和不同付款场景验证 PDF。
6. 业务与财务共同确认后上线；后续再考虑保存对账单历史、编号、审批和电子盖章。
