# 从销售订单创建销售结算单方案

## 1. 文档目的

本文记录“销售结算单可从对应销售订单直接创建”的实施方案。本阶段只整理方案和代码影响范围，不执行业务代码修改。

目标流程：

```text
已提交销售订单
  -> 创建销售结算单
  -> 自动绑定订单、客户、公司、币种、销售出库单和出库明细
  -> 用户选择本次结算数量、结算单价、折扣/扣款
  -> 系统计算结算金额
  -> 生成销售结算单草稿
  -> 后续按现有客户确认/内部复核流程提交
```

## 2. 业务口径

销售结算单是销售订单在“对账结算后确认应收”模式下的结算确认文档，不替代销售订单，也不直接把订单变成应收。

- 来源必须是已提交销售订单；
- 可结算数据必须来自该订单下已提交、非退货的销售出库明细；
- 只读取剩余未结算数量，防止重复结算；
- 创建时自动绑定来源，不允许用户在结算单中随意改换订单或出库明细；
- “本次结算数量”“结算单价”“折扣/扣款”可在草稿中调整；
- “不含税金额”“预计税额”“价税合计”由系统计算；
- 创建动作只生成草稿，不上传客户确认材料，不生成销售发票，不生成凭证。

直接确认应收模式的订单继续走原有销售发票/应收链路，不显示该入口。

## 3. 拟修改代码（本阶段不执行）

### 3.1 服务端新增分支

文件：`development/frappe-bench/apps/china_finance/china_finance/services/sales_settlement.py`

拟新增白名单函数：

```python
create_settlement_from_sales_order(sales_order, posting_date=None)
```

处理步骤：

1. 校验当前用户具备现有销售结算准备权限；
2. 校验销售订单存在、用户有读取权限且已提交；
3. 校验订单结算模式为“对账结算后确认应收”；
4. 查询订单关联的已提交销售出库明细；
5. 复用现有 `get_settleable_delivery_items`，过滤退货、已结算和剩余数量为零的明细；
6. 以首条可结算出库明细的公司、客户、币种和确认方式创建销售结算单草稿；
7. 将销售订单来源写入每条结算明细的 `sales_order` 字段，并保留销售出库单及出库明细绑定；
8. 返回新销售结算单名称，由前端跳转到草稿表单。

现有 `create_settlement_from_delivery_notes(delivery_notes, posting_date=None)` 保持参数、行为和调用方不变。订单入口只是新增一个适配分支，最终复用现有明细快照和校验逻辑。

### 3.2 销售订单表单入口

文件：`development/frappe-bench/apps/china_finance/china_finance/public/js/sales_order_settlement.js`

拟在 `refresh` 中增加按钮：

- 仅订单已提交时显示；
- 仅结算模式为“对账结算后确认应收”时显示；
- 按钮放在“中国财务”菜单下；
- 调用新增的 `create_settlement_from_sales_order`；
- 成功后跳转至新建的 `China Sales Settlement` 表单；
- 无可结算明细时展示后端提示，不创建空文档。

### 3.3 结算明细绑定增强

文件：`development/frappe-bench/apps/china_finance/china_finance/china_finance/doctype/china_sales_settlement_item/china_sales_settlement_item.json`

原则上不新增字段，优先使用现有字段：

- `sales_order`：绑定来源销售订单；
- `delivery_note`：绑定销售出库单；
- `delivery_note_item`：绑定销售出库明细；
- `settlement_qty`：本次结算数量；
- `settlement_rate`：结算单价；
- `discount_amount`：折扣/扣款；
- `settlement_amount`：系统计算的价税合计。

如果现有表单未展示 `sales_order`，只做列表显示或只读展示的元数据增量，不改变字段类型和存量数据。

### 3.4 销售结算单来源字段评估

文件：`development/frappe-bench/apps/china_finance/china_finance/china_finance/doctype/china_sales_settlement/china_sales_settlement.json`

优先不新增主表字段，因为明细行已有 `sales_order` 绑定，且一个结算单理论上可能合并同一客户的多个订单。

如果业务确认必须在主表显示单一来源订单，则新增只读 Link 字段不能覆盖多订单场景，应改为只读来源汇总字段或来源列表；该选择在开发前确认，不在本阶段直接改元数据。

## 4. 调用链路

```text
Sales Order 表单 refresh
  -> sales_order_settlement.js
  -> 中国财务 / 创建销售结算单
  -> create_settlement_from_sales_order(sales_order)
  -> 校验订单权限、提交状态、结算模式
  -> 查询 Delivery Note Item（against_sales_order = 当前订单）
  -> get_settleable_delivery_items(delivery_notes)
  -> _delivery_item_snapshot()
  -> _active_settled_quantity()
  -> _load_settlement_item()
  -> 创建 China Sales Settlement 草稿
  -> ChinaSalesSettlement.validate()
  -> validate_sales_settlement()
  -> 回填金额、税额、日期范围和调整次数
  -> 前端打开草稿文档
```

后续流程保持原有链路：

```text
草稿销售结算单
  -> 用户调整本次数量/结算单价/折扣
  -> 保存并完成客户确认或内部复核
  -> 提交销售结算单
  -> create_receivable_for_settlement()
  -> 生成正式销售发票/应收
  -> 既有会计凭证链路
```

## 5. 受影响模块

| 模块 | 影响范围 |
|---|---|
| 销售订单 | 新增“中国财务 / 创建销售结算单”入口，仅影响已提交且为对账结算模式的订单 |
| 销售出库 | 继续作为可结算数量的事实来源，不改变提交和取消逻辑 |
| 销售结算 | 增加从订单聚合出库明细的创建分支，保存/提交校验沿用现有逻辑 |
| 销售结算明细 | 继续使用现有来源字段和金额字段；用户只编辑结算相关字段 |
| 销售发票/应收 | 创建草稿阶段不触发；结算单提交阶段沿用现有生成逻辑 |
| 会计凭证 | 不新增接口，不改变凭证生成规则 |
| 权限 | 复用现有 `PREPARER_ROLES` 和来源单据读取权限 |
| 报表/对账 | 通过已有结算明细关联获取结算数量和金额，不改变报表接口 |

## 6. 兼容和增量策略

1. 不修改 `create_settlement_from_delivery_notes` 的接口和行为。
2. 不删除或替换销售出库单上的“创建销售结算单”入口。
3. 新增订单入口只在明确满足业务条件时显示，避免直接确认应收订单误用。
4. 不修改 `China Sales Settlement Item` 的字段类型，不要求历史数据迁移。
5. 不在创建草稿时调用发票、凭证、自动提交或客户确认接口。
6. 服务端再次校验订单和出库明细，不能仅依赖前端按钮条件。
7. 继续使用现有剩余数量锁定和提交时余额校验，避免并发重复结算。
8. 如果订单包含多个销售出库单，按所有可结算出库明细生成多行；如果明细跨公司、客户或币种，由现有校验拒绝合并。

## 7. 预期效果

- 用户可以从销售订单直接发起结算，不必先手工查找销售出库单。
- 创建时订单、客户、公司、币种、出库单和出库明细自动绑定。
- 草稿阶段可以选择本次结算数量、单价和折扣，系统实时按既有校验口径计算金额。
- 生成动作只产生一张可编辑的销售结算单草稿，不会提前产生发票、应收或凭证。
- 已结算数量不会再次出现在可选明细中，降低重复结算风险。
- 原有从销售出库单创建、提交确认、自动开票和凭证链路不受影响。

## 8. 验收标准

1. 已提交且为对账结算模式的销售订单显示创建入口。
2. 直接确认应收、草稿或已取消销售订单不显示入口，后端调用也会拒绝。
3. 订单关联多个已提交出库单时，草稿包含全部剩余可结算明细。
4. 已结算或剩余数量为零的明细不会进入草稿。
5. 草稿明细的销售订单、销售出库单和销售出库明细均已绑定且只读。
6. 修改本次结算数量、结算单价或折扣后，保存时金额、税额和调整次数正确更新。
7. 没有可结算明细时不创建空文档，并显示明确提示。
8. 原有出库单入口、销售结算单提交、发票生成和凭证生成回归通过。
