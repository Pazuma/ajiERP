# 先对账后销售结算及分次结算优化方案

> 状态：方案讨论稿；仅记录预期改动，不代表已实施。范围限“对账结算后确认应收”模式；直接确认应收模式保持原状。

## 一、目标与口径

目标链路：已提交销售订单 -> 已提交销售出库单 -> 客户送货口径对账单（`China Reconciliation Statement`，`statement_type=Customer`、`statement_basis=Delivery`）提交确认 -> 关联该对账单的销售结算单 -> 分次提交并生成正式销售发票/应收。`Customer + Ledger` 用于账务对账，不作为开票前的结算依据。

一张确认对账单允许多张结算单；一条确认的出库明细允许多次部分结算。结算单主表只关联一张对账单，不能跨对账单合并；同一出库行若出现在不同对账版本中，不得因版本重叠重复结算。结算单草稿不占额度，只有已提交且状态为“已生成应收”的结算单占额度。结算单仍是确认应收的执行单据，对账单自身不创建发票。

## 二、当前实现与缺口

- `services/sales_settlement.py` 从订单、出库或客户未结算出库直接创建草稿；当前可结算量仅按出库量减退货量减已完成结算量计算，未引用对账单。订单入口汇集关联出库单的全部明细，混合订单出库时可能引入其他订单行。
- `China Sales Settlement.before_submit` 校验确认附件/内部复核原因，直接创建并提交销售发票；发票反向限制已有，但不验证对账依据。前台“生成正式应收”实质是提交结算单。
- 对账单已支持 `Customer + Delivery`、`source_detail_name`（出库明细 ID）、提交后 `Confirmed`、被替代后 `Superseded`；但前端新建客户对账单默认 `Ledger`，现有“加载往来账”仅服务于 Ledger。`get_customer_delivery_rows` 能提供送货行，但包含所有符合条件的送货单，不限结算模式。
- 对账行的 `qty/rate/amount` 当前来自出库快照且只读，没有独立的“客户确认数量/单价/扣款”字段。现有对账确认并不等于逐行确认结算价格。这是实施前必须明确并补齐的数据契约。

## 三、建议业务规则

1. 仅已提交、`status=Confirmed`、`Customer + Delivery`、同公司/客户/币种的对账单可用于创建或提交结算单。对账单明细须有唯一有效 `source_detail_name`，来源为已提交非退货、结算模式的出库单；不从日期或订单号推断明细归属。
2. 对账单逐行保存明确的“确认结算数量、确认结算单价、确认扣款总额”快照；若客户无调整，初始化为扣除退货后的可对账数量、出库单价和零扣款。确认数量不得超过可结算出库量；扣款非负且不得超过对应金额。对账确认前处理差异，确认后不得在结算单另行改价或追加扣款。
3. 本次结算数量可小于剩余确认数量；同一对账行的累计已提交结算数量不得超过确认数量，同时不得超过出库实际剩余量。确认单价沿用对账行。确认扣款按本次数量占确认数量的比例分摊；最后一笔承接舍入差额。以币种精度校验累计净额不超过确认净额，税额和发票总额以正式发票计算为准，不能把对账行的未税金额直接当含税上限。
4. 在结算明细增加对账行 ID 快照；保存和提交均验证对账行属于主表关联单、来源行一致、行未重复、确认数据未缺失。提交阶段在数据库事务中按确定顺序锁定涉及的对账行与出库行，再重算两重余额；发票创建、提交、结算单提交在同一事务中完成，失败回滚。涉及出库行被不同对账单引用时，也以出库行的全局已结算余额兜底。
5. 对账单一旦有有效已提交结算，不允许取消、替代后重新分配已消费的额度；新版对账单仅覆盖未结算余额，或实施前先定义明确的版本余额转移规则。被替代对账单上的已提交结算保留审计链接；尚未提交的草稿必须重新绑定有效版本并重新选择明细。发票被取消时现有逻辑会将结算单标为“已取消”，该部分额度释放；新结算只能从仍有效的确认对账单重新发起，不能绕过版本检查。
6. 客户确认材料与方式以对账单为准；结算单保留提交时的财务执行检查，不再要求重复上传客户材料。为避免误认为双人审批，当前“确认人/财务审批人”均记提交用户的行为应在实施时调整为对账确认人快照及结算执行人，或者保留旧字段并明确其含义；不能仅改界面标签冒充独立审批。

## 四、入口及调用链

```text
销售出库单提交（对账模式不自动开票）
  -> 客户送货对账单选择公司/客户/期间、加载结算模式出库行
  -> 人工核对确认数量/单价/扣款、上传客户确认材料或内部复核
  -> 对账单提交：检查来源、确认值、已有确认单重叠与版本关系
  -> 对账单“创建销售结算单”调用新增 API（按行剩余额度生成草稿）
  -> 结算单选择部分行/数量，保存时关联对账单及明细快照
  -> 提交：锁行并复核对账余额 + 出库余额 -> ERPNext 映射发票
  -> 提交发票 -> 写回结算单状态/发票关联 -> 刷新订单和出库汇总
```

订单、出库单的旧按钮改为“查看/创建送货对账单”的导航入口，不再调用旧的直接创建结算单 API。结算单页面“选择未结算销售单”改为先选已确认对账单，再从其确认行选择。所有直接创建路径必须在服务端受同一门禁约束，隐藏按钮不能替代后端验证。

## 六、关联影响与迁移

- **订单/出库/自动开票**：继续快照结算模式；对账模式不自动生成发票。订单按钮只跳转或筛选与订单相关的出库对账行，尤其避免混合订单出库全量带入。汇总字段仍由结算成功/发票取消后更新。
- **对账单与 PDF**：`Customer + Ledger`、Supplier、Bank 不变；送货口径 PDF 如共用现有 PDF 导出，需要核对展示确认数量、单价、扣款及本次/剩余结算，不把旧 Ledger PDF 列定义强行套用。
- **发票、凭证、收款**：正式发票仍由结算单提交产生；`validate_sales_invoice_settlement` 保持对直接开票的拦截，凭证和后续收款仍跟随 ERPNext 发票链路；发票取消的额度释放与历史结算状态需回归。
- **历史单据**：既有已提交结算/发票保留且不倒填虚构对账关系；新增关联字段先可空并区分历史记录，但上线后新建草稿必须绑定对账单。上线前已有未提交草稿需选择：补关联并逐行匹配确认值，否则禁止提交；不静默赋予豁免。对账单旧 Delivery 行无确认值时不能直接用于新结算，须先完成补录和确认/新版替代流程。
- **权限与审计**：读取对账单、来源出库行、创建/提交结算单及发票权限分别检查；Link 过滤仅辅助选择，后端复核不可省略。版本、确认值、结算来源及取消链路均应可追溯。

## 七、验收场景与预期效果

1. 未对账、草稿对账、Ledger 对账、已替代或已取消对账均无法新建/提交新的结算；确认的 Customer + Delivery 对账单能正常生成部分结算草稿。
2. 同一确认行分两次结算，数量合计恰好达到确认数量，扣款分摊与净额合计恰好等于确认值；第三次被拒绝，草稿未提交不占用余额。
3. 改动结算行来源、公司、客户、币种、数量、价格或关联对账行均被服务端拒绝；不同结算单并发抢占同一行时仅允许不超余额的提交成功。
4. 同一出库行跨对账版本重复出现，不能重复开票；已有结算的对账单取消/替代时有明确保护；旧正式结算仍可查，未提交草稿不会绕过新版校验。
5. 混合订单出库时，订单入口只定位该订单相关行；直接模式的自动开票、对账模式发票提交、销售退货/发票取消和订单出库汇总均回归通过。
6. 客户能从对账单看到确认值及已结/未结余额，财务从结算单追溯对账单、确认行、出库明细与正式发票，避免重复确认材料。

## 八、建议实施顺序与待确认项

先实现 Delivery 对账入口及确认值数据契约；再加结算关联和后端门禁/原子余额控制；之后调整旧按钮和表单选择器；最后处理历史草稿、PDF/报表及全链路回归。每步保持旧 API 的函数名和返回结构（成功路径）不变，仅对不符合新规则的调用明确拒绝。

待业务确认：对账单确认金额为未税金额还是含税金额；退货发生在确认后时是否要求先出新版对账单；已有已确认 Delivery 对账单如何补录新确认值；对账单已有结算时是否彻底禁止替代，或允许只转移未结余额。上述口径确定前，不应上线自动补数或静默迁移。
