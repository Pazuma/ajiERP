# 销售订单按可分配库存生成送货单与生产工单优化方案

## 1. 文档目的

本文档沉淀销售订单提交后的自动履约分流优化方案，当前阶段仅形成设计，不修改任何业务代码、接口、数据库结构或系统配置。

目标规则如下：

- 物料可分配库存足够：创建草稿销售送货单（Delivery Note）。
- 物料可分配库存不足：对可分配数量创建草稿销售送货单，对缺口数量创建草稿生产工单（Work Order）。
- 物料完全无可分配库存：不创建空送货单，仅对缺口创建草稿生产工单。
- 自动生成的单据保持草稿状态，必须由有权限的人员核对后提交。

本次优化坚持小增量改造：保留现有公开接口、提交钩子、异步队列、实时事件和人工创建送货单入口，优先新增内部计划分支和只读预览能力，不修改 ERPNext 核心代码。

## 2. 已查明的现状

当前代码的实际顺序并不是简单地把“库存充足”和“库存不足”写反，而是：

1. 调用 ERPNext 标准 `create_pick_list` 计算可拣配数量。
2. 将可拣配数量写入草稿销售送货单。
3. 使用“销售订单待交付数量 - 已有送货单数量 - 已有生产工单数量”计算剩余缺口。
4. 对剩余缺口创建草稿生产工单。

现有代码已经能够出现以下三种结果：

| 场景 | 当前可观察结果 |
| --- | --- |
| 全部可分配 | 仅生成草稿销售送货单 |
| 完全不可分配 | 仅生成草稿生产工单 |
| 部分可分配 | 送货单承接可分配数量，生产工单承接剩余数量 |

用户感知为“流转反了”的主要风险是库存口径不同：页面可能展示 `actual_qty`（账面实际库存），自动履约实际采用 ERPNext 拣货分配结果。实际库存即使大于订单数量，也可能已经被其他单据预留，因此当前订单的可分配库存仍为零。

此外，现有实现存在以下需要收敛的问题：

- 主流程中库存分配、历史单据扣减、缺口判断分散，无法直接展示每行为什么进入送货或生产分支。
- 只要销售订单任一明细存在 `stock_reserved_qty > 0`，当前实现会整单跳过自动规划，粒度过粗。
- 已存在生产工单时不会再次创建送货单；后续补货后，重新计算无法自然反映新的库存状态。
- 已有送货单与生产工单均按 `docstatus < 2` 汇总，草稿与已提交单据没有被分别表达。
- 自动化测试仍保留旧拣货单辅助函数的模拟，与目前直接创建销售送货单的实现存在偏差。
- 前端提交提示仍出现“草稿拣货单”，与当前生成“草稿销售送货单”的实际行为不一致。

## 3. 库存判定口径

### 3.1 推荐口径

自动履约以 ERPNext 标准分配引擎返回的“可分配库存”为唯一分流依据，继续复用 `create_pick_list(sales_order)`，不自行使用 `Bin.actual_qty` 编写另一套扣减公式。

原因如下：

- `actual_qty` 只表示账面实存，不能完整表达预留、仓库和订单占用关系。
- ERPNext 标准分配逻辑能够处理仓库、换算因子、批次/序列号及既有预留规则。
- 复用标准引擎可避免自动送货占用已分配给其他订单的库存。
- 不改库存台账与预留接口，对采购、仓储、生产和其他销售订单的影响最小。

页面如需解释分流结果，应分别显示“实际库存、已预留/已占用、可分配库存”，不能只显示一个笼统的“库存”。

### 3.2 数量公式

所有自动规划数量统一换算到库存单位计算：

```text
待履约数量 = max(销售订单库存数量 - 已交付库存数量, 0)
锁定送货数量 = 已提交且未取消的销售送货单数量
草稿送货数量 = 未取消草稿销售送货单数量
锁定生产数量 = 已提交且未取消的生产工单数量
草稿生产数量 = 未取消草稿生产工单数量

剩余待规划数量 = max(
  待履约数量
  - 锁定送货数量
  - 草稿送货数量
  - 锁定生产数量
  - 草稿生产数量,
  0
)

建议送货数量 = min(标准分配引擎返回的可分配数量, 剩余待规划数量)
建议生产数量 = max(剩余待规划数量 - 建议送货数量, 0)
```

必须以 `Sales Order Item.name` 作为行级关联键，避免同一销售订单中相同物料出现多行时互相串量。

## 4. 目标调用链路

```text
提交销售订单
  -> hooks.py: Sales Order.on_submit
  -> enqueue_on_submit(doc)
  -> 提交事务完成后进入 short 队列
  -> create_draft_fulfilment_documents(sales_order, notify_user)
  -> 锁定销售订单并校验状态
  -> build_fulfilment_plan(sales_order)
       -> 读取每行待履约数量
       -> 调用 ERPNext create_pick_list 获取可分配数量
       -> 分别读取草稿/已提交送货单数量
       -> 分别读取草稿/已提交生产工单数量
       -> 按销售订单明细行生成送货建议和生产建议
       -> 校验生产物料及有效 BOM
  -> apply_fulfilment_plan(plan)
       -> 有建议送货数量：新增一张草稿销售送货单
       -> 有建议生产数量：按明细行新增草稿生产工单
       -> 某分支失败：保存问题，其他可执行分支继续
  -> 写销售订单时间线备注
  -> 向生产人员发送缺货通知
  -> 发布 sales_order_auto_fulfilment_complete 实时事件
  -> 前端刷新草稿角标并展示结果
```

人工点击“重新生成备货草稿”时继续走现有公开方法：

```text
销售订单表单
  -> recalculate_sales_order_fulfilment(sales_order)
  -> 原有异步任务入口
  -> 同一 build/apply 计划链路
```

“一键创建销售送货单”属于人工映射路径，继续调用 `sales_order_delivery.make_simple_delivery_note`，不纳入本次自动分流改造。

## 6. 建议新增的内部结构

建议新增内部函数 `build_fulfilment_plan(sales_order_doc)`，每条销售订单明细生成如下结构：

```python
{
    "sales_order_item": "SO-ITEM-ROW-ID",
    "item_code": "ITEM-001",
    "warehouse": "成品仓 - T",
    "pending_qty": 10,
    "actual_qty": 12,
    "reserved_qty": 5,
    "allocatable_qty": 7,
    "draft_delivery_qty": 0,
    "submitted_delivery_qty": 0,
    "draft_work_order_qty": 0,
    "submitted_work_order_qty": 0,
    "recommended_delivery_qty": 7,
    "recommended_work_order_qty": 3,
    "status": "partial",
    "reason": "可分配库存仅满足部分需求",
}
```

其中 `actual_qty`、`reserved_qty` 主要用于解释和界面展示，真正创建送货单的数量仍以标准分配引擎返回值为准。计划函数只计算、不写数据库，便于测试和后续增加只读预览。

现有 `create_draft_fulfilment_documents` 改为协调函数：校验、调用计划、执行计划、通知，不在循环中重复推导业务规则。

如需让用户在执行前查看结果，建议新增只读接口 `preview_sales_order_fulfilment(sales_order)`，而不是修改现有重新生成接口的响应契约。该接口仍必须执行销售订单读取权限校验，不暴露用户无权查看的库存或下游单据。

## 7. 分支规则与单据边界

### 7.1 首次自动执行

| 条件 | 动作 | 预期结果 |
| --- | --- | --- |
| 可分配量 >= 待规划量 | 只创建送货草稿 | 不创建生产工单 |
| 0 < 可分配量 < 待规划量 | 创建送货草稿和生产草稿 | 两者之和等于待规划量 |
| 可分配量 = 0 | 只创建生产草稿 | 不创建空送货单 |
| 缺口物料无有效 BOM | 创建可送部分；缺口记为问题 | 不创建无效生产工单 |
| 非库存物料、直送物料或产品套装 | 沿用 ERPNext/现有排除规则 | 不误建生产工单 |

### 7.2 重复执行与幂等性

- 每次先扣除所有未取消的关联送货单和生产工单数量。
- 同一销售订单明细的“已规划数量 + 本次新增数量”不得超过待履约数量。
- 重复队列任务、重复点击或任务重试不应生成重复数量。
- 使用当前销售订单行锁和现有队列去重标识，继续防止并发规划。
- 任一分支失败只记录该分支问题，不回滚已经成功创建的另一类草稿。

### 7.3 已有草稿单据

第一阶段采用保守的“只补不减”策略：

- 已有草稿销售送货单或草稿生产工单时，只补充尚未覆盖的数量。
- 不自动删除、取消、减少或改写人工已经编辑的草稿。
- 补货后若可分配库存增加，但已有草稿生产工单已经覆盖该数量，系统不静默把生产数量转成送货数量。
- 对这种可重新分配的情况返回冲突提示，例如“现有草稿生产工单占用 3，当前库存已可送 3，请人工确认是否调整草稿生产工单后重新计算”。

后续如确需“一键重排草稿”，应作为单独二期能力：展示变更预览并由用户明确确认，仅允许调整系统自动创建且仍为草稿的单据。

### 7.4 已提交单据

- 已提交销售送货单和生产工单视为锁定数量。
- 自动流程不得修改、取消或冲减已提交单据。
- 已提交数量超过当前待履约量时停止该行新增，并记录数据冲突供人工核查。
- 已取消单据不参与数量占用。

### 7.5 库存预留

第一阶段保留 ERPNext 标准预留校验，不绕过预留库存。建议把当前“任一行存在预留则整单跳过”收敛为行级结果：

- 能由标准分配引擎正确计算的行继续生成计划。
- 无法安全自动处理的预留行单独标记为 `reservation_conflict`，不创建送货或生产草稿。
- 其他无冲突明细不应被一并阻断。

该调整必须先用站点实际启用的 Stock Reservation 流程做集成测试；若标准分配结果无法可靠关联预留，第一阶段仍保持整单跳过，以安全优先。

```text
recalculate_sales_order_fulfilment(sales_order)
create_draft_fulfilment_documents(sales_order, notify_user=None)

```

现有执行结果字段继续保留：

```python
{
    "delivery_note": None,
    "pick_list": None,
    "work_orders": [],
    "issues": [],
}
```

仅允许向结果和实时消息追加可选字段，例如：

```python
{
    "plan_summary": {
        "delivery_qty": 7,

        "conflict_count": 0,
    }
}
```

旧前端忽略新增字段仍可正常工作，新前端可以渐进读取。这样不会破坏现有按钮、后台任务、实时消息监听和角标刷新。

## 9. 受影响模块

| 模块 | 影响说明 | 风险控制 |
| --- | --- | --- |
| 销售订单 | 提交和手工重新计算时按行生成计划 | 不改变提交校验、状态和老接口 |
| 销售送货单 | 根据可分配数量生成草稿 | 不自动提交，不修改人工单据 |
| 生产工单 | 根据剩余缺口生成草稿 | 继续要求有效 BOM，不自动提交 |
| 库存/拣货 | 复用标准分配结果 | 不直接改 Bin 或库存台账 |
| 库存预留 | 影响可分配数量 | 不绕过预留，冲突时停止相关行 |
| BOM | 决定缺口能否转生产 | 无有效 BOM 时提示人工处理 |
| 通知与时间线 | 展示分流结果和异常 | 失败不回滚业务草稿 |
| 工作台角标 | 继续统计自动生成草稿 | 保持现有权限过滤和接口 |
| 权限 | 创建动作仍由后台自动化完成，查看沿用 DocType 权限 | 不扩大其他功能权限，不新增角色权限 |
| 人工送货入口 | 不参与自动分流 | 保留现有行为，避免范围扩张 |

## 10. 关联部分同步修改

实施时需同步检查以下关联点，避免主流程正确但页面表达仍错误：

- 提交提示中的“草稿拣货单”统一改为“草稿销售送货单”。
- 自动完成弹窗明确区分“可送数量”和“生产缺口”，不能只显示单据数量。
- 销售订单时间线备注记录各明细行的计划数量和异常原因。
- 生产人员通知仅针对实际新增的草稿生产工单。
- 草稿角标继续只统计当前用户有权读取的单据，不因计划预览绕过权限。
- 自动生成来源字段 `custom_auto_fulfilment` 和 `custom_auto_fulfilment_sales_order` 继续写入，便于区分人工草稿。
- 中文翻译补全新增状态：库存充足、部分满足、库存不足、预留冲突、无有效 BOM、已有草稿冲突。
- 旧的 Pick List 内部辅助函数若确认无调用，可在独立清理提交中移除；本次小增量修改不强制删除，避免扩大变更范围。

| T13 | 非库存物料、直送物料、产品套装 | 不误建生产工单 |
| T14 | 有预留库存 | 以标准可分配量判断，或按安全策略标记冲突 |

### 11.2 集成与页面验收

- 在测试站点准备“无预留、部分预留、全部预留”三组同物料数据，对照 Bin 与 Pick List 分配结果。
- 提交销售订单后确认异步任务只生成草稿，不自动提交。
- 校验送货草稿每行 `against_sales_order`、`so_detail`、仓库、单位和换算数量。
- 校验生产工单的 `sales_order`、`sales_order_item`、BOM、成品仓和数量。
- 重复点击“重新生成备货草稿”，确认不会重复规划。
- 分别使用有/无 Delivery Note、Work Order 读取权限的用户验证弹窗链接和角标。
- 确认人工“一键创建销售送货单”仍保持原行为。
- 确认销售订单提交、取消、库存预留、采购、生产领料及销售出库等既有流程不受影响。

## 12. 分阶段实施顺序

### 第一阶段：修正表达并固化计划计算

- 新增纯计划函数，统一数量口径。
- 调整主流程消费计划结果。
- 保持“已有草稿只补不减、已提交完全锁定”。
- 修复前端“拣货单/送货单”文案。
- 更新单元测试，覆盖三种库存分流和幂等性。

预期效果：新订单能够稳定按可分配库存生成正确草稿，重复执行不重复建单，且页面能够解释分流原因。

### 第二阶段：增加只读计划预览

- 新增只读预览接口和销售订单内的计划展示。
- 展示需求、实际库存、预留/占用、可分配、送货建议、生产缺口和冲突原因。
- 严格复用销售订单及下游单据读取权限。

预期效果：用户在重新计算前能看到系统为什么判断库存不足，减少将“账面库存”误认为“可分配库存”的情况。

### 第三阶段：可选的草稿重排

- 仅在业务确认确有需要后实施。
- 只允许调整系统自动生成且仍为草稿的单据。
- 先展示差异，再由有权限用户明确确认。
- 已提交单据永不自动调整。

预期效果：补货后可在受控条件下把尚未执行的生产草稿转为送货草稿，同时保留完整操作痕迹。

## 13. 总体验收标准与预期效果

实施完成后应达到以下结果：

1. 库存充足时，只创建对应数量的草稿销售送货单，不创建生产工单。
2. 库存不足时，只对真实缺口创建草稿生产工单。
3. 部分库存时，送货数量与生产数量之和等于未被已有单据覆盖的待履约数量。
4. 页面可以明确解释“实际库存有数但可分配库存不足”的原因。
5. 重复任务、重复点击、后台重试不会造成数量重复。
6. 已有草稿默认只补不减；已提交单据不被自动修改、取消或冲减。
7. 无 BOM、预留冲突、权限不足等情况有明确提示，不生成不合法单据。
8. 原有接口路径、参数、实时事件、角标、提交钩子和人工送货入口保持兼容。
9. 不改变其他功能权限，不扩大用户对销售送货单、生产工单或库存数据的可见范围。
10. 自动化失败不会回滚已经成功创建的其他合法草稿，并能在日志和销售订单时间线追踪原因。

## 14. 实施前待确认事项

以下业务口径应在编码前确认，但不影响本方案作为第一阶段实施基线：

- “库存充足”是否正式确认采用扣除预留后的 ERPNext 可分配库存，而不是 `actual_qty`。
- 已有自动生产草稿且后来补货时，第一阶段是否接受“提示人工调整、不自动重排”。
- 同一订单多仓库时，是否严格以销售订单行仓库/订单默认仓库为限，还是允许标准策略跨仓分配。
- 生产缺口是一条销售订单明细一张生产工单，还是相同物料/BOM/仓库允许合并；为保持追踪和幂等性，本方案默认逐明细创建。

在上述口径未另行确认前，推荐默认采用：标准可分配库存、已有草稿只补不减、禁止自动调整已提交单据、逐销售订单明细创建生产工单。
