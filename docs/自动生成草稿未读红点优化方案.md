# 自动生成草稿未读红点优化方案

## 1. 背景与目标

销售订单提交后，系统通过异步任务自动创建销售送货单或生产工单草稿。当前已有自动生成来源标识 `custom_auto_fulfilment`，并有 `get_auto_draft_badge_counts()` 统计入口，但缺少按当前用户记录“是否已查看”的能力。

目标：

- 自动生成的销售送货单、生产工单草稿在列表单据名称旁显示小红点。
- 模块入口/菜单图标显示仍有未读自动草稿的提示。
- 当前用户打开具体单据详情后，该单据红点消失。
- 不同用户的已读状态相互独立。
- 普通手工创建的草稿不显示该红点。
- 尽量不修改原有自动流转和已有接口，采用新增字段、阅读记录和新增接口的方式实现。

## 2. 现状调用链路

```text
Sales Order 提交
  -> hooks.py: doc_events["Sales Order"]["on_submit"]
  -> sales_order_auto_fulfilment.enqueue_on_submit
  -> enqueue_after_commit 异步执行
  -> create_draft_fulfilment_documents
  -> _create_draft_delivery_note / _create_draft_work_order
  -> _set_auto_fulfilment_source
  -> custom_auto_fulfilment = 1
  -> 当前仅发送通知/统计数量，未记录用户已读状态
```

现有相关代码：

- `client_akivision/utils/sales_order_auto_fulfilment.py`
- `client_akivision/hooks.py`
- `client_akivision/public/js/auto_fulfilment_badges.js`
- `client_akivision/public/css/auto_fulfilment_badges.css`
- `client_akivision/utils/manufacturing_sidebar.py`
- `client_akivision/utils/selling_sidebar.py`

## 3. 方案总览

新增一张通用阅读记录表，使用以下唯一业务键：

```text
user + reference_doctype + reference_name
```

只对满足以下条件的单据显示红点：

```text
docstatus = 0
custom_auto_fulfilment = 1
当前用户没有对应阅读记录
用户拥有该单据 read 权限
```

打开单据详情时调用新增的“标记已读”接口。接口幂等，重复打开不会产生重复记录。

## 4. 拟修改文件与代码

### 4.1 新增阅读记录 DocType

新增目录及文件：

```text
client_akivision/doctype/auto_draft_read_record/
  auto_draft_read_record.json
  auto_draft_read_record.py
  __init__.py
```

建议字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| user | Link/User | 当前用户 |
| reference_doctype | Link/DocType | Work Order 或 Delivery Note |
| reference_name | Dynamic Link | 被查看单据 |
| first_read_at | Datetime | 首次查看时间 |
| last_read_at | Datetime | 最近查看时间 |

增加唯一索引：`user + reference_doctype + reference_name`。该表只保存阅读状态，不改变业务单据状态。

### 4.2 新增服务端模块

新增：

```text
client_akivision/utils/auto_draft_read.py
```

建议新增接口：

- `get_unread_auto_draft_names(doctype, names)`：返回当前用户未读单据名称集合。
- `mark_auto_draft_read(doctype, name)`：校验 read 权限后写入阅读记录。
- `get_auto_draft_badge_counts()`：保留原接口名，内部增加按当前用户未读统计；返回结构继续兼容原有 `delivery_note`、`work_order`，可新增 `unread_total`。

实现要求：

- 只允许 `Work Order`、`Delivery Note` 两个目标 DocType。
- 只处理 `docstatus=0` 且 `custom_auto_fulfilment=1` 的单据。
- 所有查询必须带权限校验，不能通过前端传参越权读取。
- 记录写入使用 `get_or_create` 或唯一键冲突兜底，保证幂等。

### 4.3 自动生成链路

修改：

```text
client_akivision/utils/sales_order_auto_fulfilment.py
```

只增加“生成后刷新未读提示”的分支，不改变送货单/生产工单创建逻辑：

- 保留 `_set_auto_fulfilment_source()` 作为识别依据。
- 创建成功后继续发送现有通知。
- 可通过实时事件通知前端刷新对应列表和模块计数。
- 不在创建任务中预写所有用户的阅读记录；阅读记录应按实际查看用户生成。

### 4.4 Work Order 列表

新增：

```text
client_akivision/public/js/work_order_auto_draft_badge.js
client_akivision/public/css/auto_draft_read_badge.css
```

并在 `hooks.py` 的 `doctype_list_js["Work Order"]` 中以新增分支挂载脚本，保留原有 `document_export_list.js`。

功能：

- 列表加载后批量调用 `get_unread_auto_draft_names`。
- 在名称链接旁渲染红点，并使用 tooltip 标明“自动生成草稿，未查看”。
- 点击名称进入详情页时调用 `mark_auto_draft_read`。
- 标记成功后刷新当前行和模块计数。

### 4.5 Delivery Note 列表

新增：

```text
client_akivision/public/js/delivery_note_auto_draft_badge.js
```

在 `hooks.py` 的 `doctype_list_js["Delivery Note"]` 中与现有列表脚本并列加载，处理逻辑与 Work Order 一致。

### 4.6 模块入口/图标

优先修改已有：

```text
client_akivision/public/js/auto_fulfilment_badges.js
client_akivision/public/css/auto_fulfilment_badges.css
```

调整为显示“当前用户未读自动草稿”而不是所有自动草稿总数。推荐显示规则：

- 模块入口有任意未读单据时显示红点。
- 仅点击模块入口不清除红点。
- 打开具体单据详情并成功标记已读后重新计算。
- 没有未读单据时隐藏红点。

### 4.7 hooks.py

修改：

```text
client_akivision/hooks.py
```

新增脚本挂载和必要的 `after_migrate` Schema 初始化入口；原有 `on_submit`、通知接口保持不变。

## 5. 详细调用链路

### 5.1 生成草稿

```text
销售订单提交
  -> enqueue_on_submit
  -> create_draft_fulfilment_documents
  -> 创建 Delivery Note / Work Order 草稿
  -> 写入 custom_auto_fulfilment=1、来源销售订单
  -> realtime.publish("auto_draft_created")
  -> 当前打开的列表/模块入口刷新未读数量
```

### 5.2 列表显示红点

```text
打开 Work Order / Delivery Note 列表
  -> 请求当前页单据名称
  -> get_unread_auto_draft_names
  -> 服务端按当前用户过滤阅读记录
  -> 前端在对应单据名称旁渲染红点
```

### 5.3 打开单据并标记已读

```text
点击单据名称
  -> 路由进入详情页
  -> 调用 mark_auto_draft_read
  -> 校验单据仍是自动生成草稿及当前用户 read 权限
  -> 写入/更新阅读记录
  -> 刷新列表行和模块入口计数
```

## 6. 受影响模块

- 销售订单自动流转：仅增加事件刷新，不改变创建规则。
- 生产工单列表：名称旁红点、打开后已读。
- 销售送货单列表：名称旁红点、打开后已读。
- 制造模块入口：按当前用户显示未读提示。
- 销售/库存模块入口：按当前用户显示未读提示。
- 权限：按照现有 DocType read 权限过滤。
- 数据库：新增阅读记录 DocType 和索引。
- 缓存/实时通知：增加局部刷新事件，不改老接口返回字段含义。

## 7. 小增量与兼容策略

1. 保留 `custom_auto_fulfilment` 和现有自动创建函数。
2. 保留 `get_auto_draft_badge_counts()` 原字段，新增字段只向后兼容扩展。
3. 不改生产工单、销售送货单主表的业务状态定义。
4. 不使用单据主表的全局 `is_read`，避免多人协作互相影响。
5. 前端脚本以新增文件挂载，避免覆盖原有列表、导出和详情脚本。
6. 未安装阅读记录表或历史数据异常时，红点功能降级为隐藏，不阻断自动流转。
7. 自动任务通知失败不得回滚已创建草稿，沿用现有 `_run_non_blocking` 处理方式。

## 8. 预期效果

- 自动创建的草稿在生产工单、销售送货单列表名称旁显示小红点。
- 普通手工草稿不显示红点。
- 用户打开某一张自动草稿后，该用户看到的该单据红点消失。
- 模块入口红点只在仍有未读单据时保留。
- 多用户场景下，甲已读不影响乙的未读提示。
- 自动生成、列表查询、详情打开、通知失败等原有流程继续可用。
- 重复打开、重复刷新、重复异步任务不会产生重复阅读记录或重复红点。

## 9. 验收标准

1. 提交满足自动流转条件的销售订单，成功生成生产工单或销售送货单草稿。
2. 对应列表中自动草稿名称旁显示红点，手工草稿无红点。
3. 用户 A 打开单据详情后，A 的红点消失；用户 B 仍显示红点。
4. 仅点击模块入口不应误清除具体单据的未读状态。
5. 单据被提交、取消或删除后，不再显示自动草稿未读红点。
6. 无权限用户无法通过接口获取或标记他人可见范围外的单据。
7. 重复执行自动流转不会重复创建阅读记录。
8. 原有自动生成失败、通知失败和手工创建流程不受影响。

## 10. 实施顺序

1. 新增阅读记录 DocType、索引和服务端接口。
2. 为 Work Order、Delivery Note 列表增加红点脚本。
3. 增加详情打开后的标记已读调用。
4. 将已有模块徽标改为按当前用户未读数量计算。
5. 增加实时刷新和缓存清理。
6. 运行 migrate、bench build、缓存清理。
7. 按验收标准验证单用户、多用户、权限和重复任务场景。
