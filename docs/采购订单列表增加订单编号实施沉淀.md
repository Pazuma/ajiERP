# 采购订单列表增加订单编号实施沉淀

## 1. 实施结论

已按《采购订单表字段顺序调整实施方案》完成代码修改。本次对象是 Buying 模块标准 `Purchase Order` 列表，不是自定义“采购清单”（`Purchase List`）报表。

列表现在将系统自动生成的采购订单流水号 `Purchase Order.name` 放在第一业务列，列标题为“订单编号”。列表同时收敛为订单编号、供应商名称、状态、订单日期、含税总额等高频字段；物料、交期、收货、对账等完整信息下沉到订单详情和采购清单报表。订单编号沿用 Frappe 标准 Subject 链接，点击后进入对应采购订单详情，不新增人工编号字段，也不改变命名系列、历史编号或业务数据。

## 2. 修改清单

| 文件 | 修改内容 |
| --- | --- |
| `client_akivision/hooks.py` | 增加 `Purchase Order` 的 `doctype_list_js` 入口。 |
| `client_akivision/public/js/purchase_order_list.js` | 保留 ERPNext 原生列表设置和 `onload`，将默认 `supplier_name` 主列替换为 `name` 主列并显示为“订单编号”；列表只保留供应商、状态、订单日期、含税总额等重要字段；详细字段下沉到详情/采购清单；重新渲染表头。 |
| `docs/playwright_purchase_order_list_ui.mjs` | 新增可重复的 Playwright 验证脚本，覆盖列顺序、链接、原生动作和移动端布局。 |
| `docs/playwright_purchase_order_list_result.json` | 保存本轮 Playwright 结果。 |
| `docs/playwright_purchase_order_list.png` | 保存本轮浏览器截图。 |

未修改 `Purchase Order` DocType、`autoname`、`title_field`、自定义 `Purchase List` 报表、筛选排序、权限、金额计算、状态和历史数据。

## 3. 数据流

1. 新建采购订单时，ERPNext 按现有 `autoname: naming_series:` 配置生成唯一的 `Purchase Order.name`。
2. Frappe 列表接口返回采购订单行数据，其中 `name` 是订单真实主键/文档名，`supplier_name`、`status`、`transaction_date`、`grand_total` 等是现有列表字段。
3. `purchase_order_list.js` 在列表初始化时保留 ERPNext 原生设置，然后调整客户端列数组：`name` 成为 Subject 首列，`supplier_name` 成为后续 Field 列。
4. 标准 Subject 渲染器使用当前行的 `doc.name` 生成 `/app/purchase-order/<name>` 文档链接。
5. 用户点击链接后由 Frappe 路由打开对应 `Purchase Order` 表单，详情页继续执行原有权限校验和业务逻辑。

## 4. 依赖清单

- Frappe List View 的 `doctype_list_js` 加载机制。
- ERPNext 原生 `purchase_order_list.js`，包括状态指示器、关闭/重开、采购收货、采购发票和预付款批量动作。
- `Purchase Order` DocType 的 `name`、`supplier_name`、`transaction_date`、`grand_total` 等标准字段。
- 站点现有命名系列和采购订单查看权限。
- Playwright 项目依赖及本机 Chromium：用于前端行为和响应式布局验证。

## 5. 风险点清单

| 风险 | 影响 | 控制/处理 |
| --- | --- | --- |
| 自定义脚本覆盖 ERPNext 原生设置 | 批量动作或状态指示器消失 | 脚本先保存并调用原生 `onload`，只调整列配置。 |
| 把供应商编号或临时序号当成订单编号 | 链接无法准确打开订单 | 固定使用列表行 `doc.name`，不新增业务编号。 |
| 用户保存了旧的列表字段配置 | 个别用户缓存后仍看到旧列 | 发布后执行 `bench clear-cache`/刷新 Desk，并在默认视图和已保存视图复测。 |
| 长订单号在窄屏被截断 | 识别和点击体验变差 | 继续使用标准 ellipsis/link 样式；移动端验证订单编号仍可见。 |
| 仅有列表权限、没有表单查看权限 | 点击后无法进入详情 | 沿用标准 Frappe 权限控制，不通过前端绕过权限。 |
| 误修改自定义 `Purchase List` | 树形采购清单行为回归 | 本次未改该报表文件，单独列为复测边界。 |

## 7. 问题记录与解决方案

| 编号 | 现象 | 原因 | 解决方案 | 状态 |
| --- | --- | --- | --- | --- |
| P-01 | 初版 Playwright 夹具无法启动本地 HTTP 服务 | 当前沙箱禁止监听 `127.0.0.1` 端口 | 改为 `page.setContent`/浏览器上下文直接注入，不依赖网络服务 | 已解决 |
| P-02 | Chromium 在受限沙箱内因 `setsockopt`/`SIGTRAP` 退出 | 宿主浏览器进程受到系统调用限制 | 使用受控宿主权限运行本地无网络 Playwright 夹具 | 已解决 |
| P-03 | 初版内联 HTML 测试脚本发生 `Document.write` 解析错误 | 测试夹具嵌套脚本模板解析冲突 | 收敛为页面上下文直接执行脚本并保留独立 DOM 断言 | 已解决 |

## 8. 需要复测的场景

以下场景需要在实际运行的 `aji_test.localhost` 或生产预发布站点，用真实采购用户账号复测：

1. 草稿、已提交、已取消采购订单的订单编号是否都准确显示并可按权限打开。
2. 新建采购订单后确认编号仍由系统自动生成，编号格式和流水号序列未改变。
3. 默认列表、用户已保存列表视图、不同屏幕密度下的第一列位置和列标题。
4. 采购订单筛选、排序、分页、导出和批量 Close/Reopen/Receipt/Invoice/Advance Payment 操作。
5. 仅有列表权限、没有采购订单查看权限的账号，确认链接不造成权限绕过或错误提示。
6. 超长订单号、无数据列表、数据加载中和接口失败时的显示与可用性。
7. 自定义 `Purchase List` 报表保持原有树形订单、物料和采购收货明细逻辑。

发布后执行资源构建/缓存清理，并让采购用户重新加载 Desk。若需回滚，移除 `doctype_list_js` 入口和 `purchase_order_list.js` 即可；不需要数据库迁移，也不需要回滚订单流水号或历史业务数据。
