# aki_erp 系统交接文档及核心业务流程

文档版本：V1.0  
编制日期：2026-11-17  
适用系统：基于 Frappe / ERPNext 的 aki_erp 制造与贸易管理系统  
适用对象：系统管理员、实施运维、销售、采购、工程、生产、质量、仓库及财务负责人

> 本文依据当前代码仓库、发布包清单、操作手册和实施记录整理。仓库中的“优化方案”不等于生产站点已经上线；正式交接必须使用目标站点和各岗位测试账号完成本文验收表。文中的审批人、会计科目、税率及金额权限以公司最终制度为准。

## 1. 系统概况

系统覆盖客户与供应商、物料、报价、销售、采购、库存、BOM、图纸、生产、质量、项目、应收应付、中国财税、对账及经营看板。标准业务由 ERPNext 承载，客户化能力主要由 `client_akivision`、`china_finance` 等应用扩展。

当前发布资料记录的核心版本如下，现场应以 `bench --site <站点名> list-apps` 的结果为准：

| 组件 | 发布资料版本 |
|---|---|
| Frappe | 16.23.0 |
| ERPNext | 16.23.0 |
| china_finance | 0.6.11 |
| client_akivision | 0.0.1 |
| deeplinkerp_branding | 0.0.6 |
| custom_filters | 0.0.2 |
| draft_notifications | 0.0.1 |
| mes_integration | 0.0.1 |

发布包的版本记录还包含 `ai_assistant`、`crm_integration`、`oa_purchase_request`、`overseas_costing`。这些扩展是否启用，必须在现场逐项核实。仓库示例 Compose 使用的镜像标签可能与上述发布快照不同，升级时不得仅凭示例文件直接替换生产镜像。

## 2. 技术与运维交接

### 2.1 运行架构

推荐部署形态为 Windows Server + Hyper-V Ubuntu 虚拟机 + Docker Compose。应用由前端 Nginx、Frappe 后端、WebSocket、短/长队列、调度器、Redis 和 MariaDB 组成。历史现场资料中的示例站点为 `aki_test.localhost`、Web 端口为 `8300`；仓库 `pwd.yml` 的演示环境使用 `8080`。生产地址、端口、站点名必须填入交接台账，不能照抄示例。

### 2.2 必须移交的资料

| 类别 | 交接内容 | 验收方式 |
|---|---|---|
| 主机 | Windows/Ubuntu 地址、主机名、管理员、SSH 端口 | 接手人独立登录 |
| Docker | 项目目录、Compose 文件、镜像来源、容器清单 | `docker compose ps` 正常 |
| 站点 | 站点名、访问地址、公司、时区、默认语言 | 登录并打开首页 |
| 应用 | 已安装应用、版本/提交号、定制应用源码或镜像 | `list-apps` 与清单一致 |
| 数据库 | MariaDB 库名、账号保管方式、备份位置 | 只读连接检查 |
| 密钥 | `encryption_key`、外部接口密钥、邮箱凭据 | 密钥库交接，不写入本文 |
| 文件 | public/private files、共享盘路径、图纸根目录 | 抽查公开与私有附件 |
| 运维 | 启停、迁移、日志、备份、恢复、监控方法 | 接手人完成一次演练 |
| 账号 | 系统管理员、应急账号、服务账号、责任人 | 改密并验证最小权限 |

严禁把仓库示例中的 `admin` 密码用于生产。站点配置和数据库备份中可能含密钥或个人信息，应限制访问并加密保存。

### 2.3 日常运维命令

以下命令在实际 Compose 项目目录执行，容器名和站点名按现场替换：

```bash
docker compose ps
docker compose logs --tail=200
docker compose exec backend bench --site <站点名> list-apps
docker compose exec backend bench --site <站点名> doctor
docker compose exec backend bench --site <站点名> clear-cache
```

应用升级的一般顺序为：冻结写入 → 完整备份 → 核对版本与回退点 → 更新程序/镜像 → `migrate` → 清缓存 → 启动服务 → 技术冒烟 → 业务回归。不得在无可恢复备份时恢复数据库或执行迁移。

### 2.4 备份和恢复

每次完整备份至少包含数据库、公共文件、私有文件、站点配置中必要密钥、Compose 配置、定制应用版本及校验值。建议数据库每日备份、文件每日增量/定期全量，保留周期由公司确定，并至少保留一份异机副本。

恢复演练顺序：建立隔离环境 → 校验备份哈希 → 恢复数据库 → 恢复 public/private files → 恢复正确 `encryption_key` → 执行迁移和清缓存 → 核对应用版本 → 抽查附件和核心单据。每季度至少演练一次，并记录恢复耗时和数据恢复点。

### 2.5 上线后健康检查

1. 容器无反复重启，队列、调度器、Redis、数据库正常。
2. 登录、列表、保存草稿、提交、打印和附件上传下载正常。
3. 邮件、共享盘、OCR、CRM/MES 等已启用接口分别测试；目录存在不代表接口可用。
4. 用销售、采购、质量、仓库、生产、财务账号各完成一条最小业务链。
5. 检查错误日志、后台任务失败、磁盘空间、备份结果和证书有效期。

## 3. 业务控制总则

系统中必须区分：保存不等于提交；提交不等于审批；到货不等于合格入库；对账不等于形成应收应付；建立收付款单不等于银行已收付；报价成本不等于实际完工成本。

每次岗位交接至少记录公司、往来单位、来源单号、本次数量/金额、累计和剩余、当前状态、附件、差异、下一责任人及完成期限。已提交单据原则上通过取消、修订、红字或冲销处理，不直接覆盖历史事实。

## 4. 核心业务流程

### 4.1 阶梯报价

适用场景包括供应商采购阶梯价和产品批量成本报价，两者口径不同。

```text
询价/成本资料准备 → 建立有效价格规则或报价批量
→ 校验供应商/物料/单位/币种/税价/有效期/数量
→ 系统试算档位 → 采购或报价负责人复核
→ 生成采购订单或客户报价版本 → 提交/审批 → 保留历史版本
```

**采购阶梯价操作：**

1. 采购维护供应商报价及物料供应商明细，填写适用供应商、物料、采购单位、币种、含税口径、起止日期和数量档位。
2. 将价格规则关联到对应物料的供应商行；只新建规则但未关联时，订单可能无法读取。
3. 建采购订单时，系统按同一采购订单内“相同物料”的适用数量试算。跨仓明细可保留，但是否汇总取档以现场已启用规则为准。
4. 采购核对命中档位、最低订量、单位换算、税费、运费和交期后提交审批。不同物料、不同单位或不同规则不得为凑档混算。
5. 数量、日期、供应商或单位变化后必须重新取价；已确认历史订单不直接覆盖价格。

**产品批量报价：**在产品成本报价单中设置 50/100/200 等批量，刷新来源并分别核算材料、制造和分摊成本，再按毛利率/成本占比生成各批量报价。低于最小接单量的档位只能作为估算，未经审批不能对客承诺。

**控制点：**币种、单位、有效期、含税/未税和数量边界必须同时满足；系统取价不替代质量、交期和供应商选择审批。验收时至少测试边界数量、过期规则、单位换算、跨仓同物料、数量修改和无匹配规则。

### 4.2 物料折旧、资产折旧与库存减值

普通库存物料不应按固定资产折旧。先由财务判断业务实质：可长期使用并资本化的设备/工装走固定资产；用于销售或生产的存货若发生跌价、呆滞，走库存减值。

**A. 固定资产折旧：**

```text
采购/验收 → 采购发票及资本化确认 → 建立 Asset 资产卡片
→ 资产类别/原值/可用日期/残值/折旧方法和期间
→ 生成折旧计划 → 财务复核 → 定期折旧记账
→ 调拨/维修/价值调整 → 处置 → 归档
```

1. 资产管理员建立资产卡片，关联采购来源，维护类别、位置、部门、保管人、原值和可用日期。
2. 财务按政策设置折旧方法、年限/期数、频率和残值，生成折旧计划。每月折旧额应由计划计算，不把手工导入的“每月折旧金额”当作正式记账依据。
3. 财务在每期记账前核对在用状态、期间和科目，提交折旧分录；累计折旧属于非现金项目，不应错误映射为现金流。
4. 调拨、停用、价值调整、资本化和处置走各自正式单据，不能直接改原值或累计折旧清零。

**B. 库存呆滞/跌价减值：**

```text
库存账龄/可变现净值分析 → 形成减值建议 → 仓库与业务复核数量
→ 财务审批减值金额 → 会计凭证确认减值
→ 后续销售/领用/报废复核 → 满足条件时转回 → 留存依据
```

库存数量仍由收发存单据管理；减值不等于报废、出库或改变实物数量。减值与转回的科目和上限由财务确定，不得将历史估值率直接覆盖为“折旧”。

**当前状态提示：**现有用户手册未把固定资产确认成 aki_erp 日常必用模块，库存减值资料也包含方案性质内容。两条路径均须先由财务和管理员确认目标站点已启用、科目已配置、权限与测试通过。

### 4.3 从销售订单到财务

```text
客户需求/报价 → 销售订单审批
→ 库存满足：销售送货
→ 库存不足：采购补货或工单生产、质检、成品入库
→ 分批交付/客户签收 → 客户对账
→ 销售结算/销售发票形成应收 → 真实收款
→ Payment Entry 分配核销 → 应收余额/总账/税票核对
```

1. 销售核对客户、产品、数量、价格、税率、交期、仓库、付款条件和客户 PO，保存后交审批并提交。
2. 仓库核对可分配库存；不足部分交采购或生产。系统生成的送货/工单草稿不是已发货或已开工，重复生成前先查关联记录。
3. 仓库按实际批次创建并提交送货单，核对批次/序列号、库存流水、累计交付和客户签收。
4. 销售按客户及期间整理送货、退货和差异；财务选择“送货依据”或“往来账依据”创建客户对账单。两种口径不得混用。
5. 需要销售结算时，核对剩余可结算数量后生成正式应收；该动作可能提交结算并创建销售发票，不能用于试点。
6. 财务复核销售发票的订单/送货来源、税额和应收；税务发票登记与系统应收分别核对。
7. 实际到账后建立收款类型的 Payment Entry，分配到对应销售发票并提交。检查未核销余额、总账和银行凭据。

退货须关联原送货，由仓库办理实物、财务办理红字/退款/核销调整；不能只减小原订单数量。验收至少覆盖现货、生产补货、分批送货、部分收款、退货和重复结算拦截。

### 4.4 BOM 成本报价

```text
有效物料/BOM/图纸/供应商价格/工时费率/项目投入
→ 新建 Product Cost Quotation
→ 选择产品、BOM 版本、项目/参考工单和报价批量
→ 读取来源并预览 → 选择并应用成本分组
→ 核对材料+制造+项目/研发摊销 → 设置税率和定价方式
→ 核算各批量报价 → 内部审批 → 导出客户版 → 复制新版本
```

1. 工程确认 BOM 已提交、有效，基准产量、材料单位、损耗、下层 BOM 和图纸版本正确。
2. 采购维护有效供应商价格；生产/财务维护可用工时和费率；项目负责人确认实际投入、预计剩余投入和摊销数量。
3. 报价人员选择产品、BOM、客户、公司、币种及批量，按需关联项目和参考工单，执行“读取来源/刷新预览”。刷新可能重建来源明细，应先保留必要的人工依据。
4. 逐项检查材料取价、税价口径、单位换算、制造成本和项目分摊。缺价必须标识和补依据，不能默认为零。
5. 选择目标毛利率或成本占售价比例，按系统规则计算；毛利率 40% 不等于成本加价 40%。
6. 内部版保留成本、毛利和依据；客户版只展示授权的产品、数量、币种、价格、税费、有效期和商务条款。
7. 成本、规格或批量变化时复制为新版本，历史对客版本不得覆盖。

BOM 估算成本、参考工单成本和实际完工成本是三种口径；不得把参考工单实际成本与未来材料/制造成本重复叠加。

### 4.5 对账

对账分客户对账和供应商对账；业务确认、形成应收应付、收付款是不同节点。

**客户对账：**销售/财务选择客户、公司和期间，按业务目的选择送货或往来账口径，加载明细，核对退货、期初、期间发生、收款和期末余额，处理差异并取得客户确认。需要时由已确认对账范围创建销售结算/销售发票；实际收款另建 Payment Entry 核销。

**供应商对账：**采购在 Purchase Follow Up 选择公司、供应商、币种和期间，加载已提交的合格收货及退货范围，核对数量、单价、税额、供应商账单和差异，上传确认依据后提交。财务从待接收入口接收，关联采购发票形成正式应付，再按审批和真实银行付款建立 Payment Entry 并核销。

**关键规则：**

- 对账单不改库存、不记账、不直接付款。
- 同一来源行分批对账时，累计数量/金额不能超过可对账余量。
- 常规库存采购以合格收货并扣除退货为依据；服务类采购须使用明确的例外流程。
- 已提交、财务已接收、已开票、部分付款、已结清必须分别展示和核对。
- 取消发票/付款或发生退货后应重新计算状态，不能依赖手工改“已结清”。

### 4.6 权限表单

权限申请使用“用户新增申请单/权限变更申请单/账号状态变更单”的管理流程；若站点没有电子申请 DocType，可使用公司批准的 OA 表单，但审批结果和执行记录必须回填。

```text
申请人填表 → 直属主管/数据负责人审批 → 财务或内控复核高风险权限
→ 系统管理员配置角色、用户权限、工作流/共享
→ 使用测试账号做正反向验证 → 申请人确认 → 留存变更前后清单
→ 到期回收/定期复核
```

权限变更表至少包含：用户、员工号、部门/岗位、申请类型、现有角色、新增/取消角色、公司/部门/仓库/项目范围、查看/新建/编辑/提交/取消/审批/导出权限、生效和失效时间、原因、申请人、审批人、执行人、验证结果。

| 岗位 | 核心可用范围 | 默认不应开放 |
|---|---|---|
| 销售 | 客户、授权销售产品、本人/授权销售单据、交付跟踪 | 采购价、BOM 成本、全量财务数据 |
| 采购 | 供应商、采购价格、采购申请/订单、收货跟踪、采购对账 | 销售毛利、付款提交、全量总账 |
| 工程 | 物料工程资料、BOM、图纸和版本 | 收付款、总账、非必要采购金额 |
| 生产 | 工单、作业卡、领料、报工及必要 BOM/图纸 | 客户价格、采购敏感价格、财务成本 |
| 质量 | 待检来源、质量检验、不合格处置所需数据 | 全量库存/财务数据、价格修改 |
| 仓库 | 收发存、调拨、盘点及授权仓库 | 价格审批、会计凭证、未授权仓库 |
| 财务 | 应收应付、发票、收付款、对账、凭证和报表 | 工程版本修改、质量判定 |
| 系统管理员 | 配置和故障处理 | 代替业务审批、使用共享账号操作业务 |

角色控制功能，用户权限控制公司、部门、仓库、项目等数据范围，工作流控制审批动作。隐藏按钮或菜单不等于安全隔离；还要检查列表、报表、导出、打印、API 和直接 URL。申请人不得审批本人权限，临时权限必须有失效日期，离职优先禁用并撤销会话/API 密钥而非删除历史账号。

### 4.7 图纸关联

```text
工程提出/接收图纸 → 建 Engineering Drawing 或受控共享盘文件
→ 维护图纸号、版本、状态、生效日期和文件校验信息
→ 关联 Item → 关联/确认 BOM 版本
→ 采购订单、工单、质检引用并形成版本快照
→ 变更审批 → 新版本生效 → 旧版本作废但保留追溯
```

1. 工程先建立物料，维护工程图号和修订版；图号应唯一或具备明确的物料映射规则。
2. 上传受控附件或填写批准的共享盘路径。共享盘需统一根目录、访问权限、备份和文件命名，普通用户不能任意覆盖已发布文件。
3. 在 BOM 中关联正确图纸，核对型号、版本、生效信息、材料结构和下层 BOM，提交并设置适用/默认版本。
4. 采购下单、生产开工和质检前核对实际业务单据引用的 BOM/图纸版本。仅修改物料或默认 BOM 不会自动更新历史工单。
5. 变更时建立新图纸/新 BOM 版本，填写变更原因和生效安排；评估在途采购、在制品和库存处理后通知采购、生产、质量。
6. 作废版本保持只读可追溯，历史业务仍指向原版本。严禁用同名文件覆盖旧版而不变更版本号。

验收应抽查：从物料能打开图纸，从 BOM 能定位图纸，从采购订单/工单/质检能确认实际版本，权限不足者不能下载受限图纸，历史单据不随新版发布而变化。

### 4.8 采购和生产质检

**采购质检：**

```text
采购订单 → 本批到货 → 收料通知
→ Quality Inspection（检测总数=合格+不合格）
→ 合格数量创建采购入库并提交 → 库存可用
→ 不合格隔离 → 退货/补货/让步接收审批
→ 对账按合格收货和退货净额 → 采购发票/付款
```

仓库只登记本批实际到货；质量人员填写检验项目、总数、合格数、不合格数、缺陷和结论。只有已提交、来源正确且未被重复使用的合格数量才能创建采购入库。不合格品须隔离，退货、补货、折让或让步接收分别保留批准依据；质检结论不等于实物已退或财务已扣款。

**生产质检：**

```text
销售/生产计划 → Work Order 固化 BOM 版本
→ 领料 → Job Card/工序报工 → 本批完工待检
→ 成品质检 → 合格数量成品入库
→ 不合格返工或报废 → 返工重新报工、重新质检
→ 工单完工 → 实际成本归集/结算 → 销售交付
```

生产开工前核对产品、BOM/图纸版本、计划数量、材料和工序。末道工序报工后按本批次建立质检；检验数量不得超过本批待检量，合格和不合格之和必须等于检测总数。成品入库只能消耗尚未入库的合格数量，并校验工单、物料、批次和来源。不合格数量不得进入正常成品仓；返工后建立新的报工和质检记录，不覆盖原历史。

**共同控制点：**支持分批检验和分批入库，但累计占用不可超量；已有草稿时优先打开原草稿；取消下游单据应按入库 → 质检 → 报工/收料的反向依赖处理。生产完成、成品已入库和成本已结算必须分别核对。
