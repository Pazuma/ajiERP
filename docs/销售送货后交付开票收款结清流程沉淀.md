# 销售送货后交付、开票、收款与结清流程沉淀

## 1. 适用范围

本文记录销售订单创建销售送货单之后的完整业务闭环。本次只做流程沉淀，不修改代码、不自动提交单据、不自动创建发票或收款。

适用主流程：

```text
销售订单
  -> 销售送货单草稿
  -> 提交销售送货单
  -> 销售订单交付数量更新
  -> 创建并提交销售发票
  -> 创建并提交收款单
  -> 发票未结清金额为 0
  -> 发票已结清，订单完成
```

## 2. 关键结论

1. 创建销售送货单草稿不会更新销售订单的已交付数量。
2. 提交销售送货单后，系统才更新对应销售订单明细的 `delivered_qty` 和订单级 `per_delivered`。
3. 销售送货单提交代表货物出库，不代表货款已结清。
4. 销售发票提交代表形成应收，不代表客户已经付款。
5. 收款单提交并核销销售发票后，发票的 `outstanding_amount` 才会减少。
6. 当发票 `outstanding_amount <= 0` 时，发票状态通常变为 `Paid`。
7. ERPNext 标准销售订单 `Completed` 状态同时要求交付完成且开票完成（`per_delivered >= 100` 且 `per_billed >= 100`）；“已交货”或“交付完成”不等同于财务结清。

### 2.1 测试时看到“已完成”的判定说明

提交销售送货单后，如果界面显示“已完成”，先确认显示位置和字段：

- 销售订单标准状态：应查看 `status`、`per_delivered`、`per_billed`。仅送货完成而未开票时，标准状态通常是 `To Bill`（待开票）。
- 销售送货单状态：送货单自身的“完成”最多表示该送货单的开票数量已完成，不代表客户已经付款；界面不应把它直接解释为“已结清”。
- 客户 Akivision 的销售订单/交付报表：报表可能按 `delivered_qty >= qty` 显示“已交货/已完成”，这是履约展示口径，不是 ERPNext 标准财务完成状态。

本次测试截图显示的是销售送货单 `MAT-DN-2026-00012`，不是销售订单。标题旁的绿色“已完成”首先代表送货单状态。若该送货单确实没有单独创建销售发票，应继续核对送货单的 `per_billed`、`grand_total`、关联销售发票，以及对应销售订单的 `per_billed`；仅凭“已结算金额/待结算金额”两个展示字段，不能确认 Payment Entry 已核销。

最终应同时核对：销售订单的 `status`、`per_delivered`、`per_billed`，以及销售发票的 `outstanding_amount`。只有发票余额为 0，才能确认货款结清。

## 3. 单据与状态关系

| 单据 | 草稿状态的作用 | 提交后的业务影响 | 结清判断 |
|---|---|---|---|
| Sales Order | 记录客户、物料、订单数量和价格 | 允许创建送货、发票等后续单据 | 由交付和开票进度决定订单状态 |
| Delivery Note | 可修改仓库、数量、批次和序列号 | 扣减库存，更新订单已交付数量 | 不负责判断货款是否结清 |
| Sales Invoice | 核对客户、税费、价格和应收金额 | 形成应收账款和收入凭证 | `outstanding_amount=0` |
| Payment Entry | 选择收款账户和付款方式，分配核销发票 | 形成银行/现金与应收的会计分录 | 收款核销金额覆盖发票未结清金额 |

## 4. 推荐的傻瓜式操作流程

### 4.1 第一步：创建销售送货单

在已提交且仍有未交付数量的销售订单中：

1. 点击“创建 -> 一键创建销售送货单”。
2. 系统生成销售送货单草稿。
3. 核对客户、仓库、物料、数量、单位、批次/序列号。
4. 确认本次数量等于实际出库数量。

如果订单已经有已提交送货单，系统应只生成剩余数量；如果已有未提交送货单，也应先检查草稿，避免同一订单明细重复出库。

### 4.2 第二步：提交销售送货单

核对无误后点击“提交”。提交后检查：

- 销售送货单 `docstatus=1`；
- 库存数量已经扣减；
- 送货明细包含正确的 `against_sales_order` 和 `so_detail`；
- 销售订单明细 `delivered_qty` 增加本次提交数量；
- 销售订单 `per_delivered` 按全部已提交送货单重新计算；
- 订单状态变为部分交付或已交付相关状态。

送货单提交失败时，先处理库存、批次、序列号、仓库或超量出库校验，不要直接增加订单数量或放宽超量参数。

### 4.3 第三步：创建销售发票

销售送货单提交后，根据业务开票节点选择一种方式：

```text
方式 A：从销售送货单创建销售发票
方式 B：从销售订单创建销售发票
```

推荐优先从已提交销售送货单创建发票，因为可以直接沿用实际出库数量和送货关联；如果业务允许先开票后发货，也可以按公司财务制度从销售订单开票。

创建发票草稿后核对：

- 客户和公司；
- 发票日期、付款条款、到期日；
- 物料和数量；
- 单价、折扣、税费；
- `against_sales_order`、`dn_detail` 或送货关联；
- 总额、已收金额和未结清金额。

确认无误后提交销售发票。提交发票会形成应收账款，但不会自动代表客户付款。

### 4.4 第四步：登记并提交收款

收到客户款项后：

1. 创建 Payment Entry，付款类型选择 `Receive`。
2. 选择客户、公司、收款账户和付款方式。
3. 在 References 中选择对应的 Sales Invoice。
4. 核对分配金额；部分收款只填写实际到账金额。
5. 提交 Payment Entry。

提交后检查：

- Payment Entry `docstatus=1`；
- Reference 指向正确的销售发票；
- 分配金额没有超过发票未结清金额；
- 销售发票 `outstanding_amount` 减少；
- 部分收款时发票状态为 `Partly Paid`；
- 足额收款时发票状态为 `Paid`。

### 4.5 订金、部分收款与尾款

收到订金时，收款可能只针对销售订单形成预收，也可能暂不分配到销售发票。此时应区分：

```text
订金已收但未核销发票 -> 客户有预收款，发票仍可能是 Unpaid
订金已核销发票     -> 发票 outstanding_amount 按核销金额减少
尾款未收           -> 发票仍为 Partly Paid 或 Unpaid
尾款足额收齐       -> outstanding_amount = 0，发票为 Paid
```

判断规则：

1. 只看 Payment Entry 的总收款金额，不能判断尾款是否结清。
2. 必须查看 Payment Entry 的 `references.allocated_amount` 是否实际分配到对应 Sales Invoice。
3. 未分配的收款属于客户预收/未核销款，不应直接冲减发票 `outstanding_amount`。
4. 销售订单可辅助查看 `advance_paid`、`advance_payment_status`，但最终结清仍以销售发票的 `outstanding_amount` 和核销记录为准。

### 4.6 第五步：确认结清

结清不是只看销售订单状态，应同时检查三层结果：

```text
交付层：Sales Order Item.delivered_qty >= Sales Order Item.qty
开票层：应开票数量/金额已完成，Sales Invoice 已提交
收款层：Sales Invoice.outstanding_amount <= 0，状态为 Paid；订金或未核销收款不计入发票结清
```

建议以销售发票的 `outstanding_amount` 作为财务结清事实，以 Payment Entry Reference 作为收款核销事实，以 Sales Order/Delivery Note 作为业务履约追溯事实。

## 5. 状态变化示例

以订单数量 20 为例：

| 操作 | 已交付数量 | 订单交付比例 | 发票状态 | 订单可能状态 |
|---|---:|---:|---|---|
| 仅创建送货草稿 20 | 0 | 0% | 无 | 待交付/待开票 |
| 提交送货单 20 | 20 | 100% | 无 | 待开票 |
| 提交销售发票 | 20 | 100% | Unpaid | 待收款 |
| 收到订金 8，暂未核销发票 | 20 | 100% | Unpaid | 已收订金，待开票/核销 |
| 将订金 8 核销到发票 | 20 | 100% | Partly Paid | 尾款未收 |
| 再收款并核销 12 | 20 | 100% | Paid | 已完成或已结清 |

如果分两次交付：

| 操作 | 已交付数量 | 订单交付比例 |
|---|---:|---:|
| 第一次送货单提交 | 3 | 15% |
| 第二次送货单提交 | 20 | 100% |

第二次创建送货单时，数量只能是剩余 17，不能再次填写 20 或 50。

## 6. 数据流

```text
Sales Order
  -> Sales Order Item.qty
  -> 创建 Delivery Note 草稿
  -> Delivery Note Item.against_sales_order / so_detail
  -> 提交 Delivery Note
  -> Delivery Note 状态更新库存
  -> Sales Order Item.delivered_qty
  -> Sales Order.per_delivered
  -> 创建 Sales Invoice 草稿
  -> 提交 Sales Invoice
  -> 应收账款 + outstanding_amount
  -> 创建 Payment Entry（订金可先不分配发票）
  -> Payment Entry Reference.reference_name = Sales Invoice（核销时关联）
  -> 提交 Payment Entry
  -> 未分配订金进入预收；已分配金额减少 outstanding_amount
  -> outstanding_amount <= 0
  -> Sales Invoice.status = Paid
```

## 7. 依赖清单

| 依赖 | 要求 |
|---|---|
| 销售订单 | 已提交，客户、公司、物料、数量、价格和仓库有效 |
| 库存 | 送货仓库有足够可用库存，批次/序列号可用且未过期 |
| 送货权限 | 用户有 Delivery Note 创建、写入和提交权限 |
| 发票权限 | 用户有 Sales Invoice 创建、写入和提交权限 |
| 收款权限 | 用户有 Payment Entry 创建、写入和提交权限 |
| 会计设置 | 公司、应收账户、收入账户、税费账户、收款账户有效 |
| 客户主数据 | 客户、付款条款、信用额度和默认账户配置正确 |
| Payment Entry Reference | 正确关联 Sales Invoice，分配金额不超过未结清金额 |
| 订金/预收配置 | 预收账户、`advance_paid` 和 `advance_payment_status` 口径明确 |
| 期间设置 | 送货、发票和收款日期处于可过账会计期间 |
| 汇率 | 外币订单、发票和收款使用正确汇率，避免汇兑差异异常 |

## 8. 风险点与处理建议

| 风险点 | 表现 | 处理建议 |
|---|---|---|
| 送货草稿未提交 | 订单已交付数量仍未变化 | 提交送货单后再检查 `delivered_qty` |
| 重复创建送货单 | 提示数量超出订单允许量 | 检查已提交和草稿送货单，不重复生成整单 |
| 送货数量填写订单总量 | 第二次送货失败 | 按“订单数量 - 已交付数量”填写 |
| 送货单已提交但未开票 | 订单已交付但仍有应收流程 | 从送货单创建销售发票 |
| 发票已提交但未收款 | 发票状态 Unpaid/Overdue | 创建 Receive 类型 Payment Entry |
| 部分收款误判为结清 | 发票仍有 outstanding_amount | 以 `outstanding_amount` 为准，不以 Payment Entry 数量条数判断 |
| 订金误判为尾款结清 | Payment Entry 已提交但未关联发票，或发票仍有余额 | 区分 `advance_paid`、未分配金额和发票 `outstanding_amount` |
| 收款未核销发票 | 总账有收款但发票未结清 | 检查 Payment Entry References |
| 收款金额超过发票余额 | 提交收款时报超额 | 调整分配金额，超额款按预收/其他业务规则处理 |
| 多发票收款 | 一笔收款对应多张发票 | 在 Payment Entry 中分配每张发票金额并复核合计 |
| 发票和送货数量不一致 | 订单交付和开票进度不同 | 明确按送货开票还是按订单开票，保留来源关联 |
| 退货/红字发票 | 已交付或已收款数量被冲销 | 使用标准退货、贷项凭证和反向收款流程，不直接修改数量 |
| 跨期收款 | 账龄和期间报表异常 | 使用实际到账日和会计过账日，按财务口径统计 |
| 汇兑差异 | 外币发票结清后仍有差额 | 按汇兑损益和核销差异规则处理 |

## 9. 复测场景清单

### 9.1 基础全流程

1. 创建销售订单 20。
2. 创建并提交销售送货单 20。
3. 确认 `delivered_qty=20`、`per_delivered=100`。
4. 创建并提交销售发票。
5. 创建 Receive 类型 Payment Entry，收款 20 对应发票。
6. 确认发票状态 `Paid`、`outstanding_amount=0`。

### 9.2 分批交付与分批收款

1. 订单数量 20，第一次送货 3。
2. 第二次送货只能生成剩余 17。
3. 发票分两次收款，例如 8 和 12。
4. 第一次收款后发票应为 `Partly Paid`。
5. 第二次收款后发票应为 `Paid`。

### 9.3 重复送货保护

1. 创建一张送货草稿但不提交。
2. 再次点击一键创建销售送货单。
3. 新草稿数量应扣除原草稿数量。
4. 剩余量为 0 时应阻止生成。
5. 提交其中一张后，再次创建只能生成实际剩余数量。

### 9.4 异常与冲销

- 库存不足、批次过期、序列号不在仓库；
- 发票部分开票、部分收款；
- Payment Entry 取消后发票余额恢复；
- Delivery Note 退货后订单交付数量冲减；
- Sales Invoice 贷项凭证后应收余额变化；
- 多张发票由一笔收款分配；
- 外币订单和汇兑差异；
- 送货、发票、收款跨会计期间；
- 无提交权限用户不能越权过账。

## 10. 优化建议：把“完成”拆成三种状态

当前页面将系统单据状态“已完成”和结算金额放在同一视觉区域，容易让用户误以为“货已出库 = 已开票 = 已收款”。建议后续按以下方式优化展示，不改变 ERPNext 的底层过账规则：

| 展示层 | 建议状态 | 判定字段 | 用户含义 |
|---|---|---|---|
| 出库状态 | 未出库 / 部分出库 / 已出库 | `delivered_qty`、`per_delivered` | 货物是否已经实际出库 |
| 开票状态 | 未开票 / 部分开票 / 已开票 | `per_billed`、关联 Sales Invoice | 是否已经形成应收 |
| 收款状态 | 未收款 / 已收订金 / 部分收款 / 尾款未收 / 已结清 | `outstanding_amount`、`advance_paid`、Payment Entry Reference | 客户是否已经付款及是否已核销 |

实施时建议：

1. 保留 ERPNext 原生 `status`，但在页面上标注为“系统状态”，不要单独用绿色“已完成”表达业务结清。
2. 在标题或摘要区域并列显示“出库状态、开票状态、收款状态”，优先显示下一步动作，例如“待开票”或“待收款”。
3. 没有关联销售发票时，结算区域显示“未开票”；如果已收到订金，另显示“已收订金（未核销）”，不要用“待结算 CNY 0.00”造成已结清错觉。
4. 有发票但 `outstanding_amount > 0` 时，按实际情况显示“已收订金/部分收款/尾款未收”；只有余额为 0 且发票状态为 `Paid` 时才显示“已结清”。
5. “销售结算模式：直接确认应收”应增加说明：它只代表应收确认口径，不代表 Payment Entry 已提交或尾款已收齐。

推荐的页面文案示例：

```text
出库状态：已出库
开票状态：已开票
收款状态：已收订金，尾款未收
下一步：核销尾款
```

这样即使送货单标题仍显示 ERPNext 原生“已完成”，用户也能立即看出订单目前只是完成了出库或开票环节，尚未完成收款。

## 11. 操作判断口诀

```text
草稿不算交付，提交送货才扣库存；
送货完成不等于收款，发票提交才形成应收；
收款必须核销发票，余额为零才算结清；
重复出库先查历史单据，数量按剩余量处理。
```
