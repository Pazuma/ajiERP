# 销售订单自动履约未实现项优化方案

## 1. 文档目的与范围

本文基于《销售订单提交自动生成拣货单与生产工单优化方案》的已实现代码，沉淀后续七项优化方案。本阶段只做设计，不修改业务代码、不新增数据库字段、不改变现有接口行为。

待优化项：生产模块红点、销售订单人工重算、取消/数量变更联动、公司级配置、无 BOM 转采购需求、库存变化后的二次规划，以及库存充足时生成草稿 Delivery Note。

## 2. 设计原则

- 小增量：每项使用独立函数、事件分支或后台任务，保留现有 Pick List/Work Order 链路。
- 兼容：不修改 ERPNext 核心文件，不覆盖已有白名单接口；旧接口继续可用。
- 草稿优先：自动生成的 Delivery Note、Pick List、Work Order、Material Request 均保持草稿。
- 幂等与可追溯：以 `sales_order + sales_order_item` 汇总已有未取消单据，重复执行只补差额；所有结果写入时间线和日志。
- 人工可控：数量减少、取消、库存波动不得自动删除或提交人工已处理单据。
- 信息填充边界：系统只自动填写关联订单、客户、业务人员和数量，并据此生成对应草稿；草稿的最终提交始终由人工完成。

## 2.1 草稿信息填写边界

系统自动填写以下基础信息：

- 关联销售订单及销售订单明细；
- 客户；
- 业务人员；
- 物料和库存/生产数量；
- 因上述关联所需的标准关联字段。

系统根据库存结果自动生成对应的草稿 Pick List、Delivery Note 或 Work Order，但不自动提交任何草稿。仓库人员或生产人员打开草稿后，按实际业务需要核对、补充并人工点击提交。

后续涉及的仓库调整、批次序列号、排产安排或其他业务判断，均不作为本次自动生成的前置要求，由人工在草稿处理中完成。

## 3. 推荐分阶段实施

### 阶段一：送货单分支与人工重算

新增配置读取和策略参数：`fulfilment_document_type = Pick List | Delivery Note`，默认保持 `Pick List`，仅配置为 Delivery Note 时走新分支。

拟新增/修改代码：

| 文件 | 改动 |
|---|---|
| `client_akivision/utils/sales_order_auto_fulfilment.py` | 新增 `build_draft_delivery_note()`、`recalculate_sales_order_fulfilment()`；复用 `make_mapped_doc`/标准 Delivery Note 映射，保存草稿；保留原 `build_draft_pick_list()` |
| `client_akivision/hooks.py` | 保留现有 `on_submit`，不替换；如需权限控制，仅新增 whitelisted 人工重算入口映射 |
| `client_akivision/public/js/sales_order_delivery.js` | 在已提交订单增加“重新计算备货计划”按钮，调用新增接口并显示结果弹窗；不在前端计算库存 |
| `client_akivision/utils/test_sales_order_auto_fulfilment.py` | 增加 Delivery Note、重算幂等、草稿状态测试 |

调用链路：

```text
已提交 Sales Order → 人工点击重新计算 → 新增后台接口 → 加订单锁/幂等汇总
→ 按配置创建草稿 Delivery Note 或原 Pick List → 缺口创建 Work Order
→ 写时间线、Notification Log、realtime 弹窗
```

预期效果：库存足够时可按配置得到一张草稿送货单；默认配置下现有拣货单行为完全不变。人工重算可补建差额，重复点击不重复建单。

### 阶段二：公司级开关与无 BOM 采购需求

拟新增配置（优先使用 Company 自定义字段或 Single DocType，避免硬编码）：

- 是否启用自动履约；
- 履约单据类型（Pick List/Delivery Note）；
- 是否自动创建草稿 Work Order；
- 无 BOM 缺口是否创建草稿 Material Request；
- 默认成品仓库及仓库优先级。

拟新增/修改文件：

| 文件 | 改动 |
|---|---|
| `client_akivision/utils/sales_order_auto_fulfilment.py` | 新增 `get_company_fulfilment_config()`、`create_draft_material_request()`；无 BOM 分支按配置创建采购/制造用途 Material Request |
| `client_akivision/patches/...` 或 Custom Field 配置 | 新增 Company/Single DocType 字段及默认值，默认关闭新策略，保证升级安全 |
| `client_akivision/hooks.py` | 仅在现有任务入口增加配置判断，不改变 hook 名称 |
| 测试文件 | 覆盖开关关闭、按公司隔离、无 BOM 采购草稿 |

调用链路：`on_submit → 读取公司配置 → 关闭则记录跳过 → 开启则执行 Delivery/Pick → BOM 缺口建 Work Order；无 BOM 按开关建 Material Request 草稿或仅提示`。

预期效果：不同公司可独立启停和选择单据类型；无 BOM 缺口能够形成可供采购人员处理的草稿需求，但不会自动下采购订单。

### 阶段三：取消、数量变更与库存二次规划

拟新增事件分支（不改原校验）：

| 文件 | 改动 |
|---|---|
| `sales_order_auto_fulfilment.py` | 新增 `enqueue_recalculate_on_update()`、`handle_cancel_notice()`、`replan_after_stock_change()`；比较变更前后数量，锁定订单后只补差额 |
| `hooks.py` | Sales Order 新增 `on_update_after_submit`/`on_cancel` 分支；库存事件仅监听相关物料/仓库并异步入队 |
| `client_akivision/public/js/sales_order_delivery.js` | 增加“有待处理变更”提示和人工确认入口，不自动删除下游单据 |
| 测试文件 | 覆盖数量增加/减少、取消、有已提交下游单据、库存变化去重 |

处理规则：数量增加只补建；数量减少或订单取消只生成提醒清单，由仓库/生产人员人工调整；已提交下游单据不回写。库存变化采用短时去重队列，不因每次库存流水无限建单。

预期效果：订单和库存变化可被发现并给出可操作提醒，同时避免误删、重复建单和库存波动风暴。

### 阶段四：生产模块红点

拟新增：`client_akivision/public/js/sidebar_icons.js`（或独立 `production_badge.js`）订阅 realtime；后端新增只读统计接口 `get_pending_production_draft_count()`，按用户权限统计未处理草稿 Work Order/Material Request。

调用链路：`创建新草稿 → publish_realtime → 生产模块刷新徽标 → 点击模块进入待处理列表 → 阅读/处理后重新统计`。

预期效果：生产模块图标显示红色数量徽标；数量来源明确、按权限过滤，处理后自动归零。首期仍保留标准通知铃铛作为兜底。

## 4. 受影响模块

销售订单、销售拣货单、销售送货单、生产工单、物料需求、库存/Bin、BOM、公司配置、系统通知、Desk 侧栏、后台队列与权限。ERPNext 核心、库存 Ledger、既有送货接口和生产计划接口均不直接修改。

## 5. 验收标准与预期总效果

1. 默认配置和旧订单行为不变；新配置可选择 Delivery Note。
2. 所有自动单据 `docstatus = 0`，正确关联销售订单及明细。
3. 重复提交任务、人工重算、库存事件均不产生重复数量。
4. 有库存生成草稿 Delivery/Pick；缺口按 BOM 生成 Work Order；无 BOM 按配置提示或生成 Material Request。
5. 提交、完成、异常均有中文弹窗/时间线记录；生产人员同时收到铃铛通知和模块红点（阶段四）。
6. 取消或数量减少不自动删除人工单据；数量增加仅补差额。
7. 原有“一键创建销售送货单”、出货明细、项目进度及其他模块点击功能无回归。

## 6. 实施顺序建议

先实施阶段一并灰度验证 Delivery Note 与人工重算，再实施公司配置和无 BOM 采购需求，最后接入取消/库存二次规划及红点。每阶段均先补测试和日志，再发布缓存与队列配置。

## 7. 本次确认的核心业务口径

本次后续开发以以下规则为准：

```text
一张销售订单逐条明细计算库存
  ├─ 成品库存足够：纳入一张草稿 Delivery Note
  └─ 成品库存不足：该成品单独创建一张草稿 Work Order
```

### 7.1 单据数量规则

- 一张销售订单中，库存充足的多个成品原则上合并到同一张草稿 Delivery Note；
- 一张销售订单中，每一个缺货成品对应一张独立草稿 Work Order；
- 同一成品在同一销售订单存在多条明细时，按销售订单明细分别追溯，除非标准业务规则明确允许合并；
- 生产工单数量为该销售订单明细的缺口数量，不是整张销售订单总数量；
- 所有下游草稿均关联原销售订单和对应销售订单明细。

### 7.2 示例

销售订单明细：

```text
成品 A：需求 10，库存 4，缺口 6
成品 B：需求 8，库存 0，缺口 8
成品 C：需求 5，库存 5，缺口 0
```

预期生成：

```text
草稿 Delivery Note：
  成品 C，数量 5

草稿 Work Order 1：
  成品 A，数量 6

草稿 Work Order 2：
  成品 B，数量 8
```

其中 Delivery Note、Work Order 都只生成草稿，不能由自动任务执行提交。系统自动填写关联销售订单、销售订单明细、客户、业务人员、物料和数量；人工负责核对、补充必要信息并最终提交。

## 8. 按核心口径拟修改的代码

本节只描述实施计划，本次文档沉淀不执行代码修改。

### 8.1 后端编排

文件：`client_akivision/utils/sales_order_auto_fulfilment.py`

拟新增或调整：

| 函数/分支 | 作用 |
|---|---|
| `create_draft_fulfilment_documents()` | 保留现有异步入口，按销售订单明细逐条计算库存和缺口 |
| `build_draft_delivery_note()` | 将库存充足的明细合并映射为一张草稿 Delivery Note |
| `create_draft_work_order()` | 每个缺货成品明细独立创建一张草稿 Work Order |
| `_get_existing_delivery_note_qty()` | 汇总已有未取消 Delivery Note 数量，避免重复创建 |
| `_get_existing_work_order_qty()` | 按销售订单明细汇总已有未取消 Work Order 数量 |
| `_publish_completion_notice()` | 在完成事件中同时返回 Delivery Note 和多张 Work Order 编号 |

调整原则：

- 不删除现有 `Pick List` 方法，保留为兼容分支；
- 新增 Delivery Note 分支，不覆盖现有“一键创建销售送货单”接口；
- 不直接调用 `submit()`，只执行标准映射、字段补充和 `insert()`；
- 每个缺货成品独立保存点，单张工单失败不影响其他成品；
- 生产工单上的 `sales_order`、`sales_order_item`、`customer`、`sales_person`（字段存在时）和缺口数量自动填写。

### 8.2 Sales Order hook

文件：`client_akivision/hooks.py`

保留现有：

```python
"on_submit": "client_akivision.utils.sales_order_auto_fulfilment.enqueue_on_submit"
```

不修改原有 `before_validate`、`before_submit` 和既有送货接口，只在自动履约服务内部增加单据类型分支。

### 8.3 前端提示

文件：`client_akivision/public/js/sales_order_delivery.js`

拟调整完成弹窗内容：

```text
新增草稿已生成
草稿销售送货单：DN-XXXX
草稿生产工单：WO-XXXX、WO-YYYY
以上单据尚未提交，请人工核对后提交。
```

对于部分失败，弹窗同时列出成功生成的草稿和失败成品，不因一张工单失败而隐藏其他结果。

### 8.4 测试

文件：`client_akivision/utils/test_sales_order_auto_fulfilment.py`

新增测试场景：

1. 全部库存充足：生成一张草稿 Delivery Note，不生成 Work Order。
2. 一个成品部分缺货：生成一张 Delivery Note 和一张 Work Order。
3. 多个成品缺货：生成一张 Delivery Note 和多张 Work Order，每张工单只对应一个成品。
4. 全部缺货：不生成空 Delivery Note，按缺货成品分别生成多张 Work Order。
5. 已存在草稿或已提交下游单据：只创建差额，不重复创建。
6. 所有单据均为 `docstatus = 0`，关联订单、订单明细、客户、业务人员和数量正确。
7. 一个成品工单失败时，其他成品仍继续处理，完成弹窗显示成功和失败明细。

## 9. 新调用链路

```text
Sales Order 提交成功
  → on_submit 入队（after_commit）
  → 读取已提交 Sales Order
  → 按 Sales Order Item 逐条读取待交付数量和可用库存
  → 库存充足明细汇总
  → 创建一张草稿 Delivery Note
  → 缺货明细逐条计算缺口
  → 每个缺货成品创建一张草稿 Work Order
  → 自动填写订单、明细、客户、业务人员、物料、数量
  → 写销售订单时间线
  → 发布完成 realtime 事件
  → 前端弹窗显示 Delivery Note 和多张 Work Order
  → 仓库/生产人员人工核对并提交
```

## 10. 受影响模块与风险控制

| 模块 | 影响 | 控制方式 |
|---|---|---|
| 销售订单 | 提交后新增异步规划 | 不改变提交校验，失败不回滚订单 |
| 销售送货单 | 库存充足明细自动出现草稿 | 复用标准映射，不自动提交 |
| 生产工单 | 每个缺货成品新增一张草稿 | 按明细关联，不合并不同成品 |
| 库存 | 读取库存，不直接扣减 | 不写 Stock Ledger，提交时由标准校验 |
| 客户/业务人员 | 自动从销售订单带入 | 字段不存在时跳过，不破坏标准 DocType |
| 通知 | 显示一张送货单和多张工单 | realtime + 时间线，失败分项反馈 |
| 旧送货接口 | 继续保留人工一键创建 | 新自动分支不覆盖旧接口 |

## 11. 最终预期效果

对于一张包含多个成品的销售订单：

- 库存充足的成品自动进入同一张草稿销售送货单；
- 每个库存不足的成品自动生成一张独立草稿生产工单；
- 草稿自动带入销售订单、订单明细、客户、业务人员、物料和数量；
- 所有草稿保持未提交；
- 提交完成后有“正在生成”提示；
- 后台完成后有“新增草稿已生成”弹窗；
- 弹窗展示送货单和全部生产工单编号；
- 人工核对后分别提交送货单和生产工单；
- 单个成品处理失败不会阻断其他成品的草稿生成。
