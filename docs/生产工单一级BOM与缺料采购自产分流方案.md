# 生产工单一级 BOM 与缺料采购／自产分流方案

日期：2026-10-13  
状态：已于 2026-10-13 按方案实现。下文保留设计说明，实际完成情况见第 14 节。

## 1. 目标与范围

生产工单默认按成品 BOM 的直接组件（一级物料）安排领料，包括半成品及直接原材料。蓝框位置新增“显示全部物料”，展开子 BOM 层级供查看；展开操作不得改变工单需求、领料数量、库存扣减和成本归集。

生产领料缺料弹窗中，有有效子 BOM 的半成品增加“发起生产工单”复选框：勾选则针对待安排缺口创建子生产工单，不采购该半成品；未勾选则针对半成品本身创建采购申请，不展开采购其下级材料。普通原材料走采购申请。已有库存优先用于满足需求。

本轮优先限定于生产工单关联的“生产领料调拨（Material Transfer for Manufacture）”和“领料出库（Material Issue）”。采购收货、销售出库、普通调拨及其他出入库不套用缺料生产规则。

## 3. 实施原则与兼容范围

1. 不修改 ERPNext 核心代码，不改旧 RPC 参数及返回结构。
2. 新规则增加显式模式标记，旧工单及旧缺料接口继续运行。
3. 新模式下实际需求始终为一级组件，全层级视图与 `required_items` 分离。
4. 已提交、已领料或已有库存流水的旧工单不自动切换模式。需要按原流程完成或另行评估取消／修订，不直接重写历史物料行。
5. 库存变化全部使用标准 Stock Entry、Purchase Receipt 等单据，不直接写库存台账。
6. 勾选只表示补料决策；点击“确认并发起补料”才创建单据，不能在勾选瞬间创建。

## 4. 字段与 UI 方案

建议新增 `Work Order.custom_direct_component_supply`（Check，一级组件补料模式），复用 `custom_layered_mode`。新模式启用时必须满足公司允许分层组装，设置 `custom_layered_mode=1`、`use_multi_level_bom=0`，并重取直接组件；不影响旧分层模式。

首期不在已提交工单 `required_items` 中保存可编辑采购／自产复选框，避免改变已提交子表。复选框放在缺料弹窗行内，默认为未勾选。仅有有效子 BOM 的行显示可选框；无子 BOM 行显示“采购”。

工单界面：

```text
所需物料 ⌄    [□ 显示全部物料]
┌──────────┬──────────┬──────────┬──────────┐
│ 物料     │ 子 BOM   │ 发料仓   │ 需求数量 │
├──────────┼──────────┼──────────┼──────────┤
│ 半成品 A │ BOM-A    │ 仓库 T   │ 10       │
│ 原材料 C │ —        │ 仓库 T   │ 20       │
└──────────┴──────────┴──────────┴──────────┘

勾选“显示全部物料”后增加独立只读层级视图：
半成品 A（需求 10）
  ├─ 原材料 A1（折算需求 ...）
  └─ 原材料 A2（折算需求 ...）
原材料 C（需求 20）
```

缺料弹窗：

```text
物料      本次需求  可用库存  缺口  已安排  待安排  发起生产工单  子 BOM
半成品 A     10        4       6      0       6       ☑          BOM-A
半成品 B      5        0       5      0       5       □          BOM-B
原材料 C     20        8      12      0      12       —          —
                                          [确认并发起补料]
```

确认结果：A 创建数量 6 的子工单，B 创建数量 5 的采购申请，C 创建数量 12 的采购申请。单据默认创建草稿，不自动提交、审批或扣库存。

## 5. 业务流与数量规则

```text
销售订单／生产需求 → 创建新模式主工单 → 获取一级组件
                                       ↓
                         创建本批生产领料库存单
                                       ↓
                     按物料＋发料仓计算可用库存
                                       ↓
                 库存足够 → 标准领料提交／库存记账
                 库存不足 → 展示缺料弹窗
                                       ↓
                       扣除已有未完成补料安排
                                       ↓
          有有效子 BOM 且勾选 → 创建子生产工单草稿
          有效子 BOM 未勾选  → 创建半成品采购申请草稿
          无子 BOM 原材料    → 创建原材料采购申请草稿
                                       ↓
           生产／采购正式入库 → 主工单重新领料 → 主工单完工入库
```

- 缺口 = max(本次领料库存单位需求 − 可用库存, 0)。
- 可用库存需考虑发料仓、过账时间及其他工单预留，不能只读取物料全公司库存。
- 待安排数量 = max(缺口 − 已安排未完成补料数量, 0)。
- 新接口只允许将待安排缺口整体分配到采购或自产之一，不提供混合比例；旧接口保留混合功能。
- 已安排但未入库的补料只能减少“新增安排量”，不能作为可领库存。
- “优先用库存”不等于弹窗自动扣库存。库存单仍不能超库存提交；用户可另行调整本批领料量先领取可用部分，剩余需求到货后再领。首期不自动拆单、不自动部分提交。
- 子工单生产数量按库存单位缺口换算，并校验 BOM 产出单位及换算关系；不能忽略 BOM 产出数量或把展示单位直接当库存单位。
- 子工单完成并正式入库至主工单可取料仓后，主工单才能领用。子工单的原材料不足，递归进入同样流程。

## 6. BOM 选择与校验

优先使用主 BOM 对应组件行的 `bom_no`，避免擅自切换组件生产版本；未指定时才考虑物料有效默认 BOM。必须校验 BOM 物料匹配、已提交、启用、访问权限、公司适用性及单位换算。

同一物料关联多个子 BOM 时不能任意选一个；首期提示明确生产版本，不自动合并。全层级展示保留每条路径及层级，校验循环引用并限制最大深度，避免无限展开。

未勾选表示请求采购，不代表绕过采购资格：不可采购物料应明确报错。勾选表示请求自产：无效子 BOM 应明确阻止。旧接口的 `custom_supply_mode` 校验不删除；新模式是否以此限制采购／自产建议仍遵守已有限制，冲突时提示维护物料供应方式，不静默替换用户选择。

## 8. 新接口与拟议代码示意

新增只读接口：

```python
@frappe.whitelist()
def get_work_order_component_tree(work_order):
    # 读取权限、公司和 BOM 校验；基于工单 BOM 按路径递归。
    # 返回层级、父路径、子 BOM、库存单位需求，不写 required_items。
    return {"work_order": work_order, "rows": rows}
```

新增缺料安排接口，避免修改 `allocate_shortage(entry, selections)` 旧契约：

```python
@frappe.whitelist()
def allocate_direct_component_shortage(entry, decisions):
    # 校验新模式、来源工单及库存单权限。
    # 锁定来源工单，重新计算缺口及已安排数量。
    # decisions 仅携带 item_code、warehouse、create_work_order 布尔值。
    # 按服务端待安排量生成唯一方式；验证有效 BOM／采购资格。
    # 标准单据 insert 后登记 Layered Supply Allocation。
    return {"created": created, "existing": existing, "rows": refreshed_rows}
```

不要在新接口直接信任前端缺口、BOM 编号或采购数／自产数。建议抽出旧接口中单据构造及关联记录的内部帮助函数，由新旧接口复用；旧函数签名与行为不变。新接口请求整体在同一事务内完成，校验失败不留下部分草稿。

## 9. 调用链路

```text
Work Order 页面 refresh
  → 新模式判断
  → 默认 required_items（use_multi_level_bom=0）
  → 用户展开 → get_work_order_component_tree → 独立只读树表

标准 make_stock_entry
  → 继承直接组件模式
  → Stock Entry 提交前分层库存校验
  → stock_entry_shortage_dialog.js 识别新模式
  → layered_shortage_dialog.js 新复选框分支
  → get_shortage_details（沿用读取接口）
  → allocate_direct_component_shortage（新增写接口）
      → 来源工单行锁 → _shortages → _pending
      → 二选一：Material Request 草稿 / 标准 make_work_order + 子工单草稿
      → Layered Supply Allocation
  → 返回创建单据链接，原领料单保持未提交
```

子工单沿用 `custom_parent_work_order` 和 `custom_root_work_order`，通过根工单追溯销售订单，避免重复直接关联销售订单造成成本重复归集。采购申请继续填写现有缺料来源字段及来源分摊表，与供应商汇总采购链路兼容。

## 10. 关联模块及影响

| 模块 | 影响及处理 |
| --- | --- |
| BOM／物料 | 使用有效子 BOM、库存单位、采购资格和供应方式；全层级展示只读 |
| 生产工单 | 新工单实际需求一级化；子工单关联根工单；旧工单不批量转换 |
| 生产领料／库存 | 以直接组件计库存缺口和领料；已有预留和过账校验保留 |
| 采购申请／供应商汇总采购 | 采购半成品本身，保留来源工单和分摊关系；正式收货才计库存 |
| 生产入库／质检 | 子工单沿用已有质检与完工入库规则，不新增自动入库 |
| 销售订单／生产计划 | 核实新工单入口，确保模式及一级物料同步；不重算历史订单成本 |
| 成本归集／工单进度 | 下级生产成本随半成品标准库存价值进入主工单；查看全层级不重复扣料或计成本 |
| 权限 | 工单读取、BOM 读取、子工单创建、采购申请创建及库存操作均按用户权限校验 |

## 11. 防重与异常处理

- 复用来源工单行锁和已安排记录；两个页面重复确认不能重复覆盖同一缺口。
- 已有采购补料时，勾选自产不能自动取消采购或再建全额工单；展示已有安排，待取消原单据后重新安排剩余缺口。
- 已有子工单时未勾选也不重复采购。停止／取消后的剩余安排量重新计算，保留历史关联。
- 明确提示 BOM 无效、不可采购、单位无法换算、没有权限、公司不一致及物料结构变化等原因。
- 库存变化时以确认瞬间重新计算为准；返回新的需求和缺口供用户核对，不沿用旧弹窗数量。

## 12. 验收用例与预期效果

1. 主 BOM 含两个半成品和一个原材料：默认需求仅三条一级物料；全层级查看显示子件但不改变需求和库存单行。
2. 半成品需求 10、可用 4、无待补料：勾选后只创建数量 6 子工单；未勾选只创建数量 6 半成品采购申请。
3. 同一缺口已安排 2：只安排剩余 4；再次确认不新增重复单据。
4. 普通原材料只采购；库存足够不创建补料单据。
5. 不同库存单位、BOM 产出数量不为 1、非整数用量：数量换算正确。
6. 其他工单预留、多个仓库、分批领料及历史已发料：缺口按本批实际有效需求计算，不重复补料。
7. 两个用户并发、草稿取消、采购部分收货、子工单部分完工：剩余补料量正确。
8. 子 BOM 下级缺料可继续创建下一级工单／采购申请；循环 BOM 阻止展开及安排。
9. 无权限、无有效 BOM 或不可采购：明确提示且不留下部分新单据。
10. 原分层下拉模式、普通工单、采购收货和销售出库行为不变。
11. 子工单入库后主工单正常领取半成品；母子工单库存和成本不重复。

## 13. 分步落地与回退

第一步：核实目标工单及公司模式、生成工单入口；新增字段和接口，编写库存与防重测试。第二步：增加只读物料树和新弹窗分支，在测试公司新工单验证销售→生产→领料→采购／自产→入库→再领料的完整流程。第三步：启用目标公司新工单，保留旧模式回归验证。

回退只关闭新模式的创建入口及 UI 分支；已经生成的工单、采购申请、补料关联及库存流水保留，按标准取消／停止流程处理，不删台账、不重写历史需求。

本方案需在实施前明确启用范围，尤其是已有已提交工单是否需另行修订；文档阶段不执行模式切换、schema 迁移或业务单据创建。

## 14. 实施结果与验证记录

- 在 `layered_manufacturing.py` 新增工单初始化分支、只读树接口、二选一补料接口；旧写接口对新模式明确拒绝，避免绕过二选一规则。
- 在 `layered_shortage_dialog.js` 增加新模式表单初始化、全层级只读表及缺料复选框分支。为减少文件改动，工单 UI 也放在已全局加载的该脚本中，没有改动 `work_order.js`。
- 在 `stock_entry_shortage_dialog.js` 先查询工单模式再决定入口，分层查询失败不降级为旧采购；保留普通工单原入口。
- 增加 schema 迁移文件和 `before_validate` 事件。目标站点 `aki_test.localhost` 已执行字段初始化；为截图公司“阿基视觉（东莞）”开启允许分层组装，新工单自动进入新模式。其他公司未修改。
