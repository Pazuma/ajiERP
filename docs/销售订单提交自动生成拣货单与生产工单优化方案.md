# 销售订单提交自动生成拣货单与生产工单优化方案

## 1. 文档目的

本文沉淀“销售订单提交后，按成品可用库存自动创建草稿销售拣货单，库存不足时按缺口自动创建草稿生产工单”的小增量实施方案。

本文最初用于描述设计和预期改动。第一阶段功能已于 2026-09-14 按本文方案实施；系统只创建下游草稿，不自动提交拣货单或生产工单。

### 1.1 当前实施状态

- 已新增独立服务 `client_akivision/utils/sales_order_auto_fulfilment.py`；
- 已在 Sales Order 现有 hook 中追加独立 `on_submit` 分支；
- 已实现标准 Pick List 映射、生产缺口计算、草稿 Work Order、幂等检查和失败隔离；
- 已实现按销售订单合并的生产角色 Notification Log；
- 已新增 `client_akivision/utils/test_sales_order_auto_fulfilment.py`；
- 已刷新站点缓存，后台 Worker 在线；
- 专项自动测试 5 项全部通过；
- 已在事务保存点内用真实站点数据创建并回滚草稿 Pick List 和 Work Order，标准 DocType 校验链通过。

## 2. 目标与边界

### 2.1 目标

销售订单成功提交后，系统自动完成一次备货拆分：

```text
销售订单待交付数量
    = 当前可拣数量
    + 需要生产数量
    + 无法自动处理数量
```

- 有可用成品库存：创建一张草稿 Pick List（界面名称为“销售拣货单”）。
- 成品库存不足：对具有有效 BOM 的生产物料，按缺口分别创建草稿 Work Order（生产工单）。
- 无有效 BOM、非库存物料、外包直送等不适用场景：不强行建单，记录处理结果供人工查看。
- 所有自动生成单据均保持草稿，由仓库人员和生产人员核对、调整并提交。

### 2.2 不在首期范围内

- 不自动提交拣货单或生产工单。
- 不自动创建采购申请、采购订单或原料补货单。
- 不修改 ERPNext 标准 `create_pick_list`、Work Order Controller 或库存台账逻辑。
- 不覆盖现有白名单接口，不改变现有“创建销售送货单”流程。
- 不保证生产原料齐套；草稿生产工单只表达成品生产需求。
- 不自动取消、删除或修改人员已经处理过的下游单据。

## 3. 当前系统情况

### 3.1 已有销售订单扩展

- `client_akivision/hooks.py` 已为 Sales Order 配置 `before_validate` 和 `before_submit`，尚无专属 `on_submit` 处理器。
- `client_akivision/public/js/sales_order_delivery.js` 提供简化销售送货入口。
- `custom_filters/public/js/sales_order.js` 展示销售出货明细。
- 两个 App 均扩展 Sales Order，因此本功能应集中在 `client_akivision` 后端独立模块中，避免继续耦合前端脚本。

### 3.2 可复用标准能力

ERPNext 已提供：

- `erpnext.selling.doctype.sales_order.sales_order.create_pick_list`：从已提交销售订单映射 Pick List，处理未交付数量、产品套装、多仓、批次和序列号位置。
- `Pick List.set_item_locations()`：按仓库可用库存生成拣货位置。
- Work Order 标准字段 `sales_order`、`sales_order_item`、`production_item`、`bom_no`、`qty`、`fg_warehouse`。
- Bin 库存字段和标准库存工具函数。

首期优先组合这些标准能力，不复制或覆盖 ERPNext 内部实现。

## 4. 推荐业务口径

### 4.1 待处理数量

按 Sales Order Item 的库存单位计算：

```text
待交付库存数量 = max(stock_qty - delivered_qty * conversion_factor, 0)
```

还应扣除该订单明细已有、未取消的草稿或已提交拣货数量，避免重复生成：

```text
本次待规划数量 = 待交付库存数量 - 已有关联拣货数量 - 已有关联生产工单数量
```

所有比较使用字段精度和 `flt`，禁止用整数截断。

### 4.2 可拣数量

推荐以 ERPNext 标准 Pick List 实际生成的 `locations.stock_qty` 合计作为“本次可拣数量”，而不是自行用单个 Bin 的 `actual_qty` 简单判断。这样可以保留：

- 多仓库拆分；
- 仓库树；
- 批次和序列号；
- 已拣数量；
- 产品套装组件；
- ERPNext 自带库存校验。

若销售订单启用了 Stock Reservation 且明细已有 `stock_reserved_qty`，标准 ERPNext 禁止直接创建 Pick List。首期应跳过该订单的自动拣货并记录“存在预留库存，需按预留流程人工处理”，不绕过标准校验。

### 4.3 生产缺口

普通生产物料按销售订单明细分别计算：

```text
生产缺口（库存单位）
    = 本次待规划数量 - 本次实际可拣数量
```

创建 Work Order 时：

- `production_item` = Sales Order Item.item_code；
- `sales_order` = Sales Order.name；
- `sales_order_item` = Sales Order Item.name；
- `qty` = 生产缺口库存数量；
- `bom_no` = 销售订单明细 BOM，若为空则取该物料当前有效默认 BOM；
- `fg_warehouse` = 明细仓库，缺失时回退销售订单 `set_warehouse`，仍为空则记录异常；
- `planned_start_date` / 预计完成日期依据订单交付日期初始化，允许生产人员修改；
- 调用 Work Order 标准方法补充工序和所需物料后，仅执行 `insert()`，不执行 `submit()`。

缺口是成品需求，不等于可生产数量。即使原料不足，也保留草稿工单供生产人员判断和后续补料。

### 4.4 特殊明细

| 明细类型 | 首期行为 |
|---|---|
| 普通库存成品，有有效 BOM | 可用量进入草稿拣货单，缺口创建草稿生产工单 |
| 普通库存商品，无 BOM | 可用量进入草稿拣货单，缺口记录“无有效 BOM” |
| 非库存物料 | 不创建拣货单和生产工单，记录跳过 |
| `delivered_by_supplier = 1` | 跳过，保留供应商直送流程 |
| Product Bundle | 沿用标准 Pick List 拆组件；首期不对虚拟套装父项创建生产工单 |
| 已关闭、暂缓、取消订单 | 不处理 |
| 已完全交付明细 | 不处理 |
| 已有预留库存 | 不绕过标准限制，记录人工处理 |

## 5. 调用链路

### 5.1 主链路

```text
用户提交 Sales Order
  -> ERPNext 完成 Sales Order.submit()
  -> client_akivision Sales Order.on_submit 新增处理器
  -> after_commit 入队 enqueue_sales_order_fulfilment_plan(sales_order)
  -> 后台任务读取已提交销售订单
  -> 幂等检查：现有 Pick List / Work Order
  -> 调用 ERPNext create_pick_list(sales_order)
  -> 标准 set_item_locations() 形成实际可拣位置
  -> 有可拣位置：保存草稿 Pick List
  -> 逐销售订单明细计算剩余生产缺口
  -> 查找有效 BOM
  -> 有 BOM：分别保存草稿 Work Order
  -> 本次有新工单：向生产角色用户发送一条合并的 Notification Log
  -> 无 BOM或不适用：记录处理结果
  -> 更新销售订单时间线/评论，列出新建单据和异常
```

### 5.2 为什么使用提交后后台任务

- 必须等销售订单事务成功提交，避免下游草稿引用尚未提交的数据。
- 拣货位置、批次、序列号和 BOM 展开可能耗时，不应阻塞销售人员提交订单。
- 单个物料异常不应回滚已经成功提交的销售订单。
- 使用固定 `job_id` 加数据库幂等检查，可以抵御重复队列任务。

建议调用方式：

```python
frappe.enqueue(
    "client_akivision.utils.sales_order_auto_fulfilment.create_draft_fulfilment_documents",
    queue="short",
    enqueue_after_commit=True,
    job_id=f"sales-order-auto-fulfilment::{doc.name}",
    sales_order=doc.name,
)
```

后台函数必须再次校验 `docstatus == 1`，不能只信任 hook 入参。

## 6. 小增量代码修改方案

### 6.1 新增后端服务文件

新增：

`client_akivision/utils/sales_order_auto_fulfilment.py`

职责建议拆分如下：

```python
def enqueue_on_submit(doc, method=None):
    """只负责在事务提交后入队。"""

def create_draft_fulfilment_documents(sales_order):
    """后台编排入口；幂等地创建草稿下游单据。"""

def build_draft_pick_list(sales_order_doc):
    """复用 ERPNext create_pick_list，过滤空位置并保存草稿。"""

def calculate_shortages(sales_order_doc, pick_list=None):
    """按 Sales Order Item 名称计算待交付、已拣、已生产和剩余缺口。"""

def create_draft_work_order(sales_order_doc, item_row, shortage_qty):
    """按一条销售订单明细创建一张草稿生产工单。"""

def get_existing_planned_qty(sales_order, sales_order_item):
    """汇总未取消 Pick List 与 Work Order，保证重复调用不重复建单。"""

def notify_production_users(sales_order_doc, work_orders):
    """本次有新草稿工单时，向生产角色用户发送一条合并通知。"""

def add_result_comment(sales_order_doc, result):
    """把成功单据和异常写入销售订单时间线。"""
```

实现原则：

- 使用标准 Document API 和 ERPNext 映射函数，不直接拼装数据库记录。
- 以 `sales_order + sales_order_item` 标准关联字段做幂等键，首期不新增数据库字段。
- 对已有关联草稿及已提交单据都计入已规划数量；取消单据 `docstatus = 2` 不计入。
- 单张 Work Order 创建失败时记录对应明细错误，继续处理其他明细。
- 整体失败使用 Frappe Error Log，并在 Sales Order 时间线给出可读提示。
- Pick List 和 Work Order 仍执行标准字段及业务校验；仅服务端草稿 `insert` 使用 `ignore_permissions=True`，避免普通销售提交人因缺少仓库/生产建单权限导致自动化失败。该入口不白名单开放，只能由已提交 Sales Order 的后台任务触发。

### 6.2 修改 hooks

修改：

`client_akivision/hooks.py`

只给现有 Sales Order 分支增加 `on_submit`，不修改已有事件：

```python
"Sales Order": {

    "before_submit": "...validate_customer_sales_person",
    "on_submit": "client_akivision.utils.sales_order_auto_fulfilment.enqueue_on_submit",

```

此处是新增分支，不覆盖 ERPNext 方法，也不影响 `custom_filters` 的销售订单前端扩展。

### 6.3 草稿生产工单通知提醒

首期复用 Frappe 标准 `Notification Log` 和 Desk 顶部通知铃铛，不新增悬浮图标，也不修改 Frappe 通知组件。

触发条件：

- 本次后台任务实际新建了一张或多张草稿 Work Order；
- 仅查询到既有工单、重复任务没有新增工单时不发送；
- 创建工单全部失败或只有无 BOM 异常时，不向生产人员发送“新工单”通知，异常仍写入销售订单时间线。

接收人规则：

- 仅发送给启用状态的系统用户；
- 用户至少具有 `Manufacturing User` 或 `Manufacturing Manager` 生产角色；
- 去重后每位用户每张销售订单收到一条通知；
- 实施前需结合站点实际角色确认最终角色集合，避免把通知发给无权读取 Work Order 的用户。

通知内容建议：

```text
标题：有新的草稿生产工单待确认

销售订单 SAL-ORD-2026-00040 库存不足，
系统已生成 2 张草稿生产工单，请核对 BOM、数量、仓库和排期。

WO-2026-00018：物料 A，数量 40
WO-2026-00019：物料 B，数量 20
```

交互与链接：

- Desk 右上角通知铃铛显示未读数量小圆点；
- 点击通知优先回到来源 Sales Order，由标准 Dashboard 和时间线查看全部关联工单；
- 通知内容列出本次新建工单编号；若标准通知内容不支持多个可靠链接，以来源销售订单作为唯一跳转目标；
- 用户阅读后沿用 Frappe 标准已读状态，不另建已读字段。

示意效果：

```text
       ①
      [铃铛]

有新的草稿生产工单待确认
SAL-ORD-2026-00040 · 新增 2 张草稿工单
```

实现建议仍放在新增的 `sales_order_auto_fulfilment.py` 中，通过 Document API 创建 `Notification Log`。通知创建失败只记录错误，不回滚已创建的草稿 Pick List、Work Order 或已提交的 Sales Order。

左侧“生产”模块图标的红色数量徽标不纳入首期。该能力需要持续统计待处理草稿、定义已读与已处理口径，并修改自定义模块栏；待标准铃铛方案稳定后再单独评估。

## 8. 幂等、并发与事务设计

### 8.1 幂等查询

重复任务开始前，应按订单明细汇总：

- Pick List Item：`sales_order`、`sales_order_item`，父单 `docstatus < 2`；
- Work Order：`sales_order`、`sales_order_item`、`docstatus < 2`。

只为未覆盖的差额创建新草稿。不得仅判断“有没有单据”，因为部分库存场景需要按数量判断。

### 8.2 并发保护

- 后台任务以销售订单名生成固定 `job_id`。
- 处理时对 Sales Order 重新读取，并可使用数据库锁或缓存锁将同一订单串行化。
- 保存每张下游草稿前再次查询现有数量，防止两个 Worker 同时创建。
- Pick List 创建与 Work Order 创建分别设保存点；单个分支失败不能留下半构造文档。

### 8.3 重试策略

- 队列临时失败允许重试，幂等检查保证不会重复建单。
- 无 BOM、无仓库、预留库存属于业务异常，不自动无限重试。
- 结果评论只在结果发生变化时新增，避免时间线被重复消息刷屏。

## 9. 修改、取消及后续库存变化

### 9.1 销售订单修改

ERPNext 已提交订单修改或 Update Items 后，首期不自动改写既有草稿。建议增加一个显式“重新计算备货计划”后台动作作为第二阶段：

- 数量增加：只补建差额；
- 数量减少：不自动删除草稿，提示人工调整；
- 已提交下游单据：只提示冲突，绝不自动改写。

### 9.2 销售订单取消

首期不自动取消关联单据：

- 有草稿 Pick List / Work Order：在取消前或取消后提示清单，由负责人处理；
- 有已提交下游单据：继续使用 ERPNext 标准取消依赖校验；
- 禁止使用 `ignore_links` 绕过关联校验。

### 9.3 提交后库存变化

自动方案只是提交时快照。拣货人员打开草稿或提交时，ERPNext 会重新校验实际库存。如果库存被其他业务消耗，允许人工调整草稿，不自动二次创建生产工单，以免库存波动导致不断建单。

## 10. 受影响模块

| 模块 | 影响 | 风险控制 |
|---|---|---|
| 销售订单 | 提交后新增异步备货任务 | 不改变提交校验；任务失败不回滚订单 |
| 销售拣货单 / Pick List | 自动出现草稿单据 | 复用标准映射和位置分配；不自动提交 |
| 生产工单 / Work Order | 按缺口新增草稿 | 每个销售订单明细独立关联；人员核对后提交 |
| 系统通知 / Notification Log | 新工单生成后向生产用户发送合并提醒 | 复用标准铃铛和已读状态；重复执行不重复提醒 |
| 库存与仓库 | 提交瞬间读取可用库存 | 不写 Stock Ledger；草稿不扣库存 |
| BOM | 查询有效默认 BOM并展开需求 | 不修改 BOM；无 BOM 记录异常 |
| 批次/序列号 | 由标准 Pick List 分配 | 不自行实现分配算法 |
| Stock Reservation | 与标准 Pick List 存在互斥约束 | 首期跳过并提示，不绕过校验 |
| 销售送货 | 后续仍可从拣货单生成 Delivery Note | 不改变已有简化送货接口 |
| 生产计划 | 不直接参与首期链路 | 不修改 `custom_filters.production_plan_work_order` |
| 权限与队列 | 后台创建草稿需要建单权限 | 明确执行用户与失败日志，禁止静默越权 |
| 项目进度引用 | 新建 Work Order 可能触发现有通用事件 | 回归验证项目字段和进度引用，不移除现有 hook |

## 11. 预期效果

### 11.1 全部有库存

```text
销售订单：A 100

结果：
- 草稿销售拣货单：A 100
- 草稿生产工单：无
- 销售订单保持已提交

销售订单：A 100
可拣库存：A 0

结果：
- 不保存空拣货单
- 草稿生产工单：A 100
```

结果：

- 一张草稿生产工单：A 40

```text

- 不新增重复生产工单
- 已规划总量仍为 100
```

### 11.6 人员操作体验

仓库人员：

- 在 Pick List 列表看到新草稿；
- 打开后核对仓库、批次、序列号和实拣数量；
- 调整无误后人工提交，再进入送货流程。

生产人员：

- Desk 通知铃铛出现未读数量小圆点；
- 每张销售订单只收到一条合并的“草稿生产工单待确认”提醒；
- 点击提醒回到来源销售订单，查看本次新建工单编号及关联单据；
- 在 Work Order 列表看到按缺口生成的新草稿；
- 核对 BOM、生产数量、工序、原料仓、成品仓和排期；
- 原料不足时按现有生产/采购流程处理；
- 确认后人工提交。

销售人员：

- 销售订单提交不被长时间阻塞；
- 在订单时间线看到已生成的草稿单据链接以及未处理异常；
- 不需要手工计算库存与生产缺口。

### 12.1 自动测试

至少覆盖：

1. 全库存、零库存、部分库存。
2. 多明细、多仓库和单位换算。
3. 有 BOM、无 BOM、停用 BOM。

## 13. 分阶段实施建议

### 第一阶段：最小闭环

- 新增独立后端服务和 Sales Order `on_submit` hook。
- 自动创建草稿 Pick List 和草稿 Work Order。
- 使用标准 Notification Log 向生产角色用户发送按销售订单合并的提醒。
- 完成幂等、异常日志和自动测试。
- 不新增前端、不新增字段、不改老接口。

### 第二阶段：可视化与人工重算

- Sales Order 增加只读生成状态和“重新计算差额”入口。
- 增加公司级启用开关及默认仓库配置。
- 对订单 Update Items 和取消场景提供显式人工处理工具。

### 第三阶段：计划协同

- 无 BOM 缺口可配置转采购需求。
- 增加仓库优先级和安全库存口径。
- 评估是否统一接入 Production Plan，而不是直接创建 Work Order。

## 14. 实施前待确认事项

以下口径需要业务负责人确认后再进入代码阶段：

1. “可用库存”是否必须扣除 Stock Reservation，还是有预留库存时完全交由人工处理；本方案默认后者。
2. 仓库范围是仅销售订单明细仓库，还是允许标准 Pick List 从公司多个仓库拆分；本方案默认复用标准多仓分配。
3. 缺口工单是一条销售订单明细一张，还是同物料合并；本方案默认逐明细创建，保证追溯。
4. 无 BOM 缺口是否只提示，还是自动创建采购申请；本方案首期只提示。
5. 后台任务以提交人权限还是指定系统服务身份建草稿；建议明确服务角色并保留创建人审计。
6. Product Bundle 父项是否存在真实生产需求；本方案首期不自动创建父项工单。

## 15. 最终建议

首期采用“小增量、后台异步、标准能力优先、只建草稿、数量幂等”的实现：

```text
Sales Order on_submit（新增分支）
  -> 标准 create_pick_list
  -> 保存有实际位置的草稿 Pick List
  -> 按销售订单明细计算成品缺口
  -> 保存逐明细草稿 Work Order
  -> 时间线反馈结果
```

该方案不修改 ERPNext 核心文件，不覆盖老接口，不触碰库存台账，也不改变现有销售送货和生产计划流程。首期风险集中在库存口径、预留库存和重复触发，均通过标准映射、业务跳过规则与数量级幂等控制。
