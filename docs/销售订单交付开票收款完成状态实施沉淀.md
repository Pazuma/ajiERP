# 销售订单交付、开票、收款与最终完成状态实施沉淀

## 1. 实施目标

将销售订单报表和运营看板中的“完成”从单纯的“已交货”口径调整为业务闭环口径：

```text
销售订单全部交付
  + 订单已全部开票
  + 关联销售发票全部已付款
  = 最终完成订单
```

本次保留 ERPNext 原生 `Sales Order.status`，不直接改写标准单据状态。最终完成状态通过报表和看板动态计算，付款、发票取消、收款取消或退货后刷新页面即可重新计算。

## 3. 数据流

### 3.1 交付数据流

```text
Sales Order
  -> Sales Order Item.qty / delivered_qty
  -> 已提交 Delivery Note Item.against_sales_order / so_detail
  -> 计算每条明细是否 delivered_qty >= qty
  -> 订单级 fully_delivered
```

只统计 `Delivery Note.docstatus = 1`。送货单草稿不计入交付完成。

### 3.2 开票数据流

```text
Sales Order
  -> Sales Invoice Item.sales_order

或

Sales Invoice Item.dn_detail
  -> Delivery Note Item.name
  -> Delivery Note Item.against_sales_order
  -> Sales Order
```

只统计 `Sales Invoice.docstatus = 1`。报表同时使用销售订单的 `per_billed` 和实际发票关联判断开票状态。

### 3.3 收款数据流

```text
Payment Entry（docstatus=1, payment_type=Receive）
  -> Payment Entry Reference
  -> reference_doctype = Sales Invoice
  -> reference_name = Sales Invoice
  -> allocated_amount
```

销售发票付款事实使用：

```text
Sales Invoice.status = Paid
AND Sales Invoice.outstanding_amount <= 0
```

直接关联销售订单的订金或未分配收款不计入销售发票已付款。

### 3.4 最终状态数据流

```text
订单明细全部交付
  -> per_billed >= 100 且存在已提交关联发票
  -> 所有关联发票 status = Paid 且 outstanding_amount <= 0
  -> final_status = 已完成
```

状态不足时按顺序显示：

```text
未交付 / 交货中 / 未交货
已交付但未开票 -> 待开票
已开票但未付款 -> 待收款
部分付款 -> 部分收款
全部条件满足 -> 已完成
```

## 4. 依赖清单

| 依赖 | 要求 |
|---|---|
| Frappe/ERPNext | 可读取 Sales Order、Sales Order Item、Delivery Note、Delivery Note Item、Sales Invoice、Sales Invoice Item、Payment Entry、Payment Entry Reference |
| 数据库字段 | `delivered_qty`、`per_billed`、`sales_order`、`dn_detail`、`against_sales_order`、`status`、`outstanding_amount`、`allocated_amount` |
| 关联完整性 | 销售发票必须通过 `sales_order` 或 `dn_detail` 能追溯到销售订单 |
| 收款规范 | Payment Entry 使用 Receive 类型并在 References 中分配到 Sales Invoice |
| 权限 | 当前用户有销售订单报表、销售发票和收款数据读取权限；看板还需要 KPI 角色 |
| 前端资源 | 修改后的报表 JS 和看板 JS 需要通过 `bench build` 或站点资源刷新加载 |
| 数据更新 | 发票、收款、取消或退货后需刷新报表/看板以获得最新动态计算结果 |

## 5. 风险点清单

| 风险 | 表现 | 处理方案 |
|---|---|---|
| 发票未关联销售订单 | 订单显示未开票或收款不完整 | 优先从销售订单/送货单创建发票；异常数据进入人工核对清单 |
| 只通过 `dn_detail` 关联 | 直接 `sales_order` 为空时漏算发票 | 查询工具已支持 `dn_detail -> Delivery Note Item -> against_sales_order` |
| 多张发票 | 一张已付款、一张未付款却误判完成 | 使用订单下所有关联发票，必须全部 `Paid` |
| 收款只关联 Sales Order | 订单有订金但发票仍未付款 | 不将 Sales Order Reference 当作发票核销；只统计 Sales Invoice Reference |
| 付款未提交或被取消 | 页面仍显示已收款 | 仅统计 `Payment Entry.docstatus = 1`，取消后动态重算 |
| 发票部分付款 | 客户已付一部分但显示完成 | `outstanding_amount > 0` 或 `Partly Paid` 时显示部分收款/待收款 |
| 贷项凭证或折让 | 发票余额为零但不一定有实际到账 | 当前按财务结清口径允许余额为零；如必须实际到账，需增加财务规则 |
| 退货/红字发票 | 已交付或已收款条件被冲销 | 退货、贷项和取消后重新刷新报表；上线前复测反向流程 |
| 原生状态含义冲突 | 系统 `Completed` 与业务最终完成不同 | 本次不改原生 `Sales Order.status`，使用独立报表/看板最终状态 |
| 历史数据不完整 | 老订单无法追溯发票或收款 | 不自动补造关联；列为数据治理和人工核对范围 |
| 查询性能 | 订单量大时发票和付款查询变慢 | 当前先按本次报表订单集合查询；数据量增大后增加索引和缓存评估 |
| 前端资源缓存 | 页面仍显示旧字段 | 发布后执行 `bench build --app client_akivision`，并清理浏览器/站点资源缓存 |

## 6. 已发现问题与解决方案

### 6.1 真实 Frappe 服务不可连接

检查时发现当前环境 Docker socket 无访问权限，MariaDB/Redis/Frappe 服务未能从本会话启动，因此无法直接使用真实登录站点验证数据库结果。

解决方案：

1. 增加 Playwright 模拟数据脚本，验证真实修改后的销售订单报表 JS、状态选项、字段和响应式布局。
2. 在可访问站点后，用一笔未付款发票、一笔部分付款发票和一笔已付款发票执行真实 SQL/页面复测。
3. 若仍无法连接，先由具备 Docker 权限的部署用户启动服务，再运行本脚本和真实报表验收。

### 6.2 Chromium 受限沙箱启动失败

初次运行时 Chromium 在受限沙箱内以 `SIGTRAP` 退出。使用受控提升权限后脚本正常执行，未发现页面断言错误。

### 6.3 Playwright 验收脚本中的脚本注入问题

初版脚本把报表 JS 放在静态 HTML 中执行，页面脚本上下文未获得模拟的 `frappe` 全局对象；后改为页面加载后注入 jQuery、建立 `frappe` 夹具，再执行报表 JS，验收通过。

## 8. 需要复测的场景

### 8.1 基础状态

1. 全部送货、未开票：订单显示“待开票”。
2. 全部送货、发票未付款：订单显示“待收款”。
3. 全部送货、发票部分付款：订单显示“部分收款”。
4. 全部送货、全部发票已付款：订单显示“已完成”。
5. 未全部送货但发票已付款：订单仍不能显示“已完成”。

### 8.2 多单据和关联

1. 一个订单多张销售发票，一张已付款、一张未付款。
2. 发票通过 `Sales Invoice Item.sales_order` 直接关联订单。
3. 发票通过 `dn_detail` 间接关联送货单和订单。
4. 同一订单分批送货、分批开票、分批收款。
5. Payment Entry 直接关联 Sales Order，但未关联 Sales Invoice。

### 8.3 反向和异常

1. 取消 Payment Entry 后订单从“已完成”恢复为“待收款”。
2. 取消 Sales Invoice 后订单从“待收款/已完成”恢复为“待开票”。
3. Delivery Note 退货后订单不再满足全部交付。
4. Sales Invoice 贷项凭证使余额归零时，按财务确认口径判断是否算完成。
5. 外币发票、汇兑差异和舍入差异。
6. 无权限用户访问报表或看板时不泄露发票和收款数据。
7. 大量订单下报表加载时间和数据库查询计划。

### 8.4 页面体验

1. 桌面端状态列完整且不遮挡金额、发票号和客户信息。
2. 移动端宽表只在表格区域横向滚动，不造成整页横向溢出。
3. 看板“最终完成订单”和“全部交货订单”数值不再混淆。
4. 点击看板最终完成卡片后，销售订单报表自动带入 `status=已完成`。

## 9. 发布建议

1. 先在测试站点执行上述复测，尤其是多张发票和 `dn_detail` 间接关联场景。
2. 执行 `bench build --app client_akivision` 并刷新站点资源。
3. 对历史订单抽样比对：销售订单、送货单、销售发票、Payment Entry Reference 和发票余额。
4. 业务确认贷项、折让、预收和核销是否计入“已付款”。
5. 观察报表 SQL 耗时；如数据量大，再增加索引或改为批量汇总表。
