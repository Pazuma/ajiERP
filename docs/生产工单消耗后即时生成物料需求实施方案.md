# 生产工单消耗后即时生成物料需求实施方案

## 1. 目标

生产工单对应的制造出库或物料转移提交后，立即检查实际消耗仓库的预计库存。当物料低于安全库存时，系统自动创建并提交采购类型的物料需求单。

本方案只处理“生产消耗导致的即时检查”，不替换 ERPNext 原有的每日自动补货任务。每日任务继续作为兜底机制。

## 2. 触发范围

### 2.1 触发 DocType

在 `client_akivision/hooks.py` 的 `Stock Entry.on_submit` 中增加后台处理函数。

### 2.2 只处理以下 Stock Entry purpose

| purpose | 是否处理 | 说明 |
| --- | --- | --- |
| `Manufacture` | 是 | 生产工单制造出库，直接消耗原材料 |
| `Material Transfer for Manufacture` | 是 | 原材料转入在制品仓 |
| `Material Issue` | 否 | 普通领料不一定属于生产消耗，避免扩大范围 |
| `Material Receipt` | 否 | 入库不会导致库存低于安全库存 |
| `Material Transfer` | 否 | 普通仓库转移由目标业务另行处理 |

只处理存在 `work_order` 的生产相关 Stock Entry；如果业务存在无工单的生产领料，应另行确认是否纳入。

## 3. 处理流程

```text
Stock Entry 提交成功
  -> 读取消耗行和 source warehouse
  -> 提取 item_code + warehouse
  -> after_commit 异步执行安全库存检查
  -> 查询 Item Reorder 和 Bin.projected_qty
  -> projected_qty <= warehouse_reorder_level
  -> 检查是否已有未完成需求
  -> 创建 Material Request
  -> 写入来源 Stock Entry / Work Order
```

### 3.1 为什么使用 after_commit 异步任务

Stock Entry 提交过程中库存账和 Bin 可能仍在当前事务内更新。若在同一事务中立即读取 `projected_qty`，可能读取到旧值。建议使用 Frappe 的队列任务，并设置提交后执行，确保库存更新已经提交。

任务失败不能回滚已提交的 Stock Entry；必须记录 Error Log，并允许人工重试。

## 4. 数据来源和计算规则

### 4.1 安全库存数据源

第一阶段统一使用标准 `Item Reorder`：

- `warehouse`
- `warehouse_reorder_level`
- `warehouse_reorder_qty`
- `material_request_type`

如果界面存在自定义“最低安全库存”字段，必须在保存时同步到 `warehouse_reorder_level`，不能让两套安全库存同时参与计算。

### 4.2 库存比较值

使用 `Bin.projected_qty`，而不是只使用 `actual_qty`：

```text
projected_qty = 当前实际库存 + 预计入库 - 已预留数量 - 其他预计扣减
```

触发条件：

```text
projected_qty <= warehouse_reorder_level
```

缺少 Bin 时按 0 处理，但仓库必须存在且未禁用。

### 4.3 补货数量

```text
补货数量 = max(warehouse_reorder_qty,
               warehouse_reorder_level - projected_qty)
```

如果 `warehouse_reorder_qty` 为 0，则不创建需求，避免生成数量为 0 的物料需求。

## 5. 幂等和重复控制

即时任务和每日任务可能同时运行，必须在创建前检查：

1. 同一物料、仓库是否已有未取消且未完成的采购物料需求。
2. 当前 Stock Entry 是否已经产生过自动补货记录。
3. 同一队列任务是否重复提交。

推荐增加自定义字段：

| DocType | 字段 | 用途 |
| --- | --- | --- |
| Material Request | `custom_auto_reorder_source` | 固定值 `Production Consumption` |
| Material Request | `custom_source_stock_entry` | 记录触发的 Stock Entry |
| Material Request | `custom_source_work_order` | 记录生产工单 |
| Material Request Item | `custom_reorder_key` | 物料+仓库的幂等键 |

创建前用数据库锁或唯一键保护并发场景。不能只依赖前端按钮禁用。

## 6. 后端模块设计

建议新增：

```text
client_akivision/utils/production_reorder.py
```

建议函数：

```python
def on_production_stock_entry_submit(doc, method=None):
    """提交生产 Stock Entry 后，提交后异步检查安全库存。"""

def enqueue_reorder_check(stock_entry_name):
    """after_commit 后投递短队列任务。"""

def check_reorder_for_stock_entry(stock_entry_name):
    """读取消耗仓库，检查并创建物料需求。"""

def create_reorder_material_request(rows, source_stock_entry):
    """按公司和物料需求类型创建幂等的 Material Request。"""
```

`hooks.py` 中只增加入口，不在 hook 内堆放库存计算：

```python
"Stock Entry": {
    "on_submit": [
        "client_akivision.utils.sample_loan.on_stock_entry_submit",
        "client_akivision.utils.sample_loan.on_stock_entry_submit_for_fgs",
        "client_akivision.utils.production_reorder.on_production_stock_entry_submit",
    ],
}
```

实际实现时应保持现有 hook 顺序，并确认函数异常不会影响 Stock Entry 正常提交。

## 7. 物料需求单规则

- 默认 `material_request_type = Purchase`，但以 Item Reorder 配置为准。
- `company` 取消耗仓库所属公司。
- `warehouse` 写入 Material Request Item 的仓库字段。
- `schedule_date` 根据物料交期计算，没有交期时使用当前日期。
- 设置 `auto_created_via_reorder = 1`。
- 物料需求单提交后记录来源工单和 Stock Entry。
- 同一次 Stock Entry 的多个物料可以按公司和需求类型合并到同一张物料需求单。

## 8. 异常和可观测性

必须记录以下信息：

- Stock Entry 名称、Work Order 名称
- item_code、warehouse、projected_qty、安全库存、补货数量
- 是否跳过及跳过原因
- 创建的 Material Request 名称
- 异常堆栈和重试次数

建议在 Stock Entry 的关联记录中显示自动补货物料需求；不建议只依赖邮件通知。

## 9. 测试方案

### 9.1 后端测试

至少覆盖：

1. 制造出库使预计库存低于安全库存，创建一张采购物料需求。
2. 预计库存等于安全库存，按规则创建物料需求。
3. 预计库存高于安全库存，不创建物料需求。
4. 没有 `Item Reorder` 配置，不创建物料需求并记录跳过原因。
5. 已存在未完成物料需求，不重复创建。
6. 同一 Stock Entry 重复执行任务，不重复创建。
7. 多仓库相同物料分别按仓库安全库存计算。
8. Stock Entry 提交成功但异步任务失败，不影响原单，并可重试。
9. 取消 Stock Entry 后不自动取消采购需求，取消策略需由业务确认。

### 9.2 Playwright 验收

1. 登录 Manufacturing/Stock 权限账号。
2. 创建或选择已配置 Item Reorder 的螺丝物料。
3. 提交生产工单对应的制造出库。
4. 监听 Stock Entry 提交请求，确认返回成功。
5. 等待物料需求后台任务完成，刷新 Material Request 列表。
6. 校验新增记录的物料、数量、仓库、类型和来源字段。
7. 重复刷新列表，确认不会增加第二张重复需求。
8. 记录浏览器控制台错误、后台接口响应和页面截图。

## 10. 上线步骤与回滚

### 上线

1. 增加后端模块和 `doc_events` hook。
2. 增加必要 Custom Field 和索引/唯一约束。
3. 执行 `bench --site <site> migrate`、`clear-cache`。
4. 使用测试物料执行完整流程。
5. 观察 worker、Error Log 和 Material Request 数量。

### 回滚

1. 移除 `production_reorder` 的 Stock Entry hook。
2. 保留已创建的物料需求，不直接删除业务单据。
3. 如有错误需求，按正常业务流程取消。
4. 恢复前先确认每日标准自动补货仍可用。

## 11. 验收标准

- 生产消耗提交成功后，预计库存低于安全库存时能自动生成需求。
- 需求创建延迟通常不超过短队列处理时间，不要求页面同步等待。
- 同一物料、仓库和未完成需求不会重复创建。
- 物料需求可追溯到 Stock Entry 和 Work Order。
- 队列异常有日志且可重试。
- 不影响 Stock Entry 提交、库存记账和原有每日自动补货任务。
