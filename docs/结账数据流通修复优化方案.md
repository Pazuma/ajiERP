# 结账数据流通修复优化方案

> 文档日期：2026-09-20  
> 当前阶段：方案沉淀，尚未修改业务代码。  
> 适用模块：中国财务 `china_finance`、ERPNext Accounts。

## 1. 背景与问题结论

当前财务模块存在两层结账：

```text
Period Closing Voucher（期末结账）
    -> 负责损益结转并生成结转 GL Entry

China Closing Run（结账）
    -> 负责结账检查、报表快照、电子档案和会计冻结
```

整体调用链路是合理的，但数据字段和状态流转存在以下问题：

### 1.1 期末结账日期字段不一致

ERPNext `Period Closing Voucher` 的期间结束字段是：

```text
period_end_date
```

但中国财务 `China Closing Run.validate()` 读取的是：

```python
["company", "posting_date", "docstatus"]
```

该单据没有 `posting_date` 作为结账截止日期，导致关联凭证时可能误判公司或截止日期不一致。

### 1.2 重新开账只恢复冻结日期，没有处理关联数据状态

当前重新开账会：

- 将 `China Closing Run.status` 改为 `Reopened`；
- 记录重新开账原因、人员和时间；
- 恢复 `Company.accounts_frozen_till_date`。

但不会同步处理：

- 关联的 `Period Closing Voucher`；
- 期末结转 GL Entry；
- 已生成的 `China Report Snapshot`；
- 已生成的电子档案包。

因此可能出现“结账运行单已重新开账，但账务结转和正式报表档案仍保持有效”的状态不一致。

### 1.3 结账状态没有明确表达档案生成结果

当前提交流程在 `on_submit()` 中生成报表快照和电子档案包，但 `China Closing Run` 只有 `Draft / Closed / Reopened` 状态，无法区分：

```text
结账检查通过
结账已提交
报表快照已生成
电子档案包已生成
```

如果后续档案生成失败，使用人员难以判断结账是否完整。

## 2. 优化目标

1. 统一期末结账凭证和结账运行单的日期口径。
2. 让重新开账后的账务、报表和档案状态可追踪。
3. 明确结账检查、结账提交、快照生成、档案生成之间的状态关系。
4. 保持现有单据、接口、权限和使用入口不变。
5. 采用小增量新增字段和分支，避免修改 ERPNext 核心代码。

## 3. 设计原则

```text
1. 不修改 ERPNext Period Closing Voucher 核心代码。
2. 不删除或重命名现有 China Closing Run 字段。
3. 保留现有 API 方法名和参数。
4. 优先新增内部辅助函数和可选参数，不破坏老调用方。
5. 默认不自动取消期末结账凭证，避免误冲账。
6. 重新开账必须记录审计原因和关联状态。
7. 提交时继续执行服务端实时检查。
```

## 4. 推荐修复方案

### 4.1 统一期末结账日期字段

修改 `China Closing Run.validate()`：

```python
company, period_end_date, docstatus = frappe.db.get_value(
    "Period Closing Voucher",
    self.period_closing_voucher,
    ["company", "period_end_date", "docstatus"],
)
```

校验规则保持不变：

```text
公司必须一致
period_end_date 必须等于 China Closing Run.to_date
期末结账凭证必须已提交
```

同时在结账服务中增加统一辅助函数，避免不同位置重复读取字段：

```python
def get_valid_period_closing_voucher(name, company, to_date):
    ...
```

该函数只新增内部调用，不改变现有 `run_closing_checks()`、`preview_closing_checks()` 等接口。

### 4.2 增加结账产物状态

在 `China Closing Run` 新增只读字段：

```text
report_snapshot_status：未生成 / 已生成 / 生成失败
archive_status：未生成 / 已生成 / 生成失败
archive_error：生成失败原因
```

字段只用于表达产物状态，不替换现有 `status`。

推荐状态流转：

```text
Draft
  -> 检查通过
  -> Closed
  -> 报表快照已生成
  -> 电子档案已生成
```

如果产物生成失败：

```text
Closed
  -> report_snapshot_status = 生成失败 或 archive_status = 生成失败
```

是否允许结账正式完成，建议默认要求两项均为“已生成”。如果需要兼容历史数据，可仅显示失败状态，不回滚已提交的结账单。

### 4.3 重新开账增加关联状态处理

保留现有接口：

```python
reopen_closing(name, reason)
```

新增内部处理函数：

```python
def mark_closing_artifacts_reopened(closing_run):
    ...
```

推荐行为：

1. 保留原始 `China Report Snapshot` 和电子档案文件，不物理删除。
2. 将快照状态标记为“已重新开账”或增加 `reopened_on / reopen_reason` 字段。
3. 将档案状态标记为“已重新开账”，保留原始文件用于审计追溯。
4. 不自动取消 `Period Closing Voucher`，除非后续业务明确要求联动冲销。
5. 恢复公司冻结日期时，继续使用结账前保存的 `previous_frozen_date`。
6. 重新开账后允许重新生成新的草稿结账运行单，但不能覆盖原记录。

这样可以避免“历史档案被删除”，同时让使用者知道这些报表不再代表当前有效结账状态。

### 4.4 增加重新开账后的再次结账限制

新增校验分支：

```text
同一公司、同一期间存在已关闭结账运行单时：禁止重复提交新的 Closed 记录
原结账运行单已 Reopened 时：允许新建新的结账运行单
```

新记录必须重新执行完整检查，不能复用原记录的检查结果。

## 6. 调用链路

### 6.1 当前链路

```text
创建 Period Closing Voucher
 -> 提交
 -> 生成损益结转 GL Entry

创建 China Closing Run
 -> 关联 Period Closing Voucher
 -> 保存
 -> 生成必需对账单
 -> 运行并保存结账检查
 -> 提交
 -> 重新运行服务端检查
 -> 生成报表快照
 -> 生成电子档案包
 -> 更新 accounts_frozen_till_date
```

### 6.2 优化后链路

```text
创建 Period Closing Voucher
 -> 使用 period_end_date 作为期间截止日
 -> 提交并等待 GL 处理完成

创建 China Closing Run
 -> 统一校验 company + period_end_date + docstatus
 -> 生成必需对账单
 -> 保存结账检查结果
 -> 提交前重新执行完整检查
 -> 状态 Closed
 -> 生成四类报表快照
 -> 更新 report_snapshot_status
 -> 生成电子档案包
 -> 更新 archive_status
 -> 按设置更新 accounts_frozen_till_date
```

### 6.3 重新开账链路

```text
已关闭 China Closing Run
 -> 填写重新开账原因
 -> 检查是否存在更晚结账记录
 -> 标记快照和档案为已重新开账
 -> 恢复 previous_frozen_date
 -> 记录 reopen 时间、人员和原因
 -> 保留原期末结账凭证和原始档案
```

## 7. 受影响模块

| 模块 | 影响 |
|---|---|
| ERPNext Period Closing Voucher | 只读取其标准字段，不改核心代码 |
| China Closing Run | 主要修改点，增加日期一致性和产物状态 |
| 结账检查 | 继续复用原检查接口，统一凭证校验口径 |
| 财务报表快照 | 增加生成/重新开账状态标识 |
| 电子档案 | 保留文件，增加有效状态和失败信息 |
| Company | 继续使用 accounts_frozen_till_date 控制冻结 |
| 重新开账 | 增加关联产物状态处理 |
| 权限 | 延续 System Manager / China Finance Manager 权限 |
| 审计日志 | 继续记录结账、重新开账、失败原因和操作人 |

## 8. 兼容性和小增量控制

1. 保留 `preview_closing_checks(company, from_date, to_date, period_closing_voucher, closing_type)` 原参数。
2. 保留 `run_and_save_closing_checks(name)` 原接口。
3. 保留 `reopen_closing(name, reason)` 原接口，仅增加内部状态处理。
4. 不修改 ERPNext 标准 `Period Closing Voucher` 字段。
5. 不自动取消已提交的期末结账凭证。
6. 不删除历史报表快照和电子档案。
7. 历史 `China Closing Run` 记录新增状态字段时使用默认值，不影响读取。
8. 旧版本结账记录没有产物状态时，页面按“未记录”兼容展示。

## 9. 预期效果

### 9.1 数据正确性

- 结账运行单能正确识别期末结账凭证的公司和截止日期。
- `period_end_date` 成为期末结账和中国财务结账的统一期间口径。
- 结账检查和表单校验结果一致。

### 9.2 状态可追踪

- 能明确看到结账是否已生成报表快照。
- 能明确看到电子档案是否生成成功。
- 产物生成失败时有可追踪的错误信息。
- 重新开账后，原快照和档案不会被误认为当前有效结果。

### 9.3 审计和操作安全

- 原结账记录、原始档案和重新开账原因均保留。
- 不因重新开账而物理删除历史财务资料。
- 同期间重新结账必须重新检查，不复用旧检查结果。
- 更晚期间存在时，仍禁止回退较早期间。

## 10. 验收标准

1. 新建期末结账凭证，使用 `period_end_date` 提交成功。
2. 创建相同公司、相同截止日期的 China Closing Run，关联校验通过。
3. 公司或截止日期不一致时，保存时明确阻止。
4. 期末结账未提交时，China Closing Run 不能提交。
5. 结账检查通过后提交，报表快照状态为“已生成”。
6. 电子档案生成成功后，档案状态为“已生成”，并存在可访问文件。
7. 快照或档案生成失败时，状态为“生成失败”，并记录错误原因。
8. 重新开账必须填写原因，并保留原始快照和档案。
9. 重新开账后公司冻结日期恢复到结账前值。
10. 同一期间重新结账时必须重新创建并重新检查，不能覆盖旧记录。
11. 不影响标准 ERPNext 期末结账、财务报表、总账和现有权限。

## 11. 实施前需确认的业务决策

以下事项在正式改代码前需要确认：

1. 重新开账是否只解除中国财务结账，还是同时要求取消 ERPNext 期末结账凭证。
2. 重新开账后的原始报表快照是否标记为“已重新开账”，还是保留“正式”状态并增加失效标识。
3. 电子档案生成失败时，是否允许 `China Closing Run` 保持 `Closed`，还是必须阻止提交。
4. 月结和年结是否使用相同的档案完整性要求。

推荐默认决策：

```text
重新开账不自动取消期末结账凭证；
原快照和档案保留但标记为已重新开账；
档案生成失败显示失败状态并阻止结账完成确认；
月结和年结使用同一套基础校验，年结额外执行年结检查。
```
